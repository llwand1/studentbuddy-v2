## §0 为什么是邮箱（资质矩阵，本契约的成立前提）

微信 / 手机号登录**都需要企业资质**，个人开发者做不了——这不是偏好问题，是硬门槛：

| 登录方式 | 资质门槛 | 个人开发者可做 | 依据 |
|---|---|---|---|
| 微信网页登录（开放平台·网站应用） | 企业营业执照 + 已备案域名 + HTTPS；认证费 ¥300/年 | **否** | 开放平台明确「个人开发者无法创建网站应用」 |
| 手机号短信验证码 | 企业（短信签名需实名制报备，个人自用资质已停止受理） | **否** | 阿里云短信：个人认证账号无法以个人名义申请签名 |
| **邮箱 + 密码** | **无** | **是** | 无第三方依赖，自建即可 |
| **邮箱 + 验证码（M1.5）** | **无**（需自有域名 + DNS 记录） | **是** | 自建发信通道，见 §4.6 |

⇒ **MVP 走邮箱 + 密码**，零资质、零第三方依赖、边际成本为零。

### §0.1 2026-09-18 拍板：微信 / 手机号确认不做，改走邮箱验证码

老板原话：「**不做微信登录了，搞完整的邮箱验证码登录**，然后模型的 api 可以让用户自带 api，但是我们自己也提供免费的额度，然后我是海外服务器，应该不要备案」。

三条结论：

1. **微信 / 手机号登录不再作为 M4 增强**。原 §0 写「企业资质就绪后接入」是留后路；但按上表，两者对**个人主体**是**永久不可得**（不是「暂时没资质」），继续挂在路线图上只会让规划失真。若将来主体变更，**仍必须映射到同一 user**（openid / phone 关联，不新建账号）。
   ★ **「两套身份合并到同一 user」已提前落地**（2026-09-18 老板点单「pk 就邮箱登录」）：原计划 M4 才做的合并，现因 PK 改用邮箱登录而**在 P1 提前做**——`pk_users` 不再写入，PK 身份直接取 `users`（细则见 `PK-SPEC §14.1`）。
   ★★ **GitHub 是本条原则的显式例外（2026-09-21 老板拍板）**：上面「不新建账号 / 映射到同一 user」的口径**只适用于将来接入的国内渠道（微信 / 手机号）**，**不适用于 GitHub**。GitHub 登录走**严格独立建号**——同一个邮箱在站内有邮箱账号、GitHub 也用该邮箱，**算两个彼此独立的账号**（完整口径见 §2.8 口径 1）。
   ⚠️ **这条例外是刻意背离「身份归一」原则的，理由必须一并记住**：GitHub 的邮箱验证体系由**第三方**掌握（用户可在 GitHub 侧增删 / 改绑邮箱），若把「GitHub 验证过某邮箱」当作「可登入本站该邮箱账号」的凭据，等于**把本站账号的进入权外包给了 GitHub** —— 用户无法在本站侧单独撤销这个入口，且 GitHub 账号一旦易主，本站账号随之易主。独立建号把两者的授权边界彻底切开：**GitHub 只是第三种「证明你是谁」的方式，不是「认领既有账号」的方式**。
2. **登录方式定为「邮箱 + 密码」与「邮箱 + 验证码」双通道并存**——密码走主路径，验证码用于注册验证、免密登录与找回密码（详见 §2.5）。★ **刻意不做「纯验证码、砍掉密码」**：验证码登录把可用性绑死在**发信通道的送达率**上（见 §4.6），一旦邮件进垃圾箱或延迟，用户**连门都进不去**；密码是那条不依赖外部服务的退路。
3. **服务器在海外 ⇒ 不适用 ICP 备案**（一手依据：阿里云备案帮助中心「域名解析指向境外服务器，则无需 ICP 备案」，2026-04-23 更新）。⚠️ 但这条同时**排除了全部国内发信厂商**——阿里云 / 腾讯云（国内站）邮件推送均要求域名备案，与海外服务器直接冲突 ⇒ 发信通道只能用海外服务商，而国内邮箱的送达率风险随之上升（§4.6）。⚠️ 同页另写「需完成**公安联网备案**」，对纯海外主体的实际执行较宽松，**此项待核实**，不在本契约的阻塞路径上。

### §0.2 范围（M1 做什么 / 不做什么）

- **做**：`users` / `auth_sessions` 两张表；邮箱密码注册、登录、登出、取当前用户四端点；
  httpOnly cookie 会话；登录失败限流；`requireAuth` 中间件（**开关 `SB_REQUIRE_AUTH` 默认关**）。
- **不做（本版）**：数据隔离（M2，给所有业务表加 `user_id`）、强制鉴权上线。
- **本版之外**：~~微信 / 手机号登录~~ → **2026-09-18 取消**（§0.1）；邮箱验证与密码找回 → **归 M1.5 的验证码覆盖**（§2.5）。
- ⚠️ **为什么强制鉴权默认关**：只有账号、没有数据隔离时贸然强制鉴权＝**所有登录用户互相看到全部数据**
  （现有 `sessions`/`messages`/题库/笔记全是全局表，见 §6）。开关默认关，等 M2 把隔离做完，
  两者**同一批开**。

**M1.5 的范围**（细则见 §2.5 / §4.5 / §4.6）：**做** `auth_codes` 表 + 两个验证码端点 + Resend 发信通道 + 五道限流；
**不做**：密码以外的二次验证（2FA）、短信/语音备通道、跨设备会话管理。

### §0.3 2026-09-18 拍板：发信域名与主站域名**分离**（主站 `.xyz` 不动，发信另购 `.com`）

**原提示词溯源**（§0.4）：

- 老板：「**但是我的就是xyz**」→（我给出三条路：另买 `.com` 专发信／先跑三档实测／主站也换 `.com`）→ 老板：「**com有点贵,fun行吗**」→（我实测：`.fun` 与 `.xyz` **同分同档**，且续费 $29.99~$44.88，比 `.com` 贵 3~4 倍）→ 老板选定：**「Cloudflare 买 .com 专发信」**。

三条结论：

1. **主站域名保持 `.xyz` 不动**。TLD 不影响搜索排名，浏览器也不拦 `.xyz` ⇒ 对**站点本身**无功能影响；主站的 A 记录 / Caddy 自动 TLS / 邀请链接全部照旧。
2. ★★ **发信域名另购一个 `.com`，与主站完全分离**。理由（一手核实，2026-09-18）：**发信子域逃不掉 TLD 声誉** —— Allegrow 原文 "using a subdomain doesn't remove every reputational dependency. The parent domain and its TLD still contribute to the overall trust profile that mailbox providers evaluate… **one built on an abused root will not escape it by moving one level down**"（同文 TL;DR：*"A dedicated sending subdomain isolates risk but still inherits the parent domain and TLD reputation"*；SenderReputation.org 同口径：子域只给**部分**隔离，独立域名才给**完全**隔离）。
   ⇒ **§4.6 缓解第 1 条的「独立发信子域」只能隔离「主域信誉被牵连」，对「TLD 基线分低」无效**；`.xyz` 属 caution 档（48/100，原文 "appears on spam-filter blocklists more than most TLDs — **risky for outbound email**"）⇒ 只能换**域名**，不能换子域。
3. **注册商选定 Cloudflare Registrar**（按注册局成本价、**零加价**、**注册=续费=转入同价**）：`.com` = **$10.44/年**（= 批发 $10.26 + ICANN $0.18；多源一致）。⚠️ 代价与连带项：① 域名**必须用 Cloudflare 的 nameserver**（DNS 记录配在 Cloudflare）；② Resend 给的 **CNAME 记录绝不能开橙色云朵代理**（官方原话：会阻止验证完成）；③ 免费档额度 **3000 封/月 + 100 封/天 + 3 个域名** ⇒「主站 `.xyz` + 发信 `.com`」两个域名，额度绰绰有余。

⚠️ **为什么不选 `.fun`（记账，防将来重复讨论）**：一手排名里 `.fun` 与 `.xyz` **同为 48 分 / caution 档**，换它**不改善可达性**；且 `.fun` 首年 $0.93~$2.00、**续费 $29.99~$44.88**（tld-list 实抓 2026-09-18），是典型「首年白菜价 + 续费翻 30 倍」结构 —— **而这正是它被整段降权的机制本身**。⇒ 若将来仍要换后缀，目标档位是 **≥74 分（standard）**（`.me`／`.cc`／`.in`／`.tech`／`.page`／`.email`／`.studio`／`.design`），且**必须看续费价而非首年价**。

⚠️ **本条的未验项（不在阻塞路径上，但必须记账）**：`.xyz` 的**实际拦截率**没有公开数据 ⇒ 「换 `.com` 发信」是**基于档位判断的风险规避，不是基于实测**；真正的判据仍是 §4.6 缓解第 3 条的**三档实测（QQ / 163 / Gmail）**，且**发信域买完、DNS 配完才能跑**。

## §1 数据模型（迁移 v21）

### users

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT PK | `u-<uuid>`（与 PK 的 `pk_users.id` 同前缀，便于 M4 合并身份时对账） |
| `email` | TEXT NOT NULL **UNIQUE** | **写入前归一化**（trim + 小写，见 `normalizeEmail`）；UNIQUE 是库层兜底 |
| `password_hash` | TEXT NOT NULL | scrypt 派生串（见 §4.1）。**永不出接口** |
| `nickname` | TEXT NOT NULL DEFAULT '' | 不传则从邮箱派生（`nicknameFromEmail`） |
| `github_id` | TEXT（迁移 v36 加列，可空） | GitHub 数字用户 id 的字符串形态（§2.8）。可空 + 部分唯一索引：邮箱注册的账号恒为 NULL；**GitHub 建号**时写入（2026-09-21 起**不再有归并路径** —— 查号键就是它本身，故不存在「邮箱已绑另一个 GitHub 账号」的撞号场景）；**幂等回填**（同一 `github_id` 再次登录命中同一行，已有值相同即不再 UPDATE） |
| `created_at` / `updated_at` | TEXT | `datetime('now')` |

### auth_sessions

| 列 | 类型 | 说明 |
|---|---|---|
| `token_hash` | TEXT PK | **SHA-256(token) 的十六进制**——★ 库里**不存明文 token**（同「密钥加密落库」取向：拖库拿不到可用的会话） |
| `user_id` | TEXT NOT NULL | 归属用户（**不设外键**：账号删除后会话行可被独立清理，且避免删号时的级联复杂度） |
| `created_at` | TEXT | `datetime('now')` |
| `expires_at` | INTEGER | ms 时间戳；`verify` 时比对，过期即失效 |
| `last_seen_at` | INTEGER | ms 时间戳；每次校验通过时刷新（**仅供观察，不参与过期判定**） |

索引：`idx_auth_sessions_user(user_id)`、`idx_auth_sessions_expires(expires_at)`（清理过期行用）。

### auth_codes（M1.5 验证码，迁移 v27）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | ★ **不是 `email` 主键**，理由见下 |
| `email` | TEXT NOT NULL | **写入前归一化**（同 `users.email` 的 `normalizeEmail`）；**不设外键**——验证码可先于注册存在 |
| `code_hash` | TEXT NOT NULL | **SHA-256(code) 的十六进制**——★ 库里不存明文验证码（同 `auth_sessions.token_hash` 取向：拖库拿不到可用的码） |
| `purpose` | TEXT NOT NULL | `login` / `register` / `reset`——**按用途隔离**：登录的码不能拿去改密码 |
| `expires_at` | INTEGER NOT NULL | ms 时间戳；`AUTH_CODE_TTL_MS`（默认 5 分钟） |
| `attempts` | INTEGER NOT NULL DEFAULT 0 | 校验失败次数；达 `AUTH_CODE_MAX_ATTEMPTS`（默认 5）即作废，**不靠过期兜底** |
| `consumed_at` | INTEGER | 非空 = 已用过；**一次性**，校验成功即写入 |
| `created_at` | TEXT | `datetime('now')` |

索引：`idx_auth_codes_email_purpose(email, purpose)`（取最新一条 + 作废旧码用）。

★ **主键是自增 `id` 而非 `email`**：同一邮箱会**多次**请求验证码，若以 email 为主键就只能覆盖（旧码无法保留以做重放审计）；且并发请求下 `INSERT OR REPLACE` 会**静默吞掉**正在校验的那一条。
★ **只存 `code_hash` 不存明文**：验证码只有 6 位数字（10^6 空间），**哈希本身不足以防爆破**——必须叠加 §4.5 的尝试次数与限流；哈希只是「拖库后不能直接拿来登录」的第二道。

## §2 API 契约

前缀 `/api/auth`。**会话走 httpOnly cookie**（名 `AUTH_COOKIE_NAME = 'sb_sid'`），
前端 fetch 同源自动携带、无需手动存 token。

### Web / 前端调用方式（用 `@sb/shared` 的密码规则校验，两端共用同一份——这是契约的一部分）。

| 端点 | 入参 | 成功 | 失败 |
|---|---|---|---|
| `POST /api/auth/register` | `{ email, password, nickname? }` | `200 { user }` + `Set-Cookie` | 400 `EMAIL_INVALID`\|`PASSWORD_WEAK`\|`NICKNAME_INVALID`；409 `EMAIL_TAKEN` |
| `POST /api/auth/login` | `{ email, password }` | `200 { user }` + `Set-Cookie` | 400 `EMAIL_INVALID`；401 `CREDENTIALS_INVALID`；429 `TOO_MANY_ATTEMPTS` |
| `POST /api/auth/logout` | — | `200 { ok: true }` + 清 cookie | — |
| `GET /api/auth/me` | —（读 cookie） | `200 { user }` | 401 `UNAUTHENTICATED` |

### 错误响应形状

`{ error: <人话>, code: <AuthError> }`（ADR-5：失败必须可读、可重试，不裸抛码）。

### 错误码 → HTTP 状态（映射只此一处，域层不碰 HTTP）

`EMAIL_INVALID`→400 / `EMAIL_TAKEN`→409 / `PASSWORD_WEAK`→400 / `NICKNAME_INVALID`→400 /
`CREDENTIALS_INVALID`→401 / `TOO_MANY_ATTEMPTS`→429 / `UNAUTHENTICATED`→401。

★ **`CREDENTIALS_INVALID` 把「邮箱不存在」与「密码错」合成一个码**：分开等于向攻击者确认
「这个邮箱已注册」（用户枚举漏洞）。

### §2.5 邮箱验证码端点（M1.5）

| 端点 | 入参 | 成功 | 失败 |
|---|---|---|---|
| `POST /api/auth/send-code` | `{ email, purpose }` | `200 { ok: true, expiresInMs }` | 400 `EMAIL_INVALID`\|`PURPOSE_INVALID`；409 `EMAIL_TAKEN`；429 `CODE_RATE_LIMITED`；**502 `MAIL_SEND_FAILED`** |
| `POST /api/auth/login-by-code` | `{ email, code }` | `200 { user }` + `Set-Cookie` | 400 `CODE_INVALID`\|`CODE_EXPIRED`；401 `CREDENTIALS_INVALID` |

错误码补充：`CODE_RATE_LIMITED`→429 / `CODE_INVALID`→400 / `CODE_EXPIRED`→400 / `PURPOSE_INVALID`→400 / **`MAIL_SEND_FAILED`→502**。

★ **`MAIL_SEND_FAILED` 是 M1.5 落地时补的（2026-09-18）**：初稿只列了 400/409/429，但发信是本批**唯一的新外部依赖**、也是**最可能失败的一环**（海外 ESP + 国内收件方）。若发信失败也回 200，用户会**拿着一个永远不会到的验证码干等**，而服务端零错误日志——这与 ADR-5「失败必须可读、可重试」直接冲突。502 的文案必须**同时给出兜底路径**（"或改用密码登录"，§4.6 缓解第 5 条）。

### §2.5.1 用途接线闸门（M1.5 落地时补，2026-09-18）

`send-code` 的 `purpose` 字段**接受**三个值，但**只有存在消费端点的用途才被放行**；本批只有 `login` 接线（`login-by-code`），`register` / `reset` 一律回 `400 PURPOSE_INVALID`。

★ 这不是"没做完"，是**刻意不开的口子**，两层理由：

1. `register` / `reset` 的消费端点（注册验证 / 找回密码）尚未落地 ⇒ 发出去的码**没有任何地方能校验**，用户收得到信却用不上，而每封都从 Resend 的 3000 封/月里扣（§4.6 成本账）。
2. ★★ **更硬的一层**：`register` 态要给**未注册的邮箱**发信（这正是注册流程需要的），但它同时意味着**任何人都能拿我们的发信通道给任意陌生邮箱发邮件**——垃圾邮件与钓鱼的现成跳板，也是让发信域名被拉黑最快的方式。`login` 态只给**已注册**邮箱发信，滥用面小得多。

⇒ 在注册端点 + 邮箱验证的完整链路落地之前，**不开这个口子**。落地时把 `auth/code-flow.ts` 的 `WIRED_PURPOSES` 加一项即可，**表结构、`purpose` 列、限流、发信全都不用改**。

★★ **`send-code` 的响应与「邮箱是否已注册」必须按 purpose 分别处理，且两个方向都是刻意的**：

| purpose | 邮箱已注册 | 邮箱未注册 | 为什么 |
|---|---|---|---|
| `login` | `200 { ok: true }` + 发信 | `200 { ok: true }` + **不发信** | **必须同响应**：分开就等于提供「这个邮箱注册了吗」的查询接口（用户枚举，同 `CREDENTIALS_INVALID` 的取向） |
| `register` | `409 EMAIL_TAKEN` + 不发信 | `200 { ok: true }` + 发信 | **刻意泄露**：用户填错邮箱要当场知道；且「注册时已存在」不构成隐私（对方本就能通过登录失败感知） |

★ 两个 purpose 的泄露策略**相反且都是刻意的**，不是不一致——判据是「这个信息会不会让攻击者拿到他本来拿不到的东西」。
★ **验证码正确但账号不存在时**（`purpose: 'login'`）：回 `401 CREDENTIALS_INVALID`，**不自动建号**——自动建号会让任何人用任意邮箱创建账号（`send-code` 在 login 态不限注册与否），且用户打错一位就多出一个空账号。
★ **登录成功即下发会话**（复用 §2 的 `Set-Cookie` 与 §1 的 `auth_sessions`）：验证码登录**不新建会话机制**，只是换了「证明你是这个邮箱的主人」的方式——两套登录方式**产出同一种会话**，后续所有归属逻辑（TENANCY-SPEC）无需分支。

### §2.6 前端登录态与跳回约定（2026-09-18 补，`PK-SPEC §14.3` 依赖本节）

- ★ **登录态不自持**：前端**不把「我已登录」存 localStorage**（`components/AccountBox.tsx` 已按此实现）——启动与每次操作后问 `GET /api/auth/me`。存了就会出现「界面显示已登录、服务端会话早过期」的假象，而这类假象正是权限类 bug 最难排查的一种。
- ★ **`returnTo`（登录后跳回）**：未登录访问受保护路由时记住目标、登录成功后跳回。存储用**内存或 `sessionStorage`**，**不用 `localStorage`**——跨会话残留会让下次登录莫名跳到旧链接。这是邀请链接（`PK-SPEC §14.2`）能走通的前提：否则用户点链接 → 登录 → 落到首页 → **得再点一次链接**，邀请链路断一半。
- ⚠️ **安全约束（P1，开放重定向）**：`returnTo` **只接受站内相对路径**，**必须拒绝绝对 URL**（`https://evil.com`）——否则钓鱼链接可借本站登录页跳去外站。判定口径：**只允许 `#/` 开头**，其余一律丢弃并回落默认页。**这是安全约束不是可选优化。**

### §2.7 注册即验证（M1.6，2026-09-18 拍板「要邮箱验证」）

**原提示词溯源**（§0.4）：老板原话「**要邮箱验证**」。

★ **落地形态是「注册即验证」而不是「注册后补验」**——判据不是偏好，而是**「补验」解决不了它要解决的问题**：

| 形态 | 能否堵住「用别人邮箱占号」 | 代价 |
|---|---|---|
| **注册即验证**（本节选定） | ✅ 建号前必须证明邮箱所有权 | 发信通道挂了就**没人能注册**（§4.6 的连带，见下方记账） |
| 注册后补验 | ❌ **堵不住**——未验证账号**照样占住那个邮箱**（`email` 唯一约束不看验证态） | 还要额外定义「未验证账号能做什么」，而这条规则一旦写松就等于没验证 |

⇒ 采用**注册即验证**：`POST /api/auth/register` 的入参**新增必填 `code`**。

⚠️ **这是破坏性变更**（同批必须改 `components/AccountBox.tsx` 与 `routes/auth.test.ts`）：旧的「只给 email+password 就建号」路径**必须消失**——留着它就是一条**绕过验证的后门**，而不是兼容性。前端漏改的表现是 `400 CODE_INVALID`（清晰可查），**不是静默降级**。★ **已落码**（2026-09-18，提交 `d512e81`）；回归锁＝`routes/auth.test.ts` 的「不传 `code` → 400 `CODE_INVALID` 且 `users` 一行不落」。

**端点契约**（`POST /api/auth/register`，端点名不变、入参变）：

| 项 | 值 |
|---|---|
| 入参 | `{ email, code, password, nickname? }`（`code` **必填**，6 位） |
| 成功 | `200 { user }` + `Set-Cookie`（与 §2 完全一致，**登录态同一套**） |
| 失败 | 400 `EMAIL_INVALID`／`PASSWORD_WEAK`／`NICKNAME_INVALID`／`CODE_INVALID`／`CODE_EXPIRED`；409 `EMAIL_TAKEN`；429 `CODE_RATE_LIMITED` |

★ **上表的码名以 `AuthError` 联合类型为准**（`shared/src/auth.ts`）：初稿这里写的 `PASSWORD_TOO_SHORT` 与 `RATE_LIMITED` **在实现里不存在**（真实码是 `PASSWORD_WEAK` 与 `CODE_RATE_LIMITED`）——契约写了一个不存在的码，前端照着写分支就会**永远进不去**。已按实现订正。

**发码侧**：`POST /api/auth/send-code` 的 `purpose: 'register'` **本批接线**（`auth/code-flow.ts` 的 `WIRED_PURPOSES` 加一项，§2.5.1 已预留）。已注册 → `409 EMAIL_TAKEN` 不发信；未注册 → 发信（泄露策略见 §2.5.1 的表，**刻意与 `login` 相反**）。

**执行顺序（防竞态，与 `login-by-code` 同口径）**：**纯校验 → `consumeCode`（原子认领）→ 建号**。
- ★★ **纯校验必须放最前**（2026-09-18 落码时明确，初稿漏了这一步）：邮箱格式 / 密码长度 / 昵称都是**纯函数、零 IO、免费**，而核销码**不可逆**。顺序反了的话「密码只打了 6 位」这种手滑会**白烧一条码**，用户得重新收信——**把可避免的失败挡在不可逆操作之前**（回归锁＝`routes/auth.test.ts` 的「弱口令被拒后同一个码还能注册」）。
- ★ **先消费再查重**：两个并发请求拿同一个码时，原子认领（`UPDATE … WHERE consumed_at IS NULL`，§4.5）保证**只有一个**能往下走，另一个拿 `CODE_INVALID`。
- ★ **最终兜底是库层的 `users.email UNIQUE`**（v21 DDL；写入前已 trim + 小写归一）：万一竞态穿过了应用层检查，`INSERT` 会抛约束错误 ⇒ **必须捕获并转成 409**，**不能让它变成 500**。
- ⚠️ **已知代价**：`EMAIL_TAKEN` 只可能在**竞态**下从这里抛出（正常流程里 `send-code` 的 `register` 态已先回 409），而**此时码已被烧掉**——宁可让极端竞态下的用户重收一次码，也不给「拿别人邮箱试注册」留口子。

**不新增 `users.email_verified` 列（2026-09-18 判定）**：
- 注册**必须**过验证码 ⇒ 每个 user **天生已验证** ⇒ 该列恒为 `1`，**没有区分度**。
- 按 §0.14 入口闸门问「三个月后它会被删的原因」，答案是「**因为它从来没有第二种取值**」——那就现在不加。
- ⚠️ §6 第 2 条曾写「需一并补 `users.email_verified` 迁移」，**该条作废**。它真正需要的时间点是**「改邮箱」功能落地时**（那时才出现「未验证的新邮箱」这一状态），届时再加不迟。

⚠️ **`register` 发信的滥用面（本节唯一的新风险，诚实记账）**：`register` 态给**未注册**地址发信 ⇒ 任何人可借我们的发信通道给陌生邮箱发邮件（§2.5.1 第 2 条已预警）。本批的处置与残余：
1. **收紧 `register` 的 IP 桶**：现有 IP 桶是 20 封/小时（§4.5），对 `register` 过宽（正常人一小时内不会注册 5 次）⇒ `register` **单独用 5 封/小时/IP**。★ 这是**参数调整不是结构改动**（`code-limit.ts` 的桶按 purpose 取阈值即可），且**改一个要重算 §4.6 的额度账**。
2. ★ **真正的硬顶是 Resend 的免费额度本身**（**100 封/天**，§4.6）——攻击者**打不穿它**去发无限垃圾邮件，他能做到的最坏是**烧光当天额度**，让真实用户收不到验证码。⇒ 残余风险的**性质是「配额 DoS」而不是「批量垃圾邮件」**。这个定性很重要：它决定了要不要上人机验证（见第 3 条）。
3. ⚠️ **未做、留作后备（记账）**：人机验证（Cloudflare Turnstile，免费，且站点本就规划走 Cloudflare DNS，见 §0.3）——**本批不做**（§0.7 简洁优先：先上线观察**实际**滥用，不做没有证据的防御）。**触发条件**：日志里同一 IP 的 `register` 发信被 429 拒绝**持续出现**，或额度被异常烧光。**判定权在老板。**

⚠️ **连带代价（诚实记账，不掩盖）**：注册即验证把「能不能建号」绑死在发信可达性上——**§4.6 的送达率风险从「登录受影响」升级为「注册受影响」**。这是本次决策的**真实代价**，不是附带说明。缓解有三层：① 已有账号**完全不受影响**（密码登录不依赖邮件，§4.6 缓解第 5 条）；② 发信失败回 **502 `MAIL_SEND_FAILED`**（§2.5 已定义，文案必须给出「稍后重试」的明确指引）；③ 运维侧可人工建号兜底（老板自己/内测用户）。

### §2.8 GitHub OAuth 登录（M1.8，2026-09-20 落码；★★ **口径 1 于 2026-09-21 重写**）

> 定位：**第三条登录通道**（密码 / 验证码之外）。产出与前两条**完全相同**的会话（同一个 `createSession` + `sb_sid` cookie，30 天）——只是「证明你是谁」的方式变了，后续所有归属逻辑（TENANCY-SPEC）**零分支**。
> ★★ **但它产出的是一个独立账号**：GitHub 身份不与邮箱账号归并。「会话机制相同」与「账号彼此独立」是两件事，**不要因为前者相同就想当然后者也相同**（这正是本口径被推翻的设计起点）。

**三个口径（口径 1 于 2026-09-21 老板拍板重写；口径 2 / 3 沿用 2026-09-20）**：

1. ★★ **严格独立建号（2026-09-21 老板拍板，推翻 2026-09-20 的「按邮箱自动归并」）**：GitHub 登录**只按 `github_id` 认人**，**绝不按邮箱归并**。拆成三条：
   - **查号键是 `github_id`**：同一 GitHub 账号**再次登录**必须找回**同一个** `users` 行。★ 这是本口径最容易做错、也最致命的一点——退化成「每次登录都新建」，用户的历史数据会在第二次登录时全部消失。
   - **同邮箱不归并**：GitHub 的已验证邮箱即便**命中**现有 `users.email`，**照旧新建独立账号**，既不登入那个账号、也不回填它的 `github_id`。⇒ 同一人在本站**可以有两个互不相通的账号**（邮箱一个、GitHub 一个），**数据不互通且这是刻意的**。
   - **邮箱不再是身份依据**（连带三处，都必须同步改，漏一处就前后矛盾）：① 建号**不强制**要求 GitHub 有已验证邮箱（见下方「四条硬约束」第 1 条已改）；② ~~授权 scope 缩到最小~~ ⚠️ **此条在实施复核时被撤回**：scope **仍保留 `user:email`**（理由见下方「scope 为什么不缩」—— 缩了就拿不到邮箱，而账号菜单要显示它）；③ `GITHUB_EMAIL_UNAVAILABLE` 由「必现的拒绝路径」**退化为罕见兜底**（仅在连 `login` 都拿不到时才可能触发）。
   ⚠️ **代价如实记账**：同一人两个账号、数据永久分裂——用户若先用邮箱注册、后又点 GitHub 登录，会以为「我的数据丢了」。这是**老板明确选择接受**的代价，换取的是「本站账号的进入权不外包给 GitHub」（理由见 §0.1 第 1 条）。⚠️ **将来若要「账号合并 / 绑定」，那是新增的显式功能**（需另立口径与端点、要用户主动确认），**不是把本口径改回归并**——两者不是一回事，别在下次讨论时混淆。

2. **新用户直接建号**：封闭打磨期不做额外审批（与现有注册口径一致——注册本身没做白名单拦截，封闭靠不公开传播控制）。
3. **会话时长保持 30 天**（`AUTH_SESSION_TTL_MS` 不动）。

**三端点（全是 GET——OAuth 重定向流必须浏览器整页跳转，没有 fetch 版本）**：

| 端点 | 行为 | 失败 |
|---|---|---|
| `GET /api/auth/providers` | `200 { providers: { github: boolean } }`——**前端画不画 GitHub 按钮的唯一依据**（按钮常在、点了 503 是坏体验） | — |
| `GET /api/auth/github` | 发一次性 state cookie（`sb_gst`，httpOnly，10 分钟）→ 302 到 `github.com/login/oauth/authorize`（scope **仍保留 `user:email`** —— ⚠️ **不是「缩到最小」**，理由见下方「scope 为什么不缩」） | 未配置 → 503 `GITHUB_NOT_CONFIGURED` 错误页 |
| `GET /api/auth/github/callback` | 验 state（**`timingSafeEqual` 逐字节**，先验后清 cookie）→ 换 token → 拉 `/user`（`/user/emails` 仅用于展示与昵称兜底，**不参与认人**）→ **按 `github_id` 查号 / 建号** → 发会话 → 302 回 `/` | 见下表 |

**错误码（`AuthError` 联合类型新增四个；失败呈现走内联 HTML 错误页而非 JSON——此刻用户在浏览器导航里，fetch 错误形状没人能看见；错误页必带「返回首页」链接，ADR-5）**：

`GITHUB_NOT_CONFIGURED`→503（缺 `SB_GITHUB_CLIENT_ID`/`SB_GITHUB_CLIENT_SECRET`）/
`GITHUB_STATE_INVALID`→400（state 不过 = CSRF，**不发会话不落库**）/
`GITHUB_AUTH_FAILED`→502（换 token / 拉身份失败）
　★ **2026-09-21 起「撞号」失败分支已删除**：改为按 `github_id` 认人后，「邮箱已绑定另一个 GitHub 账号」这个场景**不复存在**（同一个 `github_id` 只会命中它自己那一行），原 `GITHUB_AUTH_FAILED` 的撞号用途随之作废。/
`GITHUB_EMAIL_UNAVAILABLE`→502 —— ⚠️ **已退化为例外兜底**：邮箱不再作身份依据，正常路径**不再触发**它；保留仅为防御「连 `id` / `login` 都拿不到」的畸形响应。

**四条硬约束（做不对就是洞）**：
1. ★★ **（2026-09-21 重写）邮箱只用于展示与昵称兜底，不作身份依据**：原口径是「只认已验证邮箱」，它存在的**唯一理由**是保证**归并的正确性**（当时「知道某人的邮箱 ⇒ 能登入某人的账号」这条攻击链，前提是邮箱即账号标识）。**归并取消后这条前提消失**，故改为三条：① **不强制**要求 GitHub 返回已验证邮箱 —— 用户把邮箱设为私密也能正常登录（昵称退化为 `name` → `login` 派生）；② 拿到的邮箱仍优先取 `primary && verified`，但用途只剩**账号菜单里给用户看**（`AuthUser.email`）与昵称兜底；③ ★ **绝不**用它去匹配任何既有 `users` 行 —— 这是新口径与旧口径唯一不可混淆的分界线。

   **★ scope 为什么不缩（实施复核结论，2026-09-21）**：本批开工前曾计划把 scope 从 `user:email` **缩到最小**以降低授权页的「吓人度」，**实施时发现该计划不成立** —— `users.email` 对 GitHub 账号存的是**占位串**，账号菜单里能显示的邮箱只能来自 `github_email`，而 `github_email` 的唯一来源就是 `/user/emails`（**需 `user:email` scope**）。⇒ **缩了 scope 就拿不到任何邮箱**，用户会在账号菜单里看到 `gh-1234@users.noreply.invalid`。**结论：scope 保留 `user:email`**；但「**保留 scope**」与「**拿不到邮箱就拒绝登录**」是两件不同的事，前者保留、后者取消 —— 别把这两条混在一起读。
   **★ 拿不到邮箱时 `github_email` 记什么（同样经实施复核）**：不能留 `NULL` —— 否则 `AuthUser.email` 会回落成占位串、**照样暴露给用户**。⇒ 记 **`{login}@users.noreply.github.com`**。选它的三条理由：① 它是 GitHub **官方**为「不公开邮箱」用户提供的 noreply 地址格式，**真实存在于 GitHub 体系**，不是我们编的；② `login` 在 GitHub 全局唯一 ⇒ 该值唯一；③ 用户看到 `octocat@users.noreply.github.com` 能理解「这是我 GitHub 身份的地址」，比任何占位符都清楚。
2. **state 是 CSRF 防线**：授权前发、callback 里逐字节比对、无论成败先清（留着只会让重试撞上过期脏值）。
3. **授权与回调两步的 `redirect_uri` 必须同源派生**（`SB_PUBLIC_ORIGIN` 优先，反代后 `req.protocol`/`host` 可能失真；未配则从请求推导，本地开发即正确）——GitHub 对两步做比对，不一致直接拒（`redirect_uri_mismatch`）。
4. **GitHub 建号的账号 `password_hash` 写两次 `randomUUID` 拼接的 scrypt 哈希**：列是 NOT NULL 而这类账号没有口令——随机串让密码登录对它永远 `CREDENTIALS_INVALID`（等价「口令不可知」），**不为它把约束改可空再整表重建**（ADR-2）。

**数据模型（迁移 v36 ＋ v40）**：

- **v36**（2026-09-20）：`users` 加 `github_id TEXT` 可空列 ＋ 部分唯一索引 `idx_users_github_id ON users(github_id) WHERE github_id IS NOT NULL`（部分索引把「只有非空才唯一」写成约束，不靠读者知道 SQLite 的 NULL≠NULL）。★ 该索引在**新口径下由「撞号探针」升格为「查号主键」**——按 `github_id` 找回账号就靠它，**不可删**。
- **v40**（2026-09-21，独立建号批）：`users` 加 `github_email TEXT` 可空列，存 GitHub 的**真实已验证邮箱**（**仅作展示**）。
  ★★ **为什么 `users.email` 存占位、不存真实邮箱**：`email` 列是 `TEXT NOT NULL UNIQUE`（建表见 `migrations-list-v18.ts`），而新口径要求「同一真实邮箱可以对应两个账号」⇒ **真实邮箱进不了这一列**。改 UNIQUE 约束在 SQLite 要**整表重建**（12 步流程），风险与收益不成比例 ⇒ GitHub 账号在这一列写**占位串** `gh-<github_id>@users.noreply.invalid`：`.invalid` 是 RFC 2606 **保留 TLD，永不可解析**；`github_id` 唯一 ⇒ 占位串唯一性**天然成立**，无需再加约束。
  ★ **映射口径（一处改，全链受益）**：`AuthUser.email` 取 `github_email ?? email` ⇒ 用户在账号菜单里**看到的仍是真实邮箱**（`AccountTrigger.tsx` 直接把该字段渲染出来），**占位串绝不出现在任何接口返回里**。
  ★ **零数据风险**：v40 落地时线上 **0 个账号**带 `github_id`（凭据刚生效、尚无人登录）⇒ 纯加列、**无回填、无历史数据处理**。
  ⚠️ **两条连带效果（刻意保留，不是缺陷）**：① GitHub 账号**不能用邮箱密码登录 / 找回密码**（用户无从知道占位串，且其 `password_hash` 是随机不可知口令的哈希，见硬约束第 4 条）；② GitHub 账号**不占用真实邮箱位** ⇒ 同邮箱仍可正常走邮箱注册，`EMAIL_TAKEN` **不会误报**。这正是「两个独立账号」在库层的落实方式。

**部署配置（M3 外部依赖，未配置时功能整体静默下线——前端按 providers 探针不画按钮）**：
- GitHub 侧注册 **OAuth App**（Settings → Developer settings → OAuth Apps），Homepage `https://11wand.com`，**Authorization callback URL `https://11wand.com/api/auth/github/callback`**。
- 服务器 env：`SB_GITHUB_CLIENT_ID` / `SB_GITHUB_CLIENT_SECRET`；反代后显式配 `SB_PUBLIC_ORIGIN=https://11wand.com`。本地开发另注册一个 callback 为 `http://localhost:5173/api/auth/github/callback` 的 App（GitHub 不允许 localhost 生产凭据混用）。
- ★★ **线上状态（2026-09-21 实测，非推断）**：三个键**已配齐并生效** —— `GET /api/auth/providers` 回 `{"providers":{"github":true},"form":"cloud"}`；`GET /api/auth/github` 回 **302** 且 `redirect_uri=https://11wand.com/api/auth/github/callback`（**实测**印证 `baseUrl()` 推导，此前只是推演）；`Set-Cookie: sb_gst=…; Max-Age=600; HttpOnly; Secure; SameSite=Lax`；进程 environ 命中 2；`journalctl -p err` 0 条。
  ⚠️ **本次教训（写进契约防复发）**：本文此前**从未标记过线上状态**，而入口又按 ADR-5「不配凭据就不画按钮」**刻意不渲染** ⇒ 「代码已落码 ＋ 线上未配凭据」被长期误读为「这个功能不存在」。⇒ **凡是「外部配置项」的行，今后必须带实测日期与实测值**，不能只写「见 §9」的操作说明。
- ⚠️ **端到端真实登录仍未验**：需**真人**在浏览器持有 GitHub 登录态走一遍（服务端三段已实测）。这是**唯一**能同时验证 client_id ＋ secret ＋ callback URL 三者一致的路径，服务端探针替代不了。

### §2.9 部署形态：local（本地单人）/ cloud（线上多用户）（2026-09-20 拍板）

> 定位：**本地与线上的行为差异从「隐式巧合」升为「显式契约」**。老板原话：「本地的和线上的要有区别，本地的不用登录也可以使用，并且之后本地的会出现线上没有的功能」。

**形态判定（唯一事实源 `server/auth/form.ts`）**：`SB_REQUIRE_AUTH` 开 ⇒ `cloud`；关（缺省）⇒ `local`。
★ 形态是**部署事实**，启动时读定、进程内不变——`index.ts` 的强制鉴权闸门与 `/api/auth/providers` 的 `form` 字段都认这一个值，**禁止任何代码再各自读 env 判形态**（读两次必然漂一次）。

**前端启动分叉（`main.tsx` → `app/entry.ts` 纯函数，配回归锁）**：

| 登录态 | form=local（本地单人） | form=cloud（线上多用户） |
|---|---|---|
| 已登录 | 应用壳 | 应用壳 |
| 未登录 | **免登录直进应用壳** | 落地页（介绍 → 注册/登录） |

★ **本地免登录不是新造的能力**：后端 `auth/ownership.ts` 的归属模型里 `ownerIdOf → null`（不过滤 / 无主行）就是「未登录的单人本地模式」，早已有之且经 M2 系列锁死（`canAccessSession` 对 null 放行、`ownerForWrite(null) → ''`）；本批补的只是**前端不再未登录就怼落地页**。★ 兜底口径：`me()` 401 后问 surface，surface 也问不到（服务没起/网络断）按 `cloud` 处理——**问不到形态时按更严的一侧兜底，不悄悄放开**。

**已知边界（诚实记账）**：本地形态下登录 → 退出 → 再操作，期间产生的数据归属会随登录态切换（无主行 vs 本人行）——单人形态可接受；真要把本地历史「认领」给某个账号，走既有 `_probe/claim-legacy.mjs` 通道。

**后续「本地有、线上没有」的功能以 `deployForm()` 返回值为唯一分叉点**；响应端点复用 `GET /api/auth/providers`（职责 = 「前端启动要问的全部 auth 面信息」，形状 `{ providers, form }`），不为此加第二个端点。

## §3 鉴权中间件与开关

- `requireAuth`：读 cookie（或 `Authorization: Bearer`，便于脚本/冒烟）→ 校验会话 → 把 `AuthUser`
  挂到请求对象。无有效会话 → `401 UNAUTHENTICATED`。
- `SB_REQUIRE_AUTH`：`'1'` 时对 `/api` 全量强制鉴权，**豁免** `/api/auth/*`、`/api/status`、`/api/health`。
  默认**不设**（＝不强制）。
- ★ **豁免清单是"必须公开"的白名单**：登录端点自身不能要求登录；`status`/`health` 是探活，也不该要登录。

## §4 安全约束（做不对就等于没做）

### §4.1 密码：scrypt（Node 内置，零新依赖）

- 格式 `scrypt$N$r$p$<saltB64>$<hashB64>`；`N=16384, r=8, p=1, keylen=64`，盐 16 字节随机。
- 校验用 `timingSafeEqual`（定长比较，防时序侧信道）。
- ❌ **绝不存明文、绝不回显** hash（`AuthUser` 契约层就没有这个字段）。
- 为什么不用 bcrypt/argon2：本仓偏好零依赖（ADR-2 简洁优先）；`node:crypto` 的 scrypt 是标准 KDF，
  够用且省一个原生依赖（`better-sqlite3` 已是唯一的原生模块，不再加第二个）。

### §4.2 会话 token

- 32 随机字节（`randomBytes(32).toString('base64url')`）；库里只存 `sha256` 十六进制。
- 属性：`HttpOnly`（JS 读不到，防 XSS 窃取）、`SameSite=Lax`、`Path=/`、`Max-Age=AUTH_SESSION_TTL_MS`；
  `Secure` 由 `SB_COOKIE_SECURE='1'` 打开（**生产 HTTPS 必须开**；本地 http 开发不能开，否则 cookie 不落）。

### §4.3 CSRF：复用既有 originCheck（不新造）

服务端 `security.ts` 的 `originCheck` 已对**非幂等方法强制合法 Origin**（继承 v1 SEC-09）。
cookie 会话 + 该闸门＝**跨站写请求被拦**，故无需再引 CSRF token。★ 这是「同源 Web + 写操作验 Origin」
这套组合的红利，别重复造轮子；但也意味着**这个闸门不能被削弱**。

### §4.4 登录限流（防撞库）

同一邮箱在 `AUTH_LOGIN_WINDOW_MS`（15 分钟）内失败达 `AUTH_MAX_LOGIN_FAILURES`（5 次）即锁定 →
`429 TOO_MANY_ATTEMPTS`。窗口内登录成功即清零。⚠️ 本版是**进程内内存计数**（重启清零）——
足够挡「在线暴力试」，挡不住分布式慢速撞库；后者需外部存储（列 M2 之后）。

### §4.5 验证码的安全约束（6 位数字 = 10^6 空间，单靠哈希远远不够）

- **生成**：`crypto.randomInt(0, 1_000_000)` 补零成 6 位。★ **绝不用 `Math.random()`**——它可预测，攻击者拿到几个码就能推出下一个。
- **一次性 + 短时效**：`AUTH_CODE_TTL_MS = 5min`；校验成功立刻写 `consumed_at`，**重放同一个码必失败**。
- **尝试次数硬上限**：同一条码失败 `AUTH_CODE_MAX_ATTEMPTS = 5` 次即作废。★ 这是**6 位码的唯一防线**：不限制的话，10^6 空间对一个脚本是分钟级的事。
- **发送频率三道限流**：同邮箱 `AUTH_CODE_RESEND_INTERVAL_MS = 60s`（防连点）／同邮箱 `AUTH_CODE_MAX_PER_HOUR = 5`（防定向刷）／同 IP `AUTH_CODE_MAX_PER_IP_HOUR = 20`（防换邮箱刷）。★ 超限回 `429 CODE_RATE_LIMITED`，**且不提示「已发过」**——提示等于确认该邮箱正在被刷。**响应体必须带 `retryAfterMs`（毫秒，见 §2.5）**：只回时间、不回原因，前端据此提示「约 N 分钟后可重发」——校园网误伤（`AUTH_CODE_MAX_PER_IP_REGISTER_HOUR` 那条）就是靠它把「没有解释的失败」变成「再等 4 分钟」。
  - ★★ **「60 秒间隔」只作用于邮箱桶，不作用于 IP 桶**（2026-09-18 落地时明确）：契约初稿只写了"同邮箱"，实现时若把三道闸门做成同一种 `blockedUntil(sends, now, max)`，就会把间隔一并套到 IP 桶上 ⇒ **同一出口 IP 上所有用户合计每分钟只能发 1 封**。共享出口（校园网 / 公司网 / 运营商 NAT）与**反代未配 `trust proxy` 时的全站单 IP** 都会被静默掐死，症状是「点了发送没反应」而**服务端零错误日志**。⇒ 两个桶的判据必须分开写（`emailBlockedUntil` / `ipBlockedUntil`），且**被拒的请求不记账**（否则窗口不断后移，正常用户一小时内永远等不到窗口滑出）。
- **旧码作废**：发新码时把同 `(email, purpose)` 的未消费码全部标记作废。★ 不这么做的话，用户点两次「重新发送」会得到**两个都能用的码**，攻击面翻倍。
  - ★ 用 `consumed_at` **标记**而不是 `DELETE`：留着才能回答"这个邮箱发过几次码、何时被换掉"，而这类审计信息**删了就再也回不来**（同 `term_review_log` 只追加的口径）。
- **校验失败不消耗尝试次数的例外**：**格式不对**（位数不符 / 含非数字）直接回 `CODE_INVALID` 且**不计 attempts**——它不是"猜错了一次"，是"根本没在猜"；计了的话用户手滑多打一位就能把自己的码打废。
- **比对用定长比较**：`timingSafeEqual`（同 §4.1 密码校验）。
- ⚠️ **限流仍是进程内计数**（同 §4.4）：重启归零 ⇒ 防不住「卡着重启窗口期」的爆破。**已知局限，不修**（要修得上外部存储，属 M2 之后的活）。
- ⚠️ **两条已知旁路，刻意不修（2026-09-18 落地时记账，写在 `auth/code-flow.ts` 头注）**：① `login` 态「已注册」要走一次发信网络往返、「未注册」直接返回 ⇒ **响应时间可区分两者**（秒表即可枚举）——该信息本来就能从 `register` 的 409 直接拿到（本节上方已承认这一点），修它要么牺牲"发信失败能如实告知用户"、要么加人为延迟（脆弱）；**若将来 `register` 的泄露策略收紧，这条必须同批修**，两者是同一道防线的两半。② 限流按邮箱计数 ⇒ **知道受害者邮箱的人可以替他刷满每小时配额**（连发 5 封骚扰邮件 + 让他这一小时无法用验证码登录）——这是"按邮箱限流"的内生代价，而**密码登录完全不受影响**（§4.6 缓解第 5 条），这正是双通道并存不可退让的实例。

### §4.6 发信通道（M1.5 唯一的新外部依赖）

★ **这是本契约第一次引入第三方服务**，故把选型依据与风险一并落在这里。

**为什么只能用海外服务商**：服务器在海外（不备案）⇒ 国内发信厂商全部出局：

| 服务商 | 价格 | 免费额度 | 备案要求 | 结论 |
|---|---|---|---|---|
| 阿里云邮件推送 | ¥2.00 / 千封 | 200 封/天 + 终身 2000 封 | **域名必须备案** + 模板人工审核 | ❌ 与海外服务器冲突 |
| 腾讯云邮件推送（国内站） | ¥1.90 / 千封 | 终身 1000 封 | **同上** | ❌ 同上 |
| **Resend**（本契约选定） | Pro $20~35/月（5~10 万封） | **3000 封/月** | **仅需 DNS 验证** | ✅ 选定 |
| AWS SES | $0.10 / 千封 | 沙箱内 200 封/天 | 无 | 备选：最便宜但需工单提额 |
| Plunk（开源） | 自托管接 SES | 1000 封/月 | 无 | 备选：成本最低但要自己运维 |

⇒ **选定 Resend**（2026-09-18 老板拍板）：免费额度对起步阶段足够、DNS 验证即可接入（无需备案与模板审核）、支持 React Email 写模板。⚠️ 上表价格与额度来自第三方调研（2026-02 发布），**开通前须以 Resend 官方定价页复核**。

⚠️ **送达率是本批最大的未验风险**（诚实记账）：国内厂商的看家本领恰恰是「对 QQ / 163 等国内 ISP 做了白名单优化」，而**目标用户是国内学生、QQ 邮箱占绝大多数**——用海外发信通道发国内邮箱，**有进垃圾箱甚至被直接拦截的风险**。同类调研的共识是：家宽或廉价 VPS 直发**基本被直接拦截**，故必须走专业 ESP 而非自建 SMTP。

**缓解手段（上线前必须全做完）**：

1. **独立发信子域**（如 `mail.<发信域>`），不用主域、更不用 ESP 默认域——一旦子域信誉受损，主域不受牵连，且**可以整个换掉**。
   ★★ **但子域逃不掉 TLD 声誉（2026-09-18 一手核实，本条的口径已被修正）**：Allegrow 原文 "using a subdomain doesn't remove every reputational dependency. The parent domain and its TLD still contribute to the overall trust profile that mailbox providers evaluate… **one built on an abused root will not escape it by moving one level down**"。⇒ 本条只解决「**主域**信誉被牵连」，**解决不了「TLD 基线分低」**；后者只能**换域名**。本项目因此把**主站与发信拆成两个域名**（主站 `.xyz` / 发信 `.com`，见 §0.3）。
2. **SPF / DKIM / DMARC 三条 DNS 记录全配**（Resend 会给记录值；缺 DMARC 时 Gmail 侧会直接降级）。★ **顺序必须按 Resend 官方来（2026-09-18 复核，本条初稿的顺序是错的）**：先加 **DKIM + SPF**（`TXT` + `MX` 或 `CNAME`，值必须**逐字符一致**，复制粘贴）完成**域名验证**；**DMARC 是验证通过之后再单独加**一条 `_dmarc.<发信域>` 的 TXT，且**先 `p=none`**（只监控），调通后再收紧到 `quarantine` / `reject` —— 一上来就上严格策略会把**尚未调通的信全打回**。⚠️ **CNAME 记录绝不能开 Cloudflare 代理（橙色云朵）**，官方原话：会阻止验证完成（这是用 Cloudflare 做 DNS 时最常见的翻车点）。验证通常 **15 分钟**内完成、最坏 72 小时（可用 `dns.email` 自查）。
3. **上线前实测三档送达**：QQ 邮箱 / 163 邮箱 / Gmail 各发一封，确认落**收件箱**而非垃圾箱，并记录实测日期。★ 这条属 §0.15 类的客观验证，**不自行判定通过**，判定权在老板。
4. **文案避开垃圾邮件特征**：主题不夹营销词、正文不放大段链接、纯文本优于富文本。
5. **兜底路径已在设计里**：密码登录不依赖邮件（§0.1 第 2 条）——邮件挂了用户仍能进。这正是「双通道并存」不可退让的理由。

★ **发送区域选东京（`ap-northeast-1`，2026-09-18 复核）**：Resend 四个区为 `us-east-1`（北弗吉尼亚）／`eu-west-1`（爱尔兰）／`sa-east-1`（圣保罗）／`ap-northeast-1`（**东京**）。目标用户在国内 ⇒ **选东京**。⚠️ 两点：① 区域只决定**发信路由**，**账号数据（含邮件元数据与日志）仍存美国**（官方原话：区域选择不控制数据存储位置）；② 改区域要**删域名 → 重加 → 改 DNS 记录**，不是改个开关。

★ **成本上限要一起算**：3000 封/月免费额度 ≈ 每天 100 封，而按 §4.5 的限流（同邮箱每小时最多 5 封），**单个账号就能吃掉 5% 的日额度** ⇒ 限流参数与免费额度必须同批复核，改一个就要重算另一个。

⚠️ **通道配置缺失会静默退化（M3 部署必查，2026-09-18 落地时记账）**：`RESEND_API_KEY` 与 `SB_MAIL_FROM` **两个都要配齐**才走真发信，只配一个（或都不配）⇒ 走**控制台兜底**（把邮件正文打进日志、**不真发**），并打一条显眼警告。本地开发够用，但**生产误配的症状是「点了发送、界面说成功、邮箱里永远没有」**——服务端一切正常、日志里连错误都没有，属最难查的一类故障。⇒ M3 部署清单必须**验它俩在位**，而不是"配了就算"。

⚠️ **同 IP 限流与反向代理的耦合（M3 部署必查）**：`send-code` 取的是 `req.ip`（socket 对端，**不读可伪造的 `X-Forwarded-For`**）。**反代后未配 `app.set('trust proxy', …)` 时 `req.ip` 恒为反代自身地址** ⇒ 全站共用一个 IP 桶 ⇒ §4.5 的第三道闸（20 封/小时）**静默退化成"全站每小时 20 封"**，100 个用户抢 20 个名额、其余全部 429。⇒ M3 必须**同时**做两件事：Caddy 下发 `X-Forwarded-For` + Express 打开 trust proxy。（这条与 §7 末尾那条 `Set-Cookie: Secure` 依赖 `X-Forwarded-Proto` 是**同一个配置项**引起的两处故障，一并处置。）

## §5 验收判据（本版已跑 / 待跑如实标注）

| 判据 | 状态 |
|---|---|
