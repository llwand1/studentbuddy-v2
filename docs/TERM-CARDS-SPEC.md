## 0. 一句话与三条边界

★ **定位：本册是 `GAMIFIED-AGENT-SPEC.md` §2「可玩性」那一维的下沉施工册**，不另立叙事。
那本契约管产品口径（一句话定位、轻量化判据、XP／连签、对外措辞闸门），**本册只管词条卡牌这一族**：
卡数怎么派生、宝箱额度怎么记、AI 怎么派单。两份文档的分工线画在边界②——
`GAMIFIED-AGENT-SPEC` 的 streak/XP 与这里的卡牌**是两把不同的尺，谁也不许换算成谁**。

把「一个词条被碰到过多少回」这件已经记在流水里的事，**翻成看得见的卡牌与星级**，再用每日宝箱和 AI 派单
把它接成一条**主动来找你**的回路。

- **边界①：本册不新建账本，只新建读法。** 卡数一律从**一行一事件的流水**派生（§1），不落中间列。
  理由见 §1 的「两处事实源」论证——这是全册最重要的一条决定，其余都是它的推论。
- **边界②：XP / 连签不归本册。** `learning/activity.ts` 那本账一字不改。卡牌与 XP 是**两把不同的尺**
  （一个量"这条词条我碰过几次"，一个量"我今天学没学"），合并必然失真。
- **边界③：公开 SEO 语料不是游戏池的下游。** 抽卡词池可以**读**公开语料，但 AI 生成的新词
  **永不自动写进** `term-corpus*.ts`——那文件头有三条被测试锁死的红线（§6.3）。

## 1. 卡牌：从流水派生，不落任何计数列

**定义**：某词条的卡数 = `提及流水条数` + `该词条的不同复习日数` + `宝箱收下次数` + `1`（建卡那张）。

```
cards(term) = COUNT(term_mention_log WHERE term_id = t.id AND owner 同主)
            + COUNT(DISTINCT term_review_log.reviewed_day WHERE term_id = t.id)
            + COUNT(chest_open WHERE term_id = t.id AND accepted = 1)
            + 1
```

★ `chest_open` 是本批新建的表，但**边界① 依然成立**：它仍是"一行一个真实事件"的流水，
卡数还是它的计数，库里没有任何 `cards`／`bonus_cards` 那种列。
⚠️ 这条是**实现期加进来的**（拟稿时公式只有三项、宝箱只发"新词"不发卡）。加它的理由不是玩法，
是一个货不对板的漏洞：`cards` 是全司唯一的派生读数，宝箱若走"另一套加分"，那些分在卡牌面板上
**永远看不见**（要嘛得伪造流水，要嘛得开一条只有 UI 知道的旁路账）。所以宝箱给卡的方式，
只能是"留下一行真实事件"。⇒ 直接后果：**从宝箱收下的词条天生 ★1**（1 建卡 + 1 宝箱 = 2 张），
这才是"奖励"；不给这一张，抽到的卡与用户自己手动添加的完全等价，玩法名不副实。

★ **为什么不落一张 `cards` 列或 `term_card` 表**（本批最容易被"先建个表好算"带走的地方）：
`term_mention_log` 与 `term_review_log` 已经是**一行一个真实事件**的流水，卡数只是它们的**计数**。
再存一份就等于给同一个事实开两个落点——`learning/mention.ts` 文件头那条
「计数加了、流水没落 ⇒ 差值此后再也无法对齐」在这里反过来同样成立：一旦派生值落了库，
任何一次补录、删除词条、改流水都会造出**没人能校验**的分叉。而词条量级 ≤500（`listTerms` 的 LIMIT），
一次 `GROUP BY` 全算出来比维护计数表**既准又便宜**——这与 `term-review.ts` 文件头
「库里只存两个真值，下次什么时候复习每次现算」是同一条判据。

★ **建卡那张（`+1`）不是奖励，是口径**：用户亲手把一条词条记进库里，本身就是一次真实接触，
而它恰好**不产生流水行**（入库不是"提及"也不是"复习"）。不给这一张，则全库最低的词条永远是 0 卡，
"我记下来的词一张卡都没有"是错的读数。

★ **复习侧只数「不同复习日」**，不数打卡次数。直接 `COUNT(*)` 会被同日重复刷词条灌爆
（`markReviewed` 明确允许同日重复且**每次都写流水**）。而 v1.2 已经为同一件事做过一次决策：
同日第二次及以后的"记住"**只记流水、不动曲线**（`EBBINGHAUS-SPEC §10.5`，理由是"曲线会变成内置作弊器"）。
卡牌复用同一条判据：**一天之内同一条词条的复习只贡献一张卡**。

**读侧口径**：`usage_count` 保持它原有的"**总提及**"语义不动（`mention.ts` §1.5 明令两个口径永久并存、
不可互相校验）。★ 卡牌**不读** `usage_count`——它含流水建表之前的历史，那部分**没有时间信息**，
拿它当卡数就等于把"历史提及"伪装成"逐次事件"，正是 `mention.ts` 拒绝补历史行的那个理由。
⇒ 老用户会看到"提及数 20、卡数 8"，这不是 bug：差值就是**流水建表之前**的那部分，UI 必须能解释
（§7.2 在卡数旁标注流水起点日期）。

## 2. 星级曲线：2/4/8/16，封顶 ★8

| ★ | 累计卡数 | 稀有度档 |
| - | ------- | ------- |
| 0 | 1       | N       |
| 1 | 2       | R       |
| 2 | 4       | SR      |
| 3 | 8       | SSR     |
| 4 | 16      | SSR     |
| … | 2^n     | SSR     |
| 8 | 256     | SSR（封顶） |

- **唯一实现**在 `@sb/shared/term-cards.ts`：`starOf(cards)` / `cardsNeededFor(star)` / `rarityOf(cards)`。
  前端不重算（双份口径 = `doc-rag.ts` 常量双写、`ebbinghaus.ts` 判定双写同款病）。
- **稀有度按卡数分档，不按星级分档**。按星分档在指数曲线下会把 ★0～★1 全塞进同一档，
  而库里绝大多数词条恰好停在那儿（demo 实测：真实提及量 1～3 次时全库 80% 是 ★0）。
  按卡分档让"2 张卡"就有 R 的观感，**这是让指数曲线活得下来的那一环**。
- ★8 = 256 张是**长期天花板**，不是设计目标。老板 2026-09-25 明确保留。

## 3. 宝箱：每日 3 把 + 任务赚钥匙

`chest_keys`（每 owner 一行）：`free_day`（本地日历日）／`free_used`／`earned`。

- **每日无条件 3 次**：读时若 `free_day !== localDayKey(now)`，按"新的一天"处理并把 `free_used` 归零。
  ★ 用 `localDayKey` 不用 SQL `date('now')`（那是 UTC 日，+8 区晚上会提前一天，`term-review.ts` 已为此写过注释）。
- **完成一单任务 = +1 把 earned**，earned **不随日清零**（囤积是玩家自由）。
- ★ 但加一条**每日开盒硬上限** `DAILY_OPEN_CAP = 8`（3 免费 + 最多 5 赚）。
  没有这条，囤 20 把钥匙一天开完会同时破掉两件事：T3 动效的稀缺性（§8）与"每日"这个词的含义。
- **抽到的必须是新词**：词池里排除①库里已有的同名 ②**撞别名**的 ③本人已抽过的（`chest_open` 留流水）。
  ★ ②必须写在服务端：`term_library` 的约束是 `UNIQUE(owner_id, term, domain)`，
  **它不防别名重复**——公开语料里「主动回忆」的 alias 字段原文就写着「也叫提取练习」。
- **抽中 ≠ 进复习池**：面板给"收下 / 收下并纳入复习"两枚钮，对应 v28 的逐条 `review_in_scope`。
  理由与 `TermsPage.tsx` 那条注释同源：不在复习池里的词条显示"催你复习"是假的。

## 4. 任务清单（原「学习督促」显示名，见 §9）

`study_task`：`id / owner_id / title / why / term_id / dedupe_key / status / created_at / done_at / key_reward`。

- **约束：`UNIQUE(owner_id, dedupe_key)`**，且 ★★ **`dedupe_key` 里不得含会变的数字**。
  这条直接抄 `chat/memory-digest.ts` 付过的学费：`user_memory` 的 UNIQUE 是 `(user_id, kind, content)`，
  把会变的数字写进 `content` ⇒ 数值每变一次新增一行、旧行永不消失 ⇒ 两条记录互相打脸。
  ⇒ `dedupe_key` 取 `advance:<termId>:<目标星级>` 这种**意图键**，进度数字只进 `why` 文案。
- **完成判据由服务端算，不信前端回执**：`advance` 类任务完成 = 该词条卡数达到目标星所需；
  `newterm` 类 = 该词条已在库中；`review` 类 = 该词条今天有流水。每次 tick 与每次 `/state` 读时重算，
  满足即置 `done` 并发钥匙（同事务）。

## 5. 派单：挂进既有 6 小时 tick，**不新建调度器**

★ `learning/trend.ts:248 startTrendScheduler({ intervalMs })` 已经是本仓**唯一**的周期调度器，
且起服即先跑一次。`chat/memory-digest.ts` 文件头有一节标题就叫「**为什么不新开调度器**」
（新增一套调度要额外回答"何时跑 / 跑多少 / 从哪段跑"）。⇒ 派单是**在这个 tick 里多订阅一件事**，
不是新建第二个定时器。

三类意图全部**从已有账里派生**，不凭空造任务：
1. **推进**：某词条已过 60% 距下一星（"把「X」推到 ★n，只差 k 张"）；
2. **破停滞**：卡数停在 4～7 这种"摸得到 SSR 却没够着"的区间；
3. **补池**：可抽新词不足时，派"聊聊「Y」"把池子喂回来。

⚠️ **登记一条继承来的约束**（不是本批引入的）：`trend.ts:17` 注明定时器是**进程内的**，
多实例部署会各跑一份，现在靠"本地单实例"成立。派单挂上去之后，**同一条前提同时决定
"任务会不会被派两遍"**。横向扩容前必须先处理它（幂等键能挡住重复写，挡不住重复发钥匙——
发钥匙要挂在 `status` 的 0→1 翻转上，那是单次 UPDATE 的自然闸门）。

## 6. 词池：AI 生成 + 人工校对闸门

`term_pool_candidate`：`term / domain / aliases / definition / status('pending'/'approved'/'rejected') / source / created_at`。

- **6.1 可抽池 = `shared/chest-pool.ts` 的冷启动底座 ∪ `status='approved'` 的候选**。
  ★ **底座不是公开 SEO 语料**（这条在本批实现时改过一次，理由记录在此）：语料在 `packages/web/`，
  server 不 import web 的任何东西——这堵墙是全仓既有的，本批不为此拆它。更实在的理由是
  **两份内容的风险面不同**：语料改一个字要过公开页审查，词池加一条只是多一个可抽项。
  实测过的那个量级仍然是要害（**现查 2026-09-25**：中文公开语料 `term-entries-a.ts` 6 ＋
  `term-entries-b.ts` 6 ＝ **12 条**；公账号种子里已占掉三条同名的，demo 里**三轮就抽干**）
  ⇒ 一个只有一百来条的静态池，**老用户最先饿死**（他自己库里已经把热门词记完了）。
  所以候选表不是锦上添花，是必需品；底座只提供"第一周有东西可抽"，它自己也会枯竭。
- **6.2 生成走 agnes flash 免费档**（见 `AGNES` 实测图：flash 系免费、pro 付费），
  产出**一律落 pending**，设置页逐条点通过才进池。
- **6.3 ★ 人工闸门是硬约束推出来的，不是嫌麻烦**：`packages/web/src/seo/term-corpus.ts` 文件头三条
  由 `term-corpus.test.ts` 锁死的红线——① 不写任何用户数/使用量 ② 不引用真实账号的词条
  ③ 与产品的连接只说"产品里有哪一环"、不承诺效果。AI 直写公开语料必踩②③。
  ⇒ **AI 产出永不自动进仓，公开页与游戏池两套下游**。
- **6.4 slug 纪律**：候选若将来要升成公开页，slug 必须与 `term-entries-a/-b.ts` 逐条比对——
  线上不存在的 `/terms/*.html` 返回 **200 的 SPA 壳而非 404**，写错是静默坏链。

## 8. 动效预算（三档，老板 2026-09-25 追加要求"更花哨"后仍守）

| 档 | 触发频次 | 预算 | 本批落地 |
| -- | ------- | ---- | ------- |
| T1 | 每次发卡（每天上百次） | **不动画** | 只有数字跳一下 + `transform: scale(.97)` 100ms 按压感 |
| T2 | 升星（每周几次） | 花哨 | 粒子爆发 + 屏震 + 星位错帧点亮（★ 实测值见下，**这档一周几次，不受"屏内位移 <300ms"约束**） |
| T3 | 开箱 / 抽到 SSR / 毕业满星 | 仪式 | 独立整屏面板：遮罩 + 光轮旋转 + 掀盖 + 3D 翻卡 + 全息扫光 |

- **T2 的实测账**（2026-09-25 无头 Edge 页内量，横轴＝动画自己的 `currentTime`）：
  16 颗粒子、9px、54/38px 两圈交替，错帧步长 22ms、末颗 330ms、单颗寿命 600ms ⇒ 收口 930ms，
  `BURST_MS = 940`（`CardWall.tsx:26`）。冲击环 56px/560ms `scale(.4→3)`；星位点亮 300ms、
  错帧 40ms、峰值 `scale(1.3)`；屏震 400ms ±6/±4px（实测最大位移 ±5.97/±3.96px）。
  ★ 粒子数在两处：`CardWall.tsx` 的 `SPARKS` 与 `game.css` 的 16 条 `nth-child` 偏移，
  **改一处必须改另一处**，否则多出来的粒子全叠在中心。
  旧版本这里写的是"30～60ms 错帧、总长 <300ms"——那是一条**没被实现过也没被遵守过**的约束
  （代码从首版起就是 520～600ms 收口），现已按实测改；留着它只会让下一个人以为动效做错了。
- **两条由量出来的事故，别再写回去**：① 环与粒子**不能**用 `inset: 0; margin: auto` 居中——
  `cards-view.css` 的 `.cv-card > * { margin: 0 }` 同特异度且加载更晚，会把 `margin: auto` 吃掉，
  实测中心偏 (-61,-59)px；现在走 `left/top: 50%` ＋ keyframes 内 `translate(-50%,-50%)`。
  ② 透明度不能整条交给 `ease-out`：粒子在 380ms 就只剩 2 颗（＝"没看清"的原始症状），
  现在 keyframes 里 55% 之前钉住不降。
- **加戏不等于越界**：T2 只在"页面挂着且服务端推了 SSE"时放（`CardWall.tsx:useUpgraded`），
  平时不轮询 ⇒ 直接往库里塞流水看不到动效，这是设计不是缺陷。

- **工程红线**（照 `web-animation-design` 与仓内既有约束）：只动 `transform` / `opacity`；
  不 `box-shadow` 动画（改用一个 `.ring` 元素做 `scale()` + 透明度）；不从 `scale(0)` 起步（用 `.95`）；
  成对元素同缓动同时长；进/出用 `ease-out`，屏内位移用 `ease-in-out`，hover 用 `ease`。
- **`prefers-reduced-motion` 逐条降级**：去掉位移/缩放/粒子/飞卡，**保留**透明度与颜色变化
  （reduced-motion ≠ 无动效——透明度还承担着"告诉你刚才是哪张卡变了"的信息职责）。
- **禁内联 style**（gates 拦截）：数据驱动值一律走 CSS 变量 + `gates:style-ok` 注释，
  照 `TermsPage.tsx` 那枚 `--imp-w` 的写法。★ 注意 CSS 变量在深树里会引发子树重算，卡墙 ≤500 张时
  **不要**把动画进度塞进父级变量。
- **禁 emoji 作图标**（`terms.css:614`／`:906` 两处明写）：宝箱/钥匙/星/火苗/任务全部手绘 SVG。
- **稀有度整块饱和填色 ⇒ 文字对比度变成新的闸门**（2026-09-25 老板要"颜色更饱满"后的既成事实）：
  每档在 `game.css` 里带四个值——`--gm-cf` 卡底／`--gm-cfd` 描边与厚底边／`--gm-on` 主文字／
  `--gm-on-dim` 次级文字，**四值同批改**，只改底色就会把小字压到 AA 以下。
  ★ 判据是**渲染后 DOM 上的合成色** ≥4.5（11～14px 的小字一律按小字算），不是色号表上的纸面数：
  半透明层必须先叠出真实底色再量。实测账（09-25）：N 5.62／R 5.27／SR 6.00／SSR 7.43。
  R 档为此从 `#007aff` 改成 `#0068d9`＋白字——`#007aff` 上任何文字色都过不了 4.5（最好 4.02），
  老板拍板换底不换字色。★ 不要改 `--gm-blue` 本体（全仓共用），也不要用 `#1cb0f6` 当 R 底
  （它已经是 `--gm-dom-1` 领域色，撞了就没法区分"稀有度"和"领域"）。
- **卡底与页面底的分离度不够时靠边不靠色**：SSR 黄 `#ffc800` vs 页底 `#fafafa` 只有 **1.49**，
  看得出"一块"靠的是 2px 描边 + 7px 厚底边，不是填充色本身。加亮色时同此。
- ★★ **但卡内一切图形的对比对象是卡体、不是页面底**（2026-09-26 B-023 补）：整块饱和之后轨／角标／
  星槽都画在饱和卡面上，"轨 vs 页底"这条老判据已经不成立了。SSR 那条黄轨就是栽在这儿的——
  填充 `var(--gm-yellow)` ＋ 关掉分段遮罩 ⇒ 与卡体同色、进度读不出来。文字侧有 AA 4.5 的锁，
  **图形侧此前什么都没有**，现已按**解析后的色值**锁住（`card-pixel.test.ts`）。新增卡内图形同此。

### 8.1 像素风·数值层（2026-09-26 老板定档：像素只进**数值层与特效层**，文字一律不动）

| 落位 | 现在长什么样 | 为什么是这一档 | 机器判据（都有锁） |
| --- | --- | --- | --- |
| 星位 | 8×8 点阵星（`game-icons.tsx` 的 sprite），一排一格 | 星是"数值"，硬边读得比圆角快 | `PIXEL_GRID` 方阵逐行验宽高；调用点 `size` 必须是 8 的整数倍 |
| 角标「N 张」 | `border-radius: 0` ＋ 3px 阶梯角（`--gm-px-notch`） | 与卡体 18px 圆角分家：卡是糖果、数字是像素 | 计算样式 `border-radius: 0`（探针 I2 ＋ 源码锁） |
| 进度轨 | 8px 高、2px 边框、`repeating-linear-gradient` 分段（8px 一格 2px 留白） | 分段＝"还差几格"这件事直接数得出来，不用读字 | 分段必须靠渐变，**不许退回 JS 拼方块**（一百张卡 × 8 个节点会常驻） |
| 宝箱／吉祥物 | 点阵 lid ＋ `steps()` 眨眼 | 低频（一天三次），可以吃台阶 | `steps()` 只许出现在粒子与 SR 扫描线／这两处（其余规则吃台阶＝"卡顿"这个 bug） |
| 文字（含数字） | **不动**，仍是 `--sb-font` 系统栈 | 老板那条"文字一律不动"；像素字要引字体文件，违反零依赖 | 探针不测；改一行文案就红的是 `card-motion.test.ts` 那组配色锁 |

- **像素单元只有一个真值**：`--gm-px: 2px`、`--gm-px-row: 8px`（＝四格）、`--gm-steps: steps(6,end)`。
  硬边元素的尺寸一律取它的整数倍——各处各写一个 2px 会慢慢漂成对不齐。
  ⚠️ 它只管**图形**，不管文字（同上表最后一行）。
- **台阶缓动是按区间生效的**：被 `steps()` 驱动的 `@keyframes` 里插一帧"只写 opacity"，
  位移会被切成两段**不等长**的台阶（实测"一格一格"变成"几下抽搐"）。所以要么每帧都带
  `transform`（`gmSpark`），要么整条只有 `transform`（`gmScan`）——这条有锁。

### 8.2 合成层上限（2026-09-26 实测，B-022）

- **视口闸不是上限**。`useInViewIds` 只回答"在不在视口"，不回答"此刻几条"。无头 Edge
  1360×900@2x 实测：一屏铺得下 **17 张 SR/SSR**，`document.getAnimations()` 数到 **17 条**
  常驻无限循环同时在跑 ⇒ 卡墙是按张数排序的密集网格，"看得见的那几张"本来就是几十张。
- **上限是显式的**：`MAX_HOLO_LAYERS = 6`（`use-in-view.ts`，按墙上行序取前 6 张）。
  同屏实测降到 **7 条**（全息 6 ＋ 吉祥物眨眼 1）。★ 代价如实写着：滚到墙下半部分时，若上半
  那几张恰好还在 `rootMargin` 120px 的提前带里，新进来那张要等它们出视口才亮。
- **周期 ≥ 3s 是这道闸要求的**：120px 只是提前起跑量，周期短的话在屏外就播完一轮，
  进屏看到的是半截带子（比没有更难看）。改 `rootMargin` 要同时改这条理由（锁在 `card-pixel.test.ts`）。
- ★ **通则（比这条本身重要）**：凡写"性能靠 X 天然封顶"的注释，要么带一次实测数字，
  要么改成显式常量。注释替代码许的保证，没人会去查，直到有人查一次。

### 8.3 T3 彩带与全息层的实测账（2026-09-26 探针 `tools/probes/cards-pixel-cdp.mjs`）

- **彩带**：`CONFETTI = 16`（`ChestPanel.tsx`）＝ `.gm-confetti > i:nth-child(1..16)` 偏移表，
  两处同改否则有几片叠在原地。实测 6 帧全部 **16/16 片可见**、`border-radius: 0`、片 6px＝三格

  ★ **一片都没跑出 `.gm-ritual` 框**（框 420×455、`overflow: hidden`）：横向落点最大 ±168px ＋半片宽 3px
  ＝ 171px < 半宽 210px，算术上就装得下，实测 `outside: 0` 是这件事第一次有数。B-020 ④ 那条"光芒出框"
  是遮罩画法问题，与彩带无关。
- **升星爆帧**：峰值**同时可见 16/16 颗**、采样 10 帧、落定点云中心相对卡片 **(0,-3)px**。

- **取证怎么复跑**：`SB_PROBE_DB` 指向**系统临时目录下**那份库（护栏：不在 tmp  realpath 下就拒绝写），

## 11. 验收判据

1. 一条词条的卡数 = 它的提及流水条数 + 不同复习日数 + 1，**用 SQL 手工数一遍能对上**（无中间表可对账，

   （`countUsage` 那条"归主之后漏传就是串台"的教训在本批每个新查询上同样成立）。
