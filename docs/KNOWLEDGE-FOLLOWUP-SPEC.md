## 0. 一句话

在**词条卡**上点「向 AI 追问」→ **另开一个 fork 会话**（带原对话摘要）→ 该会话回答里沉淀的词条
**自动与源词条连一条边**。一次追问 = 一个**星型拓扑**；追问出来的词条可以再追问 ⇒ 长成**树**。

> ⚰️ **v1.1 注（2026-09-25，批次 K）**：上面这句里只有前半「点追问 → 另开 fork 会话」还在产品里；
> 后半「自动连边 / 星型 / 长成树」**已随知识图整族下线删除**。今天点「向 AI 追问」的实际效果 =
> **一个新会话 + 带过去的原对话摘要 + 首问**，不再有任何图数据被写。

## 1. 需求与边界（老板原话，2026-09-20）

> 「把这个词条显示加一个功能，那就是向 AI 追问，追问之后会单独开一个对话回复，也就是类似于 fork 的效果，
> 然后这个时候知识图就会自动记录，用户根据对哪个词条进行了追问，然后追问之后 AI 的回复里也会有词条，
> 所以这个 AI 回复的词条也就和原词条构建出了关系，然后知识图上就会自动构建出来点和线的关系……
> 因为一个 AI 回复里可能会有多个词条嘛，所以用户对一个词条进行追问可能就会形成一个**星型拓扑**，
> 然后因为追问的回复中的词条还可以再进行追问，所以最后就会形成一个**三维结构**，就和笔记软件黑曜石有点像。」

老板随后拍板的三条口径（AskUserQuestion 回执）：

| 问题 | 拍板 |
|------|------|
| 追问带什么上下文 | **带原对话摘要** |
| 图上的点与线是什么 | **点全部都是词条**；线是**知识点关系**（不是"谁追问了谁"的操作记录）；**追问是用户的手动确认动作，负责把点连起来** |
| 「三维」怎么落 | **参考 Obsidian Graph View，实际是 2D**（不引 three.js，不破零第三方库红线） |

### 1.1 由此推出的三条硬边界

1. **不建"轮次节点"、不建"操作边"。** 图上只有 `kind='term'` 的点，只有词条↔词条的边。
   追问这件事本身**不进图**——它是**触发连边的用户手势**，不是一种关系。
   （这排除了「A 追问了 B」这种边，也排除了 `knowledge_node.kind='turn'` 在本次的用法。）
2. **不是"同一条回复里出现的词条两两相连"。** 那是共现，噪声极大（一句解释里出现五个词条就产生 10 条边）。
   只有**用户明确选了一个词条去追问**，才产生边 —— 用户的动作就是那道人肉过滤器。
3. **不引第三方图库。** 现有 `NeighborhoodGraph` + `graph-visual.ts` 的**同心环 + 父角度扇区**布局
   本身就是星型/树的画法（一跳均分整圆 = 星；二跳落在父扇区内 = 树枝），本批**沿用**，不重写。
   若实测发现深树（≥3 跳、兄弟多）挤成一团，再开独立批次做力导向，不在此处破红线。

| `knowledge_edge.origin = 'ai'` | `learning/knowledge-graph.ts` 三值 origin 之一 | 有类型、有前端配色与文案（「AI 抽取·未经确认」）、有单边删除能力，**但没有任何生产写点** |

本批新增**唯一**的 schema 改动：

```sql
-- 迁移 v38
ALTER TABLE sessions ADD COLUMN forked_term TEXT
```

* `forked_term` 存**词条名**而不是 `term_library.id`。
  ★ 理由与 `evolution_event.term_text`（第五次复用）、`knowledge_node.ref_text` 同源：
  **抗删快照**。词条可能被整理（`TERM-TIDY-SPEC`）合并掉、被用户删掉；存 id 的话那些行会变成
  指向虚空的外键，且会话标题（`追问：X`）反而要回查一次库才画得出来。存名，孤儿会话仍自洽可读。
* 建边时**按名现查** `term_library`（`findTermByName`）：查不到 ⇒ **不建边**，如实返回 0。
  一个已被删掉的词条不该在图上留一个幽灵星心（见 §8 未验账）。

## 3. 边语义（★ 三条不可省的判据）

### 3.1 边的方向与类型

```
(源词条节点) --relates--> (追问会话里沉淀的每个词条节点)
```

* `kind = 'relates'`（复用既有四值之一，不加新 kind）。语义是「相关」，与 `prereq`（前置）
  / `derived_from`（由…引发）/ `contains`（从属）都不同——追问回答里出现的词条，多半是
  「解释源词条时顺带讲到的东西」或「它的上位/下位概念」，这正是 `relates` 的既有定义。
* **方向 = 源 → 新**。它不是"顺序"（图上不画箭头语义），而是给出**可追溯的出处**：
  从哪一次追问长出来的。同一条边重复抽取由库约束去重（下 3.3）。

### 3.2 `origin` 取 **`'ai'`**，不是 `'user'`（最容易搞错的一条）

`knowledge-graph.ts` 的宪章把三值**刻意不平权**：`user` = 用户手搭（最高可信）、
`ai` = AI 抽取（可能幻觉）、`derived` = 规则可重算。

这里有两件事被混在一起，必须拆开：

| 事情 | 谁做的 | 可信度 |
|------|--------|--------|
| **发起追问**（"我要深挖这个词条"） | **用户**（点击） | 高——这是真实意图 |
| **"源词条与这些新词条有关系"这个命题** | **AI**（回复里提到它们） | 未知——模型可能只是顺口提了一句 |

边承载的是**后者**（关系命题），所以 `origin = 'ai'`。
**不能因为"用户点了按钮"就把边记成 `user`** —— 那会把模型顺口提到的词条洗成用户确认过的知识点，
正是宪章要防的那种污染。用户要转正，走既有能力：知识图上手工连一条边（`origin='user'`）或删掉这条。

同理，`weight` 用 `addEdge` 的默认 **0.5**，**不因"用户主动发起了追问"而调高**——
权重该反映关系的可信度，不是动作的强度。（对照：`derived` 同域边是 0.3，因为规则推导比模型抽取更弱。）

`evidence` 记 `追问「<源词条名>」`：这是**可审计的出处**，也是用户在图上一眼看出
"这条线是哪次追问长出来的"的唯一线索（用户在节点详情卡里能看到 evidence）。

### 3.3 幂等一律交给库约束

`knowledge_node` 的 `UNIQUE(kind, ref_id)`、`knowledge_edge` 的 `UNIQUE(from_node_id, to_node_id, kind)`
配 `INSERT OR IGNORE`。**调用方不需要记得"只跑一次"**：
同一个词条在同一个追问会话里被抽到两次、或者用户重新生成了一次回复，都只会得到一条边。

★ 由此推出一个**不要做的优化**：不要为了省查询而缓存"这条边建过没有"。
库约束已经保证正确，自己再加一层缓存只会多一份会漂的状态。

## 4. 原对话摘要：三档来源（**优先免费的那一档**）

老板要「带原对话摘要」。本仓**已经有**一份真正的 AI 摘要：`sessions.summary`
（迁移 v10 加的列，`chat/compact.ts` 在上下文超窗口时 fire-and-forget 写入）。
★ 所以**优先复用它**——它是免费的（已经算过）、无损的（真正的模型摘要）。

组装时按顺序取第一档命中的：

| 档 | 来源 | `summarySource` | 说明 |
|----|------|-----------------|------|
| ① | `sessions.summary`（已有压缩摘要）非空 | `'compact'` | 零成本、真摘要。截断到预算上限 |
| ② | 原会话**最近 N 条消息**的抽取式摘录 | `'recent'` | 会话还短、没触发过压缩时走这条。**在 prompt 里如实标明是摘录、不是摘要** |
| ③ | 原会话一条消息都没有 | `'none'` | 不编造，如实留空 |

★ **为什么第 ② 档不做"现调一次 LLM 摘要"**：那是**同步阻塞**在用户点击与首个 token 之间的一次额外
模型调用（2~5 秒），而这个功能的全部体验价值就在"点完立刻开聊"。用户盯着转圈等摘要，是净损失。
抽取式摘录在短会话上信息量并不低（短会话本来就短），长会话则已经命中第 ① 档。

★ 第 ② 档在 prompt 正文里**必须写明「以下为原对话摘录（未压缩）」**：
不写的话模型会把摘录当成完整上下文，可能对"你之前说过"做过度推断。**诚实档**（ADR-5）。

## 5. 协议

### 5.1 `POST /api/sessions/:id/fork`

请求体（`normalizeFollowUpRequest` 归一）：

```jsonc
{ "term": "闭包", "question": "它和柯里化是什么关系？" }   // question 可省
```

响应 200：

```jsonc
{
  "sessionId": "…",            // 新 fork 会话
  "title": "追问：闭包",
  "forkedFromId": "…",         // = :id
  "term": "闭包",
  "summarySource": "compact"   // 前端据此如实告知「带了什么上下文」
}
```

错误：

| 码 | 条件 |
|----|------|
| 400 | `term` 缺失/空/超长（`FOLLOW_UP_TERM_MAX`）；body 不是对象；`question` 非字符串且非空 |
| 404 | 父会话不存在或不属于当前用户（与 `sessions` 域口径一致：**一律 404，不回 403**，不泄露 id 存在性） |

★ **`term` 超长是拒绝而不是截断**（与 `normalizeSpeechSettings` 的 `voiceName` 相反）。
判据是**污染半径**：音色名截断只会导致一次朗读回落默认（可自愈），而词条名截断会连到
**错误的图上节点**（不可自愈的脏数据）。这类差异要在契约里写出来，不能让两处看起来"不一致"。

### 5.2 端点内部做什么

1. `canAccessSession(:id, ownerId)` —— 不通过即 404。
2. 摘要三档（§4）。
3. **组装首问**（`chat/follow-up.ts#composeFollowUpPrompt`）：源词条 + 释义 + 摘要 + 用户问题。
4. **落后端**：`INSERT INTO sessions(…, forked_from_id, forked_term, title)`，
   `title = '追问：<term>'`（截断到 `FOLLOW_UP_TITLE_MAX`）。
   ★ title 必须**不是** `'新对话'`：`chat/flow.ts` 有一条「title 还是默认值就用首句覆盖」的逻辑，
   用默认值会被首问正文（一长段带摘要的 prompt）冲掉。
5. **起流**：`handleMessage({ sessionId, text: prompt, ownerId, signal })` —— **不带 `skipUserPersist`**。
   首问正文由正常链路落库，于是它**就是**会话的第一条 user 消息：用户看得见、可编辑重发、
   历史回放一致。不做"服务端偷偷塞一条消息"那种影子状态。
6. 立刻回 200（流走 SSE，与 `POST /chat/send` 同款 fire-and-forget）。

### 5.3 首问的组装格式（`composeFollowUpPrompt`）

```
我正在学习词条「<term>」（领域：<domain>）。
它的释义是：<definition>

【原对话摘要】            ← 'compact' 档
<summary>

  或

【原对话摘录（未压缩，共 N 条中的最近 M 条）】   ← 'recent' 档
用户：……
助手：……

请针对上面这个词条回答我的追问：<question>
```

★ 首问是**服务端生成**的，用户会在屏上看到这一整段。这是**故意的**：
用户应该能一眼看出"这次追问带了什么上下文过去"，而不是面对一个黑盒。
`summarySource = 'none'` 时**整块省略**（不写"（无摘要）"这种占位噪声）。

### 5.4 边在哪一步建（`chat/post-turn.ts`）

原逻辑在 `chat/flow.ts` 的回复收尾里：`extractTerms(...)` → `saveTerms(...)` → `compactIfNeeded(...)`。
本批把它整段搬到新文件 `chat/post-turn.ts`，中间插一步 `linkFollowUpEdges(sessionId)`：

```
抽词 → 落词条库 → 【★ 若是 fork 会话：连追问星型边】 → 压缩长期记忆
```

★ 为什么搬到新文件而不是就地加两行：`flow.ts` 收尾时 394 行，加完触 server `≤400` 红线。
按仓规**拆文件、不压注释**。接缝也干净：「这一轮**跑完了**要做什么」不属于「这一轮**怎么跑**」。

★ 为什么**读库里的 `forked_term`** 而不是从路由传参下来（如 `ChatOptions.followUpTerm`）：
  · 读库 = **服务端真相**，客户端伪造不出来；
  · 传参只覆盖"追问那一次"，而用户在 fork 会话里接着聊出的词条就悄悄丢了边；
  · 读库只用一次主键查询（`sessions` 的 PK），成本可忽略。
  ⇒ 于是 `ChatOptions` **一行都不用改**，路由也不用往下传新字段。

★ 建边的时机是**每一轮回复**（不是只有第一轮），因为 fork 会话的语义就是"关于这个词条的深挖"。
  幂等由库约束兜住（§3.3），重复不会产生重复边。

## 6. 前端交互

1. **入口只在 `full` 卡（点击固定态）**，不在 `mini`（悬停速览）——追问是"要操作"那档强度的事，
   与既有「纳入复习 / 打开词条库」同组。悬停卡多一个输入框会让速览变得不可速览。
2. 卡片里是**一行输入 + 「追问」按钮**（不是点一下直接开）：用户往往是带着具体问题来的，
   逼他先开一个空会话再打字，等于把动作拆成两步。输入框 `placeholder` = 默认问题
   （`defaultFollowUpQuestion`），**留空即用默认**。
3. **未注入 `onFollowUp` 时不渲染**这组控件（同 `openTerms` 的既有手法）——
   不做点了才报错的假按钮。`Markdown` 被笔记页复用时自然没有这个能力，不该出现按钮。
4. 点击后：`POST …/fork` → **切到新会话**（`setView('chat')` + `setCurrentId`）→ 刷会话列表
   （新会话要立刻出现在侧栏）。回答的流由既有 `useChatStream` + `GET /api/chat/active` 接住。
5. 走 `TermIndexProvider` 的上下文注入，**不穿透** `Markdown`/`MessageRow` 的 props 链
   （理由同 `openTerms`：改一处 vs 改四个组件签名，且 `Markdown` 是公共组件）。
6. ★ **同一个动作的第二个入口**（v0.2.85，2026-09-20）：学习流页**运行轨迹的产出词条**
   （`features/study-flow/ProducedNodes.tsx`；服务端视角见 `docs/STUDY-FLOW-SPEC.md` §6.7）。
   学习流跑完后用户看到的第一批词条就在那儿，原本只是一排死 chip（想深挖得先切到词条库
   再把它找回来）。★ 与词条卡**唯一的实质差别是父会话从哪来**：词条卡用「当前打开的会话」
   （`App.currentId`），而学习流页是**另一个视图**、用户此刻并没有"正在看的对话"
   ⇒ 显式给 `flow_run.session_id`。故动作签名收敛成
   `FollowUpAction = (term, question?, fromSessionId?)`（`fromSessionId` 省缺＝当前会话），
   **单点定义在 `packages/web/src/lib/api.ts`**（`App` / `FlowPage` / `ProducedNodes` 三处
   共用一份口径——内联三次将来必漏改）；★ **服务端零改动**（同一个端点、同一套连边规则）。
   ★ 只对 `term` 节点给入口：`note` / `concept` 没有对应词条行 ⇒ 追问会开出一个**连不上
   任何边**的会话（静默空转），ADR-5 不许静默 ⇒ 那种节点连按钮都不给。

## 7. 复用了什么 / 刻意不做什么

**复用（一行新的都没写）**
* `sessions.forked_from_id`（v1 就留好了）
* `knowledge_edge.origin='ai'` 的前端配色、文案「AI 抽取·未经确认」、单边删除能力
* `NeighborhoodGraph` 的同心环 + 父扇区布局（星与树本来就这么画）
* 知识图页的「按 origin 筛选统计」「清理自动关系（只删 derived）」「手工连边转正」
* `sessions.summary`（v10 的压缩摘要）作为 §4 第 ① 档
* `useActiveSessions` 的 2s 轮询——新会话在生成中会自然显示「回复中」
* ★ 同一个 `POST /api/sessions/:id/fork` 的**第二处调用点**（学习流页的产出词条，v0.2.85，

## 8. 未验账（诚实记账）

1. **源词条被删/被合并后，该 fork 会话不再连边**（`findTermByName` 查不到 ⇒ 返回 0，不报错）。
   这是**有意选择**（不留幽灵星心），但用户看到的现象是"我追问过，图上却没有线"。
   若实测觉得该有反馈，下批在 fork 响应里加一个 `linked: false` 之类的如实标记——**本批不做**，
   因为还没有实测证据说明这是个真痛点。
2. **深树（≥3 跳 + 兄弟多）的观感未验**：现有布局在 2 跳内是可读的，更深的树会不会挤成一团
   需要真机跑一个三层追问链来确认。若挤 ⇒ 开独立批次做力导向布局（不动数据层）。
3. **真机端到端未测**：沙箱里跑不了"点词条 → 追问 → 看回答流上屏 → 去知识图看星型"的完整动线。
   单测覆盖的是**每段的行为**（归一、摘要三档、连边幂等、路由状态码），
   跨段动线要靠真机冒烟（见 §9）。★ **v0.2.85 的第二入口同理未跑**：「跑一条学习流 → 在产出
   列表点词条 → 追问 → 看流式回复 → 切到知识图看它长出的边」一次都没跑（沙箱起不了监听端口）。
   该入口的父会话来自 `flow_run.session_id` 而**不是**当前会话，**这一条尤其需要真机证**——
   单测只锁到"第三个实参是那次运行的会话"，锁不到"从那次运行的会话分叉后边真的连上了"。
4. **`summary` 的时效性**：`sessions.summary` 只覆盖到 `summary_upto_rowid`，
   之后的消息不在摘要里。追问带过去的是"到压缩点为止"的上下文。
   ★ 这是**已知且可接受**的（压缩设计如此），但 prompt 里**没有**声明这一点——
   如果实测发现模型因此对"最近发生了什么"答非所问，下批在 prompt 里补一句
   「摘要截至某个时点，其后对话未包含」。本批不预先加，避免 prompt 里堆免责声明。
