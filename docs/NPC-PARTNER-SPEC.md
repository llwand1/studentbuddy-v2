## 0. 一句话与七元素口径

**把「一个会说人话、会求救、能拿词条等你来换」的 AI 学习伙伴放到知识大陆上**——它是 AI 能力的
**可见载体**（用户看得见、点得着、说得上话），也是「开疆拓土」的正反馈（地图越大、伙伴越多）。

老板列的七元素与本册的对应关系（逐条钉死，防止实现漂移）：

| # | 元素 | 落地口径 | 本节 |
| - | ---- | -------- | ---- |
| ① | NPC 接入 AI | 新增 `npc` 模型角色；无 key 时**降级到本地台词**（不静默、不说"AI 坏了"） | §4 |
| ② | 扩展辅助学习功能 | 对话里伙伴会**就自己守的那条词条**提问／给线索；交换直接送**没见过的词条** | §4 / §6 |
| ③ | 宣传点「创建你的 AI 学习伙伴」 | 伙伴可**命名**（落 `app_settings` KV，永久生效） | §3 |
| ④ | 与任务清单联动 | NPC 遇怪 ⇒ 派一条 **`npc_rescue`** 求救单进任务清单；救出即完成并发钥匙 | §5 |
| ⑤ | 可与 NPC 对话交互 | `POST /api/npc/:id/talk`，上下文 = 人设 + 他守的词条 + 附近的怪 | §4 |
| ⑥ | 卡牌交换 | 拿一张**自己的**卡当信物 ⇒ 换回**同领域没见过的**新词条（复用既有宝箱账本） | §6 |
| ⑦ | NPC 数量受地图大小限制 | `npcCountFor(词条数)`，上限 `NPC_MAX = 6` | §2 |

★★ **本批的立命之本是「零新表、零新迁移」**（与知识大陆优化批、卡牌批同一条红线）：七元素里没有一条

★ **落地后的两处分工修正（v1.1，实跑时定下）**：① 交换那一行 `chest_open` 的写口落在
`learning/npc.ts` 的 `grantTradeDraw`，**不在** `chest.ts`——同一张表上的两套付账规则
（扣钥匙／不扣钥匙）分开住既贴切，也让 `chest.ts` 守住了 400 行红线（表的形状 `PoolItem`／

`ContinentPage.tsx` 要守 `.tsx ≤300 行` 红线，伙伴这一族（取数 + 三条横幅 + 面板接线）塞进去当场撞线。
两处都是**红线逼出来的拆法**，不是设计变更。

## 1. 边界：与既有三册的分工线

- **边界①：NPC 不是第二套怪、不是第二套卡。** 伙伴不占格（不参与领地扩散、不挡英雄走位），
  他也不发卡——交换落的是**既有** `chest_open` 流水，"收下"走**既有** `POST /api/cards/chest/accept`。
  ⇒ 卡数口径（`TERM-CARDS-SPEC` §1）一字未动，从宝箱来的词条与从 NPC 来的词条**在卡墙上长得一样**。
- **边界②：伙伴不新增刷新频率。** 地图取数仍只有 `GET /api/terms/review/map` 一条只读口；
  NPC 列表随 `GET /api/npc` 单取一次，**不轮询、不订阅新 SSE**（对话是请求-响应，不是推送）。
- **边界③：伙伴不替用户做学习动作。** 他会催、会给线索、会求救，但**不代答、不改复习阶段、
  不写复习流水**。解除占领的唯一路径仍是「答对那道题」（`KNOWLEDGE-CONTINENT-SPEC`）。

## 2. NPC 数量与位置：全派生，零存储

### 2.1 数量

```
npcCountFor(termCount, radius) = clamp(floor(termCount / NPC_TERMS_PER_NPC), 1, npcCapFor(radius))
NPC_TERMS_PER_NPC = 8      // 每 8 条词条解锁一位伙伴
npcCapFor(radius) = clamp(floor((2*radius+1)^2 / 40), NPC_MAX_MIN=6, NPC_MAX_CAP=24)   // ≈ 每 40 格站 1 位
NPC_MAX_MIN = 6            // 下限：世界再小也"看得出多了人"的密度底
NPC_MAX_CAP = 24           // 硬上限：再多就成"人挤人"，且地图本身也装不下
```

- ★★ **上限跟世界半径走（2026-09-27 批 11 改，老板裁定「跟着世界涨」）**：世界开放后（见
  `KNOWLEDGE-CONTINENT-SPEC.md`「开放世界与视口」段）地图不再封在 140 格，若上限仍写死 6，
  327 条词条就顶死、加词再无奖励 ⇒ 与 ⑦「鼓励开疆拓土」相悖。本机实测：`R=9 ⇒ cap 9`
  ⇒ 327 条得 **9 位**（旧口径 6 → 9）；`R=7 ⇒ cap 6`（小库不变）；`R=20 ⇒ cap 24`（封顶）。
  ⚠️ 密度口径是**产品感受值**（把握度中）：先按"每 40 格 1 位"落，真机看密度再调；数值只在这两个
  常量与 `npcCapFor` 里，改它不动别处。

- ★ **为什么按「词条数」而不是「领地格数」**：领地是**怪**的派生量（逾期越久地越大），拿它当伙伴数量
  的输入会出现「越不复习、伙伴越多」——激励方向正好反了。词条数是**用户主动加词**的结果，
  这才与老板那条「鼓励用户通过学习来开疆拓土」同向。
- ★ **上限为什么是"跟着世界涨"而不是一个定值**：伙伴**不占格**（见 §2.2），所以世界越大越显得空；
  上限必须跟着世界半径单调增，才不至于"加了 100 条词条，一个伙伴都不多"。世界半径本身**只增不减**
  （`worldRadiusFor`），故这条上限也**只增不减** ⇒ 已落位的伙伴不会因加词而消失。
- ★ **下限是 1**：宣传点是「创建你的 AI 学习伙伴」，空大陆也该有一位伙伴在场（哪怕地图上一格都没有，
  见 2.2 的空手返回），否则用户第一眼看到的功能是"没有功能"。
- ⚠️ **空库例外（如实写）**：`termCount = 0` 时 `npcCountFor` 仍返回 1，但**没有可落脚的格**
  ⇒ `placeNpcs` 返回空数组。这是数据形状决定的，不是 bug；UI 必须说实话（§7.4）。

### 2.2 位置：锚定在「没冒怪的地块」上

```
placeNpcs(candidates, count)
  candidates = 地图上 !hasMonster 的地块（含已被占领的领地格——伙伴不怕怪的地盘）
  排序       = continentHash(`npc|${termId}`) 升序，同值按 termId 升序（稳定、跨端一致）
  取前 count 个；npcId = `npc:${termId}`；name = NPC_NAME_POOL[hash % len]
```

- ★ **为什么要锚定 `termId`**：伙伴得有个「他懂的那一块知识」才能说人话（§4 的提问、§6 的交换领域
  都从这里取）。锚在格子上就没有这个语义，锚在词的 id 上则**跨端稳定**（同一份库任何端算出同一位伙伴）。
- ★ **为什么可以站在领地格上**：领地是怪的地盘，伙伴站在那儿正是"他遇险了"的**视觉前提**
  （§5）。若把领地也排除，求救单就只剩"紧邻"一种触发形态，地图上"伙伴被围住"读不出来。
- ★ **伙伴不占格**：他**不进** `spreadLands` 的 `blocked`、不改 `walkable`。
  ⇒ 走位／领地／点击分流的既有逻辑**一行未改**（这是"接入而非改造"的直接好处）。
- ⚠️ **先过滤 `!hasMonster`，再按哈希取**：不过滤就会出现"伙伴和怪站在同一格"（画面上两只
  叠在一起，且他到底在不在危险里也说不清）。

## 3. 身份：伙伴名字落 `app_settings` KV

- 键：`SETTING_KEY_NPC_PARTNER = 'npc_partner'`，值 = JSON `{ name: string }`。
- 读不到 / JSON 坏 / 名字不合法 ⇒ **回退默认名**（`NPC_NAME_POOL` 的稳定哈希选址），不报错
  （数据容错，与 `answer-style.ts` 同口径）。
- 写：`PUT /api/npc/partner`，`name` 归一化（去首尾空白、截断到 `NPC_NAME_MAX = 12` 字），
  **空串 ⇒ 删键回默认**（与 `resetAnswerStyle` 同手法）。
- ★ **只有「主伙伴」（`placeNpcs` 结果的第 0 位）用用户起的名字**，其余伙伴用 `NPC_NAME_POOL` 的
  默认名。理由：宣传点是「**创建你的** AI 学习伙伴」——用户创建的是**那一位**；后长出来的伙伴是
  "大陆上别的居民"，跟着改名会变成"重命名一个列表"，那是另一个功能。
- ⚠️ 主伙伴的 `npcId` 会随地图长大而**变化**（第 0 位是哈希序第一，加词后可能换人）。
  ⇒ 名字存在 **`app_settings` 的单一键上（不按 npcId 分桶）**，正是为了这一刻：用户起的名字
  **跟着「他的伙伴」走，不跟着某条词条走**。这是本册唯一一处"看起来存少了、其实是存对了"。

## 4. AI 接入：`npc` 角色 + 本地降级

### 4.1 角色

- `shared/src/domain.ts` 的 `ModelRole` 加 `'npc'`；`llm/router.ts` 的 `MODEL_ROLES` 加
  `{ role: 'npc', label: '学习伙伴（大陆 NPC）' }`。★ 数组驱动 ⇒ 默认种子与设置页自动带上，**无需迁移**。
- **降级链**（照 `coach` 的既有形状，理由同源）：`npc` 角色未绑定 ⇒ 回退 `explain`（讲解）。
  伙伴对话本质是日常对话，用讲解模型是合理默认；老库升级后 `role_bindings` 里本就没有这一行，
  若按"必须绑定"处理，用户看到的是「该角色还没绑定模型」而他从没改过任何设置。

### 4.2 无 key 时的降级台词（★ 本册最容易被做错的一处）

- `routeRole('npc')` 返回 null、或 `model`/`apiKey` 为空 ⇒ **走 `NPC_FALLBACK_LINES`**：
  按 `continentHash(`${npcId}|${轮次}`)` 从台词池里选一条，**永不报错、永不空回**。
- ★ **为什么降级而不是报错**：NPC 是**地图上的常驻元素**，用户点他是"想跟伙伴说句话"，
  不是"提交一次模型调用"。报「没有可用的服务商」会让地图上多出一块**坏掉的功能**——
  这正是老板立项要消灭的观感（"AI 含量太少"）。
- ★ **但降级必须可识别**：响应体带 `source: 'ai' | 'fallback'`，UI 在 fallback 时说清
  「伙伴现在靠固定台词应答——到设置里给他绑一个模型，他就能真的聊起来」。
  **降级可以，假装没降级不行**（ADR-5 的"报错说真话"在这里的等价物是"降级说真话"）。
- 台词池（`NPC_FALLBACK_LINES`）**只谈他守的那条词条与其领域**，不编造用户进度
  （编就会与卡墙/task 的数字对不上——`TERM-CARDS-SPEC` §5 那条学费的同类）。

### 4.3 上下文（送给模型的就这几块）

人设（伙伴名 + 他守的词条 + 领域）+ **他当前是否遇险**（§5 的结论）+ 本轮用户输入。
★ **不带用户的完整卡墙/复习流水**：伙伴的职责是"陪聊＋守好自己那块地"，把全库塞进上下文
既费钱，又会让他说出与任务清单打架的话（"你还有 5 条欠账"由 `coach` 说，不由 NPC 说）。

- 温度 `0.8`（比 coach 的 0.6 高：伙伴要有人味）、上限 `NPC_MAX_TOKENS = 600`（短对话）。

## 5. 与任务清单联动：`npc_rescue` 求救单

### 5.1 判据：什么叫「遇怪求救」

```
npcDistress(npc, monsterCells) = 曼哈顿距离 ≤ NPC_DANGER_RANGE(1) 的最近怪的本体
  ⇒ 有 ⇒ { termId, term, distance }（威胁）
  ⇒ 无 ⇒ null
```

- 输入只有「怪的本体格」（`!hasMonster` 的格不会出现）；**领地格不算威胁源**——
  领地是怪**已经**吞下的地，伙伴站在上面是"地丢了"，不是"被围住"，两者文案不同（§7.4）。
- ★ 距离取 1（正相邻），与「靠近才开打」（`canStrike`）**同一条判据**：伙伴喊"救命"的位置，
  就是用户**一步就能打到**的位置。距离放宽到 2 会出现"他说被围住了，我却够不着"。

### 5.2 派单

- `study_task.kind` 新增 `'npc_rescue'`（ASCII 键，同三条既有 kind 的判据）。
- 字段：`title = '去救「<伙伴名>」'`、`why = '它被「<词条>」的怪堵住了——答对那道题，怪就散了。'`、
  `termId = 威胁怪的词条 id`、`refId = npcId`、`dedupeKey = npcRescueDedupeKey(npcId)`（**不含会变的数**）。
- ★ **求救单派在队列最前**（`dispatchTasks` 的 intents 里 `npc_rescue` 置首）：它是**有时效**的
  （怪还在那儿），而"推进/破停滞/补池"三单随时可做。`MAX_OPEN_TASKS = 4` 的额度被占满时，
  先出局的该是那三单。
- ★ 遇险的伙伴**每位一单**，且**不占新的调度器**：仍挂既有 6 小时 tick（`TERM-CARDS-SPEC` §5）。

### 5.3 完成判据（`isDone`）

```
npc_rescue ⇒ refId 对应的伙伴「当前不再遇险」即完成
  · 怪被答对 ⇒ 状态离开 due/overdue ⇒ 怪消失 ⇒ 伙伴脱险 ⇒ 这单自动 done + 发一把钥匙
  · 词条被删 / 词条被移出复习范围 ⇒ 怪没了 ⇒ 同样脱险 ⇒ done
  · 伙伴本身没了（地图缩小 / 那条锚定词条被删）⇒ 不在遇险集合里 ⇒ done（★ 防挂单）
```

- ★★ **实现方式只有一句**：`isDone` 问 `learning/npc.ts` 要**当前遇险伙伴 id 的集合**，
  `refId` 不在里面就完成。⇒ "词条缺失判完成防挂单"那条要求**自动满足**，不需要单独分支
  （这正是"判据从派生量读、不从标题猜"的好处）。
- ★ 与 `unstall` 那单的差别：`unstall` 要防"派单那一 tick 立刻判完成"，这里**天然不会**
  ——派单的前提就是"此刻在遇险"，此刻 `isDone` 必为 false。
- ★ 发钥匙仍走**唯一那处翻转**（`reconcileTasks` 的 `changes === 1`），本册不新增发钥匙路径。

## 6. 交换：信物卡 → 同领域新词条

### 6.1 语义（★★ 一处被实测纠正过的口径，必须照此实现）

```
POST /api/npc/:id/trade  body { termId }   // termId = 用户拿出来的**信物卡**（自己的词条）
  · 信物必须 cards >= 2（`NPC_TRADE_MIN_CARDS`）——★0 的卡拿不出手（那是"刚记下来"，不是"我熟"）
  · 回的是一条**没见过的**新词条，且 domain 与信物**同领域**（伙伴只懂自己那一块）
  · **不花钥匙、不落信物账**；落账只写一行 `chest_open`（`source_kind='npc'`、`pool_slug=条目 slug`）
  · 收下这张卡走**既有** `POST /api/cards/chest/accept`（收下 / 收下并纳入复习两枚钮，一字不改）
  · ★ 写口是 `learning/npc.ts:grantTradeDraw`——**不动 `chest_keys`**（不扣免费次数、不扣赚来的钥匙）
```

### 6.2 ★★ 为什么信物**不能**存进 `chest_open.pool_slug`（实测纠正，别再写回去）

`pool_slug` 是**抽卡去重集**的键：`drawablePool()` 读 `chest_open.pool_slug` 判「本人已抽过」，
`ux_chest_open_pool` 是它的唯一索引。把信物卡 id 兼存进去会**立刻破坏抽卡去重**——
宝箱会重复抽出用户早就抽过的词。⇒ 信物卡**只作领域定向**（决定"回赠哪个领域"），
**不落任何账**。

### 6.3 ★ 代价如实记：卡是**读数**不是道具，所以"给出信物"没有真实损耗

`TERM-CARDS-SPEC` §1 边界① 钉死了「卡数是流水派生，库里没有可扣的库存」。因此：

- **信物无法被消耗**（扣它就要么伪造流水、要么开一条只有 UI 知道的旁路账——两者都是 §1 明令禁止的）。
- ⇒ 交换的真实约束**只能落在别处**，本册用两条：
  1. **每日上限** `NPC_TRADES_PER_DAY = 2`：按 `chest_open` 里 `source_kind='npc' AND opened_day=今天`
     的行数判（`opened_day` 是既有列，**零迁移**做到了日级闸门）。
  2. **信物门槛** `cards >= 2`：用户得真的碰过那条词条（★1 以上）才有资格去换。
- ★ 用一句人话写进 UI 与文档，不让用户以为"卡被扣了"：**「换一次要挑一条你熟的词条
  （★1 以上）当信物——卡本身不会少，但每天只换得动两次。」**

### 6.4 选词与失败

- 选词：`drawablePool(ownerId)` 里**筛出信物同 domain** 的条目，按 `continentHash(`${npcId}|${slug}`)`
  升序取第一（**确定性**，同一伙伴同一次选择稳定；不随机 ⇒ 可单测）。
- 领域里没得换 ⇒ **回落全池**并如实告知（"你那个领域暂时没新词了，我给你挑了别的领域的"
  ——比"换不了"有用，且失败原因说清了）。
- 全池空 ⇒ `409`，文案与宝箱的 `empty` 一致（"词池里没有你没见过的新词了"）。
- 信物不存在 / 不是自己的 / `cards < 2` ⇒ `409`，三种各一句（不许压成一句"换不了"）。

## 7. HTTP 与 UI

### 7.1 路由：新册 `routes/npc.ts`，挂 `/api/npc`

| 方法 | 路径 | 说明 |
| ---- | ---- | ---- |
| GET | `/` | `{ partnerName, npcs: NpcView[], count, max, tradesLeft }`（一次读全，含遇险结论） |
| PUT | `/partner` | `{ name }` 改名；空串 ⇒ 删键回默认 |
| POST | `/:id/talk` | `{ text }` → `{ reply, source }` |
| POST | `/:id/trade` | `{ termId }` → `{ draw }`（`draw.openId` 交给 `/api/cards/chest/accept`） |

- `NpcView = { id, name, termId, term, domain, row, col, distressed, threat? }`。
  ★ **位置与遇险结论都由服务端给**：前端不重算铺格/领地（双份口径 = 「图上画着伙伴遇险、
  日志里没有那单」的开端）。这条与 `continent-view.ts` 头注同一条判据。
- ★ 端点**不新增 SSE 事件**：求救单的到达走既有 `task_dispatched`，`/state` 回读即可。

### 7.2 绘制（`continent-canvas.ts`）

- 新增 `drawNpc(ctx, spot, bob, distressed, pulse)`：像素小人（比英雄**矮一头**、戴橙帽）。
  ★ 与英雄的区别做在**高度 + 帽檐**两处，不只靠配色——像素风里颜色是最不可靠的区分手段
  （色弱、小屏、压暗的领地格都会吃掉它）。遇险时头顶冒一个**红色惊叹块**（只动 `opacity`）。
- ★ 画序（**按实现定稿**）：**领地 → 宝箱 → 怪 → NPC → 英雄**。宝箱在怪**之下**是**既有**的刻意
  取舍（「它是'地上的东西'，不该盖住怪的脸」，见 `ContinentMap.tsx` 画序注释，本批不动它）；伙伴永远在怪之上（"他在怪的地盘上"要看得见）、
  在英雄之下（玩家自己的角色永不被遮）。
- ★ 只动 `transform`／`opacity`／颜色；`prefers-reduced-motion` 下 `bob = 0`、惊叹块常亮。
  ★ 惊叹块的呼吸**不新开 rAF 循环**：地图静止时停在当前相位——与领地边界的"常驻呼吸"同一个取舍
  （地图是常驻页，空转循环等于持续耗电）。

### 7.3 交互（`NpcDialog.tsx`）

- 点伙伴 ⇒ 开对话面板：名字、他守的词条、当前状态（安好／遇险）、对话框、信物选择（`cards>=2` 的
  词条下拉）、"换一条新词"按钮、剩余可换次数。
- ★ 遇险时面板顶部给一个**直达按钮**：「去救他」⇒ 关面板 + 镜头/提示指向威胁怪（不代打，
  只是把用户送到能打的位置——`useContinentHero.walkTo`）。
- ★ 对话输入与走位的冲突照既有形状：`frozen = hunting || chestAt || npcOpen` 时**键盘走位让位**
  （否则打字变成走路，`ContinentPage.tsx` 已有这条）。
- ★ **地图点击分流里伙伴排在宝箱之后**：宝箱是**一次性**的（开了就没），伙伴一直站在那儿。
  两者同格是极小概率（怪死后那格才变成落位候选），真撞上时先给一次性那个。

### 7.4 文案必须说真话的四处

1. 空库：伙伴有 count 却一格都没有 ⇒ "大陆还是一片空地，伙伴在等你的第一条词条。"
2. 降级：`source === 'fallback'` ⇒ "伙伴现在靠固定台词应答——到设置里给他绑一个模型就能真聊。"
3. 数量没长：`count < max` ⇒ "再添 N 条词条，大陆上就会多一位伙伴。"（把 ⑦ 的激励说出来）
4. 交换代价：见 §6.3 那句原话，**逐字用**，不许改写成"消耗一张卡"。

## 8. 验收判据

1. **零迁移可证**：`git diff` 不含 `migrations-list-*.ts`；`study_task`/`chest_open`/`app_settings`
   三张既有表承担全部新状态。
2. 同库两次 `GET /api/npc` ⇒ 伙伴的 `id`/`row`/`col`/`name` **逐字段相同**（确定性派生）。
3. 词条数 8→9 时 `npcCountFor` 不变、16 时 +1（边界用例）；上限到 6 封顶。
4. 把某条 due 词的怪**答对** ⇒ 原本遇险的伙伴消失遇险标记、对应 `npc_rescue` 单翻 done
   且 `chest_keys.earned_keys` +1（同事务，判据对账 SQL 可查）。
5. 求救单幂等：连跑两次 `dispatchTasks` ⇒ `npc_rescue` 行数增 0。
6. 交换：信物 `cards=1` ⇒ 409；`cards>=2` 且同领域有可抽词 ⇒ 落一行 `chest_open`（`source_kind='npc'`）
   + 返回一条**库里没有**的词；当天换满 2 次后第三次 ⇒ 409（`opened_day` 日闸门实测）。
7. 交换出的词收下后，`drawablePool` 里它**不在**（`pool_slug` 去重生效），且卡墙显示它 ★1。
8. 无 key 环境 `POST /:id/talk` ⇒ `200` + `source='fallback'`，**不 5xx、不空串**。
9. `ownerId = null` 走 `ownerForWrite` ⇒ 只看无主行；`npc_rescue`/交换都不得串到别人。
10. `npm run check` 四连全绿；3 个新测试文件逐条登记进 `docs/dev/test-plan.md` §3。

## 9. 不做什么（登记不欠账）

- **不做伙伴的等级/亲密度/好感度养成**（那需要新账本，破 §0 红线；要做得单独立册）。
- **不做伙伴代答/代复习**（边界③）。
- **不做伙伴之间的互动与对话**（NPC↔NPC 是另一个量级的系统）。
- **不做语音**（`TERM-CARDS-SPEC` §9 的合成音效已覆盖"有声"的最小面）。
- **不改 hero 区与对外文案的既有闸门**（项目内存红线：「概念图」承诺禁入对外文案）。
- **不给 `chest_open` 加 `npc_id` 列**（§6.3 已用 `source_kind` + `opened_day` 达成闸门；
  加列就要迁移，破 §0）。
