## 1. 为什么不是「把现有 pk 搬上线」（三个决定性约束）

### 1.1 运行时不兼容（硬约束）

现有 server 是 **Express + better-sqlite3**，这两者在 Cloudflare Workers 上**一行都跑不了**。
Workers 没有 Node 原生模块、没有文件系统、没有长驻进程。

### 1.2 「点链接就能用」与「双人对战」本质冲突（反直觉，本方案的分水岭）

访客是**一个人**点开链接的。双人对战给他的第一个画面是「等待对手加入」——
他不会去找第二个人，演示当场归零。

而 **PVE（单人 vs AI）刚好能无状态化**：状态机搬到浏览器，Workers 只做三个无状态函数
（出题 / 判分 / AI 作答）⇒ 不需要 Durable Objects、不需要 SSE、不需要持久化，**完美落免费档**。

### 1.3 P0-4 在途，此刻 fork 必漂移

实测（2026-09-16 读码取证，不信文档自述）：

| 项 | 实测结论 |
|----|---------|
| P0-4 公共题 | ❌ 未落地 —— `shared/src/pk.ts:143` 仍是 `toUserId`，**无 `attempts[]`** |
| P0-5 理解题 + 0~3 判分 | ❌ 零实现 —— 无 `comp/answer`、无 `comprehension` 题种 |
| `pk/judge.ts`（258 行） | ⚠️ 只有 P0-7 那 4 个能力，**没有理解题判分 rubric** |
| PVE 人机对战 | ✅ 完整可用（`mode='pve'` 建房即占 AI 座位） |
| `pk/room.ts` / `pk/match.ts` | **395/400、394/400 行**，且正被 P0-4 改动 |

⇒ 双人对战要上 CF，需用 Durable Objects 重实现 `room.ts` + `match.ts`（`setAlarm` 替 ticker、
WebSocket 替 SSE、SQLite 替内存 Map）；而这两个文件正是 P0-4 的改造对象 —— 现在 fork 一份，
做完即过期。**故双人整体推到阶段二**（§7）。

### 1.4 附：1 核 VPS 其实够用（纠正前提，供阶段二参考）

老板排除 VPS 的理由是「只有 1 核」。该负载实为**单进程 Node + 内存 Map + sqlite**，
局域网 demo 级别，1 核撑数百并发无压力 —— **当初排除 VPS 的前提不成立**。
阶段二若 DO 重写过重，「VPS + Docker 直接跑现有代码（零改动）」反而更省。
届时再算，本阶段不纠结。

## 2. 阶段一范围（最小演示集）

### 2.1 保留（核心亮点，一个都不能少）

| 项 | 说明 |
|----|------|
| 昵称登录 | 简化，去掉 mock openid；登录态存 localStorage |
| 选主题 | **单主题**，不做轮转（轮转是两人玩法，单人无意义） |
| 出题 | 提示词 → AI 出一道四选一选择题 |
| **公共题** | 人和 AI **都答同一道题**（演示版新写，不受现有 `toUserId` 结构拖累） |
| 判分 + 即时反馈 | `PkVerdict` 对错动画（已有组件） |
| 计分三条 | 出题 **+1** ／ 答对 **+2** ／ 答错或超时 **−1** |
| 对局时钟 + 结算 | `PkResult` 结算面板弹入（已有组件） |

### 2.2 砍掉（锦上添花，都不影响「演亮点」）

| 砍掉的项 | 理由 |
|---------|------|
| **房间 / 建房码 / 入房** | 单人不需要 —— **最大的一处简化** |
| **SSE 实时同步** | 单人不需要 —— **第二大的简化**，顺带绕开 Workers 长连接问题 |
| 主题轮转、跑题校验、求助道具、二次机会 | 均为增强玩法，非亮点本体 |
| 理解题 + 0~3 判分 | 正式版本就未实现（P0-5），演示版不凭空发明 |
| 投降、对战历史、落库 | 单人局价值低，且落库要持久化 |
| 真机微信验收 | 演示版走公网普通浏览器，不走微信 X5 内核 |

## 3. 架构

### 3.1 分层

```
浏览器（Pages 静态页）
  ├─ 状态机（shared/pk-reducer.ts 纯函数，本地跑）
  ├─ 需要 AI 时才发请求 ──►  Workers（无状态，三个函数）
  │                            └─► Agnes API（RPM 20，硬约束）
  └─ AI 不可用时 ──────────►  预置题库（打包进静态资源，离线可用）
```

**Workers 上不存任何房间状态**。一局对战的全部状态在浏览器内存里，刷新即重开（可接受，
演示场景无「断点续局」需求）。

### 3.2 为什么状态机搬客户端

不是图省事，是**被运行时逼出来的唯一解**：Workers 免费档无长驻内存，
而 8 分钟一局的对战需要一个持续存在的状态机。放 DO 也能做，但那是重写（§1.3）。
放客户端则：零后端状态、零持久化、零冷启动问题、免费档绰绰有余。

### 3.3 `shared/pk-reducer.ts`（防漂移的核心，决策 ⑤）

- **纯函数、零 I/O**：输入 `(state, action) → state`，不碰网络、不碰时钟、不碰随机数。
- 承载：计分、答题超时判定、揭示时序、结算胜负。
- **正式版与演示版共用同一份**：正式版在 Express 里调它，演示版在浏览器里调它 ——
  规则只有一处，改计分时两边同步。★ 这是对现有命令式 `room.ts` + `match.ts` 的**重构**，
  属于本方案的**主要工作量**，也是唯一值得付的成本。

> ⚠️ 该 reducer 现阶段只覆盖 §2.1 的最小规则集，**不追求**覆盖正式版全部规则
> （主题轮转、道具等不在阶段一范围）。范围外规则待阶段二随双人一起收口。

## 4. 接口契约（Workers，三个无状态端点）

| 方法 | 路径 | 入参 | 出参 | 说明 |
|------|------|------|------|------|
| POST | `/api/demo/quiz` | `{ topic, prompt }` | `{ stem, options, answer, source }` | 出题。`source`: `'bank'`（预置题库）｜`'ai'`（Agnes） |
| POST | `/api/demo/answer` | `{ questionId, choice, answer }` | `{ correct, delta }` | 判分。**纯计算，不调模型**——答案由调用方回传 |
| POST | `/api/demo/ai-answer` | `{ stem, options }` | `{ choice, source }` | AI 对手作答。**只喂题干+选项，绝不喂答案** |

- **`answer` 端点不调模型**：选择题判分是字符串比对，Workers 内即可完成，
  省一次模型调用、也省掉 RPM 20 的额度消耗。
- **答案回传给服务端只为判分**：预置题库的答案本就在客户端，回传无泄露增量
  （演示版无防作弊需求，详见 §8 风险）。
- **AI 作答不喂答案**（沿用 PK-SPEC §8.3 的「AI 无特权」口径）：否则 AI 必答对，人机对战失去意义。

### 4.1 错误码

| 码 | 含义 | 前端行为 |
|----|------|---------|
| 429 | 额度/频率超限 | **静默回落预置题库**，不提示（§5.3） |
| 502 | Agnes 不可用 | **静默回落预置题库** |
| 400 | 入参不合法 | 如实提示（开发期问题，不该在生产出现） |

## 5. Agnes 集成与降级

### 5.1 key 只存 Workers 环境变量

**绝不出现在前端**。默认 key 一旦进浏览器，F12 即可取走，RPM 20 的额度几秒刷光，
且是老板账号被滥用 —— 这是本方案**唯一不可妥协**的一条。
访客填自己的 key 时，key 只存 `localStorage`，**不落服务端**。

### 5.2 RPM 20 是硬约束（不是"大概够用"）

Agnes 免费档 **20 次/分钟**（另有每 5 小时 1500 次 / 每周 15000 次）。
⇒ Workers 侧做**全局令牌桶**（不是按 IP）：总量卡在 20 请求/分钟以内。

### 5.3 降级的正确行为：静默回落，不报错

限流或 Agnes 失败时，**不弹"请求过于频繁"**，而是**静默切到预置题库**继续出下一题。
访客感觉不到中断，演示永不翻车。

> 这是本方案「能不能用」的分水岭。弹错误提示 = 演示翻车；静默降级 = 演示永远能打完。
> 省下的那点"如实告知"，远不如"局能打完"重要。

### 5.4 待核实项（动手前必须落地，不许带疑点开工）

- [ ] `platform.agnes-ai.com` 的**官方**额度与模型名（现有数字来自第三方聚合资料，非官方文档）
- [ ] 是否真为 OpenAI 兼容（`/v1/chat/completions`）、鉴权头格式
- [ ] 是否支持流式（演示版可不用流式，但影响超时设置）

## 8. 风险与未决（诚实记账）

| 风险 | 说明 | 处置 |
|------|------|------|
