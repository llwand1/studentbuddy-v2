## 3. ★★ 部署闸门（M3 的前置清单——**这是「什么时候能上线」的答案**）

**M3 不是"跑个 docker compose"**。下面四类闸门**全部**满足才能上线；缺任何一条，
上线后的症状都不是"功能少一点"，而是**全站不可用或静默烧钱**。

### 3.1 代码闸门（必须在仓库里改完——**当前全部未做**）

| # | 项 | 不改的症状 | 位置 |
|---|---|---|---|
| 1 | **`trust proxy` + Caddy 下发 `X-Forwarded-For`** | `req.ip` 恒为反代自身地址 ⇒ **全站共用一个 IP 桶** ⇒ `send-code` 的 register 桶（5/小时）与 login 桶（20/小时）**同时退化成全站上限**：100 个用户抢 20 个名额，其余全 429 | `routes/auth.ts` 的 `clientIp`（代码侧现场证据已写在注释里）；`AUTH-SPEC` §4.6 末段 |
| 2 | **`ALLOWED_ORIGINS` 从硬编码改为可配** | 现为**硬编码的 localhost Set** ⇒ 浏览器带 `Origin: https://<域名>` 时**所有 POST 一律 403** ⇒ **全站瘫痪**（登录、发码、出题、打卡全挂） | `security.ts:7` |
| 3 | **`HOST` 从 `'127.0.0.1'` 改为可配** | 容器内只监听回环 ⇒ Caddy 连不上后端（**本机开发无感，上线即挂**） | `index.ts:37` |
| 4 | **`SB_COOKIE_SECURE=1`** | HTTPS 站点下发非 Secure cookie ⇒ 会话可被明文链路截获 | `auth/middleware.ts` |
| 5 | **`SB_REQUIRE_AUTH=1`**（＝ M2 收口） | 不强制鉴权 ⇒ 任何人可读写全站数据 | `AUTH-SPEC` §3 |

### 3.2 配置闸门（部署时必须逐项验在位，不是"配了就算"）

| # | 项 | 误配的症状 |
|---|---|---|
| 1 | `RESEND_API_KEY` **与** `SB_MAIL_FROM` **两个都配齐** | 只配一个 ⇒ 走**控制台兜底**（只打日志不真发信）⇒ **「点了发送、界面说成功、邮箱里永远没有」**，服务端零错误、日志里也看不出异常——**最难查的一类故障** |
| 2 | `SB_DATA_DIR` 指向**持久卷** | 容器重建即丢全部数据 |
| 3 | `SB_PORT` / 反代目标端口一致 | Caddy 502 |
| 4 | **`SB_UPSTREAM_SITE_MAX_CONCURRENT`（全站免费通道并发封顶 N）按业务值配**；队列上限 `SB_UPSTREAM_SITE_QUEUE_MAX`（缺省 20） | 沿用**占位值 8** 上线 ⇒ 全站免费通道只允许 8 路并发，用户一多就收到「当前免费通道繁忙，请稍后再试」。★ 但**不配不会静默出错**（有队列上限兜底、会**明确拒绝**而不是卡死），比上面三条轻——**N 的具体数值待老板给值**（`TENANCY-SPEC` §8.1.3.1） |

## 4. ★ 汇报纪律（老板 2026-09-18 指令，**本文档存在的理由**）

> **老板原话**：「每次完成一个"上线"这个规划的小任务时，你就汇报一次总体进展情况，
> 这个你要存进记忆也要录入"上线"的相关文档中」。

⇒ 固化为三条：

1. **触发点**：完成一个**上线阶梯**（§2 表）里的批次时——**不是**完成每个 commit、也不是产品功能里程碑。
2. **汇报内容**（缺一不可）：① 本批做完了什么 + **实测证据**；② **总体进展**（§2 表里到哪了 / 还剩几批）；③ **离上线还差什么**（§3 四类闸门里哪些已满足）；④ 下一步与阻塞项。
3. **落盘**：同一次动作里**同时**更新 §2 状态 + 在 §5 追加一条汇报；并写入 `AGENTS.md` / `CHANGELOG.md` / `test-plan.md` 的常规登记面。

★ 这条纪律与 `AUTH-SPEC §7` 的关系：§7 是**计划**（要做什么），§5 是**台账**（做到哪了）。改计划去 §7，记进展来 §5。

## 5. 进展汇报（按时间倒序，**只追加**）

### 2026-09-18 23:20 — 第 4 次总体进展汇报

**本批（刚完成）**：**M2d-1 设置与反馈环归主** —— `app_settings` / `daily_activity` / `daily_summaries` / `user_stats` 四张「**约束会跨用户撞键**」的表随**迁移 v30** 重建。**代码与文档已完成并过测，尚未提交**。

- **这一批解决了什么**：这四张表改前**全是全局表**，而且**没有一条是"只是有点脏"，每一条都是别人能改到你**：`app_settings` 是**全局写口**（A 改出题配比／回答方式／配图开关／搜索 key，**全站所有人跟着变**）、`user_stats` 里存 `xp`（**A 和 B 的 XP 是同一个数**）、`daily_summaries` 的 `PK(day)`（**B 直接读到 A 的今日总结**）、`daily_activity` 的 `PK(day,type)`（**A、B 同一天聊天直接撞主键**）。
- **判据不是习惯，是约束本身**（本批定的可复用口径）：一张表若它的 `PRIMARY KEY` / `UNIQUE` **包含一个全局取值列**（`key` / `name` / `day` / `(term, domain)`），它天然只允许「全站一条」⇒ 多用户必然互撞 ⇒ **必须重建**；主键是 uuid 的 ⇒ **加列即可**。
- **★★ 归属值取 `''`（无主 = 谁都看不见），不是 `NULL`**——与 M2c 的 `providers`/`role_bindings` **刻意相反**（那里的 `NULL` = **平台通道 = 所有人可见**，因为免费额度是给全体用户用的）。同一个「没有主人」的处境，两组表的**可见性相反** ⇒ 取值必须不同。★ 若图省事统一，某个通用过滤函数会把「孤儿不可见」**静默变成「全站可见」**（反向泄露）。
- **★★ 本批最关键的一处纠正（读写两侧同口径）**：初稿按 `ownerFilter` 的「`null` 就不加条件」写读侧，开工时发现这四张表的读形状是**单值或聚合**（`SELECT value … .get()` 与 `SUM(count)`）⇒ 豁免过滤后库里多行时 `.get()` 会返回**任意一行**，未登录请求读到**某个用户**的设置/总结/XP（**静默串台**）。⇒ 全部改成 `ownerForWrite(ownerId)`。**判据一句话：读形状是「一批行」的用 `ownerFilter`（`sessions`/`user_memory`），是「一个值」的用 `ownerForWrite`**。
