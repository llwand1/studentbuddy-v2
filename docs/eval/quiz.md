> 口径定义**全部内联在本文件 §1**，不依赖仓外文档 ｜ **批次 A**：零裁判、零人工标注，只算机器可判的结构化指标。

## 1. 这套件量什么

两个 arm 各自独立跑，**两档的数永不合并成一个**（开不开配图是两种条件，合并就会出现「留图率里掺着关图的组」）：

| arm | 自变量 | 用来回答 |
| --- | --- | --- |
| `base` | 配图开关＝**关** | 纯出题链本身稳不稳（一次成型、满配、字段齐全） |
| `img` | 配图开关＝**开** | 模型画不画图（产图率）、画了留没留下（留图率）、以及**开图对前者的代价** |

| 指标 | 口径 | 分子 / 分母 |
| --- | --- | --- |
| 成功率 | 这组对用户可用＝至少交付 1 题 | 有交付的组 / 全部组 |
| **完美出题率** | 一次成型 **∧** 满配交付（本轮需求要把这两件事合起来看） | 完美组 / 全部组 |
| 一次成型率 | 模型**第一遍**写的 JSON 原样就能 `JSON.parse` | `strict` 组 / 全部组 |
| 满配率 | 按题型出齐（产品的 `matched` 且实收＝请求） | 出齐的组 / **有交付的组** |
| 题级交付率 | 一道一道数 | Σ交付题 / Σ请求题 |
| 字段齐全率 | 解析＋体检全过 | 完整题 / 交付题 |
| 产图率 | 交付里带图的题占比 | 交付带图题 / 交付题 |
| **留图率** | 模型画了几张，最后几张到了用户眼前 | 交付带图题 / 模型在原文里画出的图 |

**这批的数与评测契约那张表怎么对上**（★ 两句前置：⑴ 那份契约文档**此刻还没进本分支所在的历史**，所以下表把判据逐条抄了下来、本文件可独立读；⑵ 契约里**没有**「批次 A／批次 B」这两个名字，那是本报告为出题套件拆的实施顺序；A＝零裁判能算的，B＝要裁判的）：

| 契约首版判据（逐条抄录） | 本批 | 落在哪个指标 |
| --- | --- | --- |
| 交付率 `delivered/requested`（把 `QuizMixReport`＋`QuizImageReport` 归并） | ✅ 量了 | 成功率（组）／满配率（组）／题级交付率（题）——★ 刻意**不合成一个「交付率」**，三个分母不同义，合成一个数就会有人在错的层上读它 |
| 重复率 ≤ 3% | ✅ 量了 | 组内重复题数（两 arm 皆 0 ⇒ 过判据，见 §5.1 P6） |
| 答案正确率 ≥ 95%／歧义率 ≤ 5%／依据率 ≥ 90%／干扰项质量 ≥ 2.3／难度吻合 | ⛔ 批次 B | 五行全要裁判＋人工校准（先要人工一致性 κ ≥ 0.6 那道闸），本机单服务商此刻满足不了「裁判与出题不同家」 |
| 实验 Q1（生成→验证流水线的 A/B 对照） | ⛔ 未做 | 它的判据是「答案正确率提升 ≥5pt」，而正确率本身在批次 B ⇒ 本批只留下了 `arm` 这个对照机制（当前两 arm 的自变量是配图开关，不是验证层） |
| **契约表里没有、本轮需求点名的四项** | ✅ 量了 | **一次成型率／完美出题率（＝一次成型 ∧ 满配）／产图率／留图率**——★ 引用时别说成契约原文，它们是本批新增口径，判据线（成功率 <95%、完美 <50%、留图 <70% 就不该往下走）也来自本轮 §3，不在契约里 |

**⚠️ 评测契约的「可复现纪律」要求报告头固定写七项，本批只写了三项**：数据集版本／被测模型／组数与时刻 ✅，★ **缺 git sha／温度／随机种子／总成本**四项（`tools/eval/reports/*.json` 里也没有这些字段——录制件按「gitignore 原始输出」那条纪律处理，仓内只剩读数）。温度与 `max_tokens` 走的是产品参数、评测台不改，所以读数**是**「产品当时那一档」而非「可复算的那一档」；本机是免费档 ⇒ 成本本可以记 0 并注明，但脚本没这一行就是没有。⇒ 记为批次 B 之前必须补的第一件事（补法＝`run.mts` 收尾时把 `git rev-parse HEAD`／请求体里的温度／`platform_usage` 同口径成本一并写进报告头，`render.mts` 的标记区块随之多四行）。

三个刻意的设计（改之前先读，不然会误读数字）：

1. **一次出组分四档**：`strict`（原样合法）／`repaired`（靠无损修复：漏括号、漏转义）／`rescued`（靠抢救：剥 svg 值、截断逐题回退）／`failed`（整组没解出＝用户看到的 502）。
   与产品事件流水线自己的 `parseTier 1..4` **不同源**——那边把 `strict` 与 `repaired` 合成一档。
   本口径拆开是因为：模型写没写合法 JSON 是**出题质量**，修复器有多能干是**工程韧性**，混进一个数就没人知道该改提示词还是该改解析器。
2. **量不到记 `—（无分母）`，不记 0%**：`rescued` 的组原文已经解不出，「模型画了几张图」这件事根本无从得知，`svgInRaw` 记 `null` 并**退出分母**。当成 0 会虚增留图率（分子分母都不加），当成没发生会虚减。
3. **传输层失败单独计数**：429／超时／连不上是 `transportErrors`，与「模型答得差」分开。补跑过几次如实记进 `attempts`，**绝不静默丢失败组**（丢了分母就变小、成功率虚高）。

## 2. 怎么跑

```bash
npm run eval -- quiz --limit 3 --arms base   # 冒烟（3 次真调）
npm run eval -- quiz                         # 全套：18 词条 × 2 arm ＝ 36 次真调
npm run eval -- quiz --replay <reports/quiz-*.json>   # 零额度离线重算（CI 口径回归闸用这条）
```

- 真调走**产品自己的链**：`generateBlendedQuiz` → `generateQuiz`，温度与 `max_tokens` 都是产品参数，评测台一行不改（`tools/eval/runners/quiz.mts` 头注）。
- 模型侧挂一个**录制转发代理**：一次成型率量的是模型第一遍写的原文，产品返回值里这段已被解析阶梯消化掉了。
- 凭据纪律：真实库以 `readonly` 打开，只把 `enc:v1:` **密文**抄进临时库，解密仍走产品的 crypto；`Authorization` 头不落盘也不打印。
- ⚠️ 录制件与报告落 `tools/eval/reports/`，该目录**已 `.gitignore`**（同 `coverage/` 的道理＝入库就是把「采集时刻的旧数字」留在树里误导人，可对外的读数落 `docs/eval/`）。**代价照实写**：§4 那些数只能在有这份录制件的机器上 `--replay` 复算，clone 仓库的人拿到的是读数、不是模型原文；所以「CI 靠仓内产物跑零成本口径回归闸」这一条**现在不成立**，要成立得先决定录制件进不进仓（另一个办法是把脱敏后的最小复算夹具提交，本批没做）。
- 免费档 250 次/5 小时、且本仓**没有退避重试**，所以真调之间默认节流 1.2s、传输失败最多补跑 1 次。

## 7. 本批**不量**什么（免得这块看着像全了）

- **答案正确率、考点忠实度、歧义率**：需要裁判模型＋人工校准（评测契约对这两件事的纪律＝裁判与出题**必须不同源**、且先做人工一致性 κ ≥ 0.6 的校准）。
  本机现状是单服务商（agnes 一系），「换厂商做裁判」这条根本满足不了，硬上就是自己给自己背书。
- **数据集真实性**：`terms-v1.json` 的 `provenance` 是 `dev-hand`——18 段材料全部开发侧手写。
  同侪的检索评测台撞过同一种偏差（手写语料的成绩明显好于真料快照，具体读数在那一侧、尚未进本历史），所以本批**只报机器可判的结构化指标**。
- **题量对齐**：契约定的首轮规模是 60 词条 ≈ 300 题；本轮按需求点名的「100 道题」跑 18 × 6 ＝ **108 题**。补齐只增行、不改已有条目（改条目＝升 v2，旧报告才保住可比性）。
- **情景题档**（`scenario`）走独立引擎，属评测契约的另一套件；本套件配比里它恒为 0。
