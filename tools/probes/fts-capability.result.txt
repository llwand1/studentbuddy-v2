=== 5. 三个陷阱：为什么实现里那几行"看起来多余" ===
  MATCH ''    → ERR: fts5: syntax error near ""
  MATCH '   ' → ERR: fts5: syntax error near ""
  MATCH '""'  → 0
  ✓ ★ 空 MATCH 是**语法错误**（旧说法「会匹配全表」不成立）⇒ 不短路就是「敲几个空格 → 500」
  ✓ ★ 纯空白串同样报错 ⇒ 短路必须发生在 trim 之后、SQL 之前
  ✓ 空字符串字面量 `""` 返回 0 行（不报错，也不匹配全表）
  MATCH '牛顿' → 1；MATCH '-牛顿' → ERR: no such column: 牛顿
  MATCH '牛顿 NOT 闭包' → 1（二元 NOT 可用）；MATCH 'NOT 牛顿' → ERR: fts5: syntax error near "NOT"（前缀 NOT 不可用）
  ✓ ★ 未转义的 `-牛顿` 是**报错**（no such column），不是静默语义反转
  ✓ ★ fts5 的 NOT **只能做二元运算符**，没有 `-term` 前缀简写
  MATCH '"-牛顿"' → 1 行
  ✓ ★ 转义只解决**语法错误**，不改变分词结果——引号内的 `-` 被分词器当分隔符丢掉、`牛顿` 照样命中
  ⇒ 故本函数的定位是"**防 500 的护栏**"，不是"精确字面量匹配"。
    真正决定"查什么"的是 `tokenizeForFts`（它才是两侧共用的那一份）。
  MATCH 'c++'     → ERR: fts5: syntax error near "+"；MATCH '"c++"' → 0
  ✓ ★ 未转义的 `c++` 直接语法报错 ⇒ 词元必须包成双引号字面量
  ✓ 转义后不报错（0 行，库里无该词元）
