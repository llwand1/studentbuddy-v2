> 累计每三次都失败则扣一分，并且裁判 ai 会给你一些建议（出题的选型 + 相关知识）」「引入道具功能…求助 ai 的道具，
> 每局每个玩家只有一个…ai 裁判会当场联网搜索，然后给你建议，以及进行知识输出」「对于对战中玩家的错题…
> 获得现场解析，之后 ai 裁判会根据同一个主题再出一道类似的题目，如果这次作对，那么也能够加两分，然后有 3 分钟 cd」。
> ⑬ **两个主题、按轮交替**：双方各选一个主题，**每一轮只能用当轮主题的题**；轮次归属由服务端
>    `currentTopic` / `topicOwnerId` / `topicTurn` 三字段定，**前端不参与裁决**（防改包）。
> ⑭ **跑题 = 出题失败，不是作弊**：不贴合 → 422 `TOPIC_MISMATCH`，**不扣题、不占 CD**（可立刻重出），
>    只累计 `failStreak`；**连败满 3 次才 −1** 并由裁判给出题选型与相关知识。
>    ⇒ 判据是「失败要付代价、但代价是次数不是节奏」——罚 CD 会让跑题变成「罚站」，与「鼓励出题」的动机相反。
> ⑮ **求助道具**：每人每局 **1 次**（`helpLeft`），用完为止；裁判**当场联网搜索**后给建议 + 知识输出，
>    **★ 硬规则：求助输出绝不含本题答案**（答案一旦可求，PK 的判分就失去意义）。
> ⑯ **二次机会**：只能选**自己的错题**，先拿现场解析，再由裁判按**同一主题**出一道相似题；
>    答对 **+2**，**原来的 −1 保留**（**净 +1**）——不给「答错无代价」，否则错题可以靠补救刷回满分。
> ⑰ **3 分钟 CD**（`RETRY_CD_MS`）按玩家计，防止把「二次机会」当成常规答题通道连刷。
> ⑱ **裁判是旁挂能力，不是主路径依赖**（ADR-4 的具体化）：裁判模型未配/调用失败/输出不合法 ⇒
>    **一律放行**（跑题校验跳过、道具**不扣次数**、二次机会返回 502 且不计 CD）。
>    理由：裁判一挂就玩不了，是把「可选增强」做成了「单点故障」。

## 1. 玩法规则（计分唯一事实源）

一局 PK = 固定时长（默认 **8 分钟**，服务端可配）内的双向对抗。双方**同时**拥有两个动作：
**出题**（写提示词 → AI 出一道**公共题**）与**答题**（答**每一道**公共题）。

★★ **公共题（2026-09-13 改判，决策 ⑦）**：一道题**双方都要答**——
出题人答自己出的题（**+1**），对手答这道题（**+2**）。出题人信息优势最大，故分值最低。
原口径「出题人自己不答这道题」（§3）**已作废**：那条是为防「出题人泄题」写的，但代价是出题人
对自己的题毫无参与感、也拿不到除出题奖励外的任何分；改判后的动机方向依然成立——**难倒对手才划算**，
而答对自己的题只有 1 分，不足以让人靠出简单题刷分。

| 动作 | 分值 | 约束 |
|------|------|------|
| 成功出 1 题 | **+1** | 服务端强制 CD：同一玩家两次成功出题间隔 ≥ `QUIZ_CD_MS`（默认 60s）；CD 内提交 → 429，不扣分 |
| **答对自己出的题** | **+1** | 公共题新增（⑦⑧）。出题人也要答自己的题；信息优势最大 ⇒ 分值最低 |
| **答对对手出的题** | **+2** | 即原「答对 1 题 +2」。服务端判分（选择题：选项比对，毫秒级计时） |
| 答错 1 题 | **−1** | 判分即结算，无申诉 |
| 答题超时 | **−1** | 超过 `ANSWER_TIME_MS`（默认 45s）未提交，服务端自动判超时；之后该题作废不可再答 |
| 怠慢（长时间不出题） | **−1 / 次** | 对局进行中，每 `IDLE_PENALTY_MS`（默认 120s）内无一次**成功**出题提交（CD 中提交被拒不算，重试不算），扣 1 分，可累计 |
| **理解题判分** | **0 ~ 3** | 裁判 AI 出题 + 判分（§9）；**计入同一总分**（⑩），不是独立赛道 |
| **出题跑题连败 3 次** | **−1** | P0-7（§11.2，⑭）：单题跑题**不扣分**，只累计 `failStreak`；满 3 次才 −1 且 `failStreak` 归零重数 |
| **补救题（二次机会）答对** | **+2** | P0-7（§11.4，⑯）：**原错题的 −1 保留** ⇒ 净 +1；3 分钟 CD 内不可再请求（⑰） |

- **分数可为负**（增加紧张感，不设下限）。
- **结算**：对局时钟归零 → 分高者胜；平分比正确率（答对数），再平判为平局。
  ★ 理解分按 ⑩ **已计入 `score`**，故结算规则**零改动**——这是「计入同一总分」相对「单列赛道」的
  唯一好处：不必发明一套双维度比较（总分 → 理解分 → 正确率）并为此改结算、改前端、改测试。
- 所有计时（CD / 答题时限 / 怠慢惩罚 / 对局时钟 / 理解题出题节拍）**全部在服务端**，客户端时间只作展示。
- **正确答案永不下发给答题方**（含 SSE 事件），直到该题**被揭示**——揭示时序见 §1.2。

### 1.1 一道题的生命周期

```
出题（写提示词） → 生成公共题 → 双方各自作答（各自独立计时，同一 deadlineAt）
                                        ↓
                        双方都提交 / 都超时 / 一方已交一方超时
                                        ↓
                                揭示（答案 + 双方结果公开）
```

- 每道题**双方各有一份作答记录**（§2 `PkAttempt`）。`deadlineAt` 对双方相同（自 `createdAt` 起算），
  但两份作答各自先到或超时，故 `revealed` 在**最后一份落定后**才置真。
- **出题人也答自己的题，且出题与作答并行**——不必等对手先答。串行化会把 CD 与怠慢惩罚的节奏拖死。
- PVE 下 AI 出题后**AI 也答自己的题**；公平性残留风险见 §8.5（已知并接受，记录在案）。

### 1.2 揭示时序与私有反馈（决策 ⑨⑫ 的落地；**本批最容易做错的一处**）

一道题两人都答，若沿用「谁提交谁立刻判分 + 广播」，会同时踩两个洞：

1. **答案泄露**：先答方一提交，后答方就从 SSE 拿到正确答案 ⇒ 等于送分。
2. **无法定向**：本仓 `chat/sse-bus.ts` **没有按订阅者裁剪的能力**，而双方订阅的是同一个
   `pk:<roomId>` 频道 ⇒ **任何进 SSE 的字段双方都看得见**（⑫ 实测，见 §2.2）。

故定死三条：

| 规矩 | 内容 |
|------|------|
| **私有反馈走 REST** | `POST /answer`（选择题）与 `POST /comp/answer`（理解题）的**响应体**回本人 `{ correct, score, delta, reason }`。这是「本人提交后立即知道对错」的**唯一**通道 |
| **SSE 只播公开事实** | 提交只播「某人对某题已提交」（`pk-attempt`，**不含**对错、不含选择）；揭示时才播答案与双方结果（`pk-verdict`） |
| **揭示前不播本题分数** | 未揭示题的分数变化**不进** SSE 快照 ⇒「对手答对了」这条信息不会提前泄漏。<br>**代价（已知并接受）**：本人**刷新页面**后，未揭示的题看不到自己刚答的对错（前端把 REST 回执缓存在内存，刷新即丢），下一次揭示会补齐 |

> **为什么不改造 sse-bus 支持定向推送**：那会动到聊天主链路的公共实现（R1 红线：一个模块一个工作面，
> 且该文件有其他会话在途），而收益只是省一次 REST 回执；REST 回执天然点对点，比在广播通道上加白名单更不易错。
- **常量归属**：P0-1 登记 `PK_MATCH_MS`（8 分钟）／`PK_MAX_PLAYERS`／`PK_ROOM_CODE_LEN`／`PK_ROOM_TTL_MS`／
  `PK_FINISHED_KEEP_MS`；**P0-2 已补登记** `QUIZ_CD_MS`（60s）／`ANSWER_TIME_MS`（45s）／`IDLE_PENALTY_MS`（120s）／
  `PK_PROMPT_MAX`（300）＋ PVE 三常量 `AI_USER_PREFIX`（`'ai-'`）／`AI_FIRST_QUIZ_DELAY_MS`（5s）／`AI_RETRY_DELAY_MS`（10s），
  全在 `shared/src/pk.ts`（§8）。**P0-5 待补登记**（理解题与裁判，§9）：`COMP_INTERVAL_MS`（180s，每 3 分钟一道）／
  `COMP_ANSWER_MIN`（作答最少字数，少于则不送判分、直接 0 分）／`COMP_ANSWER_MAX`（作答上限，服务端截断）／
  `COMP_SCORE_MAX`（3，档位上限）／`JUDGE_USER_ID`（裁判出题时 `fromUserId` 的固定值）。

## 2. 数据契约（先在 `packages/shared/src/pk.ts` 登记再实现）

```ts
/**
 * 一名玩家对某道题的作答（★★ 公共题：双方各一份，P0-4 起）。
 *
 * 公开 vs 私有的分界（§1.2，**最要紧的一条**）：
 * ① `status` / `submittedAt` 是**公开事实**——双方都要等对方，不知道在等谁就没法玩；
 * ② `chosen` / `text` / `correct` / `score` / `delta` / `reason` 是**私有结果**，
 *    只在 `PkQuestion.revealed === true` 之后才出现在**任何**载荷里。
 */
interface PkAttempt {
  userId: string;
  status: 'pending' | 'submitted' | 'timeout';
  submittedAt?: number;       // 公开：前端据此显示「对手已交卷 / 等待对手」
  // ── 以下字段仅 revealed=true 后出现（揭示前连键都没有，不给手滑留口子）──
  chosen?: number;            // single：所选选项下标
  text?: string;              // comprehension：作答原文（§9）
  correct?: boolean;          // single：判对否
  score?: number;             // comprehension：0~3 档理解分（§9.3）
  delta?: number;             // 本题对总分的净影响
  reason?: string;            // comprehension：裁判给的判分理由
}

/** 题目（公共题：**双方都答**；对答题方始终隐藏 answer，直到 revealed） */
interface PkQuestion {
  id: string;             // pq-<roomId>-<seq>
  roomId: string;
  /** single = AI 出的四选一（P0-4）；comprehension = 裁判 AI 出的理解题（P0-5，§9） */
  kind: 'single' | 'comprehension';
  /** 出题人：single = 玩家 userId 或 AI 座位 `ai-<roomId>`；comprehension = `JUDGE_USER_ID` */
  fromUserId: string;
  prompt: string;         // 出题提示词原文（≤300 字）；理解题存「本局主题」
  stem: string;           // 题干
  options: string[];      // single 4 项；comprehension 为**空数组**（无客观选项）
  createdAt: number;
  deadlineAt: number;     // createdAt + ANSWER_TIME_MS；**双方同一个**
  attempts: PkAttempt[];  // 公共题：双方各一份（长度 = 房内玩家数）
  /** 最后一份作答落定（都提交 / 都超时 / 一交一超）后置真；此时才揭示答案与双方结果 */
  revealed: boolean;
  answerRevealed?: number; // single 专用；revealed 之前连键都没有
}

/** 对局快照（GET state / SSE `pk-state` 载荷；**两者共用同一形状＝「公开版」**，§1.2） */
interface PkRoomState {
  roomId: string;
  roomCode: string;      // 6 位数字，入房凭证
  status: 'waiting' | 'active' | 'finished';
  mode: 'pvp' | 'pve';   // PVE 建房即占 AI 座位（§8）
  players: { userId: string; nickname: string; score: number;
             correct: number; answered: number; lastQuizAt: number }[];
  nextQuizAt: Record<string, number>;   // 各玩家 CD 解锁时刻
  endsAt: number;                       // 对局截止（active 时有效）
  questions: PkQuestion[];              // 公开版：answer 与未揭示的私有判定全部剥离
  aiTopic?: string;                     // PVE 可选主题方向
  /** 裁判 AI 的最近一条盘中短评（P0-5，§9.4）；无则不下发 */
  judgeNote?: PkJudgeNote;
  winner?: string;                      // finished 时（全平不下发）
}

/** 裁判盘中短评（P0-5，§9.4）：**只读服务端已有状态**组装，不额外调模型 */
interface PkJudgeNote {
  at: number;                                    // 产生时刻
  kind: 'idle' | 'streak' | 'comp' | 'lead';     // 触发来源，前端据此配色/去重
  text: string;                                  // 已组装好的一句话（服务端产生，前端不拼）
}
```

> ★ **快照只有「公开版」一种形状，REST 与 SSE 共用**（这是 P0-4 特意选的简化）：
> 若让 `GET /state` 按请求者裁剪、而 SSE 广播公开版，两个通道就会出现**同一份 state 两种形状**，
> 前端与测试都要按来源分支——那是比「刷新后看不到自己未揭示的对错」（§1.2 已接受的代价）更贵的坑。
> 私有结果的唯一通道是 REST 响应体（`POST /answer` / `POST /comp/answer`），见 §1.2。

### 2.1 REST 端点

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/pk/auth/login` | `{ nickname }` → `{ userId, openid, nickname }`。**P0 模拟实现**：userId=服务端生成，openid=`mock_<userId>`；**P1 替换为微信公众号网页授权**（oauth2 code→openid），**响应结构不变，前端零改动** |
| POST | `/api/pk/rooms` | `{ userId }` → `{ roomId, roomCode }`；每人同时只能有 1 个 waiting 房 |
| POST | `/api/pk/rooms/join` | `{ roomCode, userId }` → `{ roomId }`；满员/不存在 → 404/409 |
| POST | `/api/pk/rooms/:id/start` | `{ userId }`（房主）→ 双方在线即 `active`，`endsAt = now + MATCH_MS` |
| POST | `/api/pk/rooms/:id/quiz` | `{ userId, prompt }` → 服务端调 AI 出 **1 道公共选择题**（**双方都要答**）。CD 内 → 429；对局未开始/已结束 → 409。成功后出题人 +1。AI 失败可免费重试（不计 CD） |
| POST | `/api/pk/rooms/:id/answer` | `{ userId, questionId, choice }` → 判**本人那一份**作答。响应体 `{ correct, delta, score, revealed }` 是**本人即时反馈的唯一通道**（§1.2）。已答过/已超时 → 409；该题没有你的作答位 → 403 |
| POST | `/api/pk/rooms/:id/comp/answer` | **P0-5（契约已立、码未开）**：`{ userId, questionId, text }` → 裁判 AI 判 0~3 分，响应体 `{ score, delta, reason, revealed }`；`text` 去空白后短于 `COMP_ANSWER_MIN` → 400（**不送判分**，堵「用一个『嗯』骗 1 分」） |
| POST | `/api/pk/rooms/:id/topic` | **P0-7**：`{ userId, topic }` → 选/改自己的对战主题（**仅 waiting 期**，`TOPIC_MAX` 20 字，trim 后空 → 400 `TOPIC_INVALID`）。开局后改 → 409 |
| POST | `/api/pk/rooms/:id/help` | **P0-7**：`{ userId, questionId }` → 用掉**唯一一次**求助道具，裁判**当场联网检索**后回 `{ advice[], knowledge, refs[] }`（**不含答案**，⑮）。次数用尽 409 `HELP_EXHAUSTED`；裁判不可用 502 `JUDGE_UNAVAILABLE` **且不扣次数**（⑱） |
| POST | `/api/pk/rooms/:id/retry` | **P0-7**：`{ userId, questionId }` → 挑一道**自己的错题**要二次机会，回 `{ explanation, question }`（相似题，同源主题）。CD 内 429 `RETRY_ON_COOLDOWN`；非错题/别人的题 → 404 `RETRY_NO_TARGET` / `RETRY_NOT_YOURS`；裁判不可用 502 `JUDGE_UNAVAILABLE` 且不计 CD（⑱） |
| GET | `/api/pk/rooms/:id/state` | 全量快照（断线重连对齐用）。**与 SSE 共用「公开版」形状**，见 §2 末注 |
| GET | `/api/pk/stream?roomId=&userId=&since=` | SSE，见 §2.2 |

### 2.2 SSE 事件（复用 sse-bus，频道键 `pk:<roomId>`）

继承 sse-bus 全部机制（seq 单调去重 / since 增量回放 / 15s 心跳 / 断链回收），
但**与聊天会话频道严格隔离**（频道键前缀 `pk:`，不复用 sessionId 空间，防串台——v1 教训）。
新事件类型在 `packages/shared/src/sse-events.ts` 登记：

> ★★ **本通道没有「按订阅者定向」的能力**（2026-09-13 实测 `sse-bus.ts`：只有
> `subscribe(channel, res, since)` 与 `publish(channel, ev)`，载荷对频道内所有订阅者完全相同），
> 而 PK 双方订阅的就是同一个 `pk:<roomId>`。⇒ **凡进 SSE 的字段，双方都看得到**。
> 因此**私有判定结果一律走 REST 响应体**（§1.2），SSE 只承载「公开事实」。
> 改本条之前先想清楚：在广播通道上做定向，等价于把「谁能看什么」的责任交给客户端。

| type | 载荷 | 语义 |
|------|------|------|
| `pk-state` | PkRoomState（公开版） | 房间状态变化（开局/结束/玩家变动/揭示/裁判短评） |
| `pk-question` | PkQuestion（公开版） | 新**公共题**到达（双方都收；answer 与私有判定已剥离） |
| `pk-attempt` | questionId / userId / status | **P0-4 新增**：某人「已提交 / 已超时」。**公开事实，不含对错、不含所选**——双方据此知道在等谁（§1.1） |
| `pk-verdict` | questionId / answerRevealed / attempts[] | **语义改（P0-4）**：该题**已揭示**，此时才公开答案与双方结果。<br>~~原「某题判分结果，双方都收」~~ 的单方判分不再走这里——那会泄露答案（§1.2），改走 REST 响应体 |
| `pk-judge` | PkJudgeNote | **P0-5**：裁判 AI 盘中短评（只读已有状态，不额外调模型） |
| `pk-end` | winner / finalState | 结算 |

服务端定时器（对局时钟、答题超时、怠慢惩罚、CD 解锁）到期时**主动 publish 对应事件**，
不依赖客户端轮询。Android 微信 X5 内核对 EventSource 支持不稳，前端加**轮询兜底**
（SSE 断开 3 次重连失败后降级为每 2s GET state）。

## 7. 可行性与难度评估（老板自定义问题，2026-09-09 答）

**结论：能行。P0 难度 = 中低（2~3 个工作阶段可落地），P1 难度 = 中。**

- **为什么不难**：出题（quiz.ts+json-repair）、实时推送（sse-bus）、判分（选择题字符串比对）、

- **真正的硬点按序**：① **P1 微信授权资质**——个人主体申请不到已认证服务号，需借用主体或走

  不稳（已备轮询兜底）；④ 提示词注入（§3 已缓解，朋友间对战剩余风险可接受）。
- **玩法可行性自检**：计分闭环无死锁（双方 CD 内仍可答题，怠慢惩罚防摆烂，超时惩罚防拖局）；
  8 分钟局 + 60s 出题 CD ≈ 每人最多出 7 题，节奏成立。

## 8. PVE（人机对战，2026-09-13 与 P0-2 一体化落地）

老板 2026-09-12 拍板三口子：**与 P0-2 一体做**／**AI 与人完全同口径答题**／**人机对称出题**。
本节是 PVE 的契约条文；实现落点 `pk/ai-bot.ts`（对手）+ `pk/room.ts`（占座）+ `pk/match.ts`（共用计分）。

### 8.1 建房与占座

- `POST /rooms` 收 `mode: 'pvp' | 'pve'`（缺省 `pvp`）与可选 `aiTopic`（主题方向，截 50 字）。
- `mode='pve'` 时**建房即占掉第二个座位**，AI 座位 id = `ai-<roomId>`（`AI_USER_PREFIX`）——
  此后人再输码入房被「满员」挡下（409），不会挤进人机局；房主无需等人、**直接开局**
  （`startRoom` 时置 `aiNextQuizAt = now + AI_FIRST_QUIZ_DELAY_MS`）。
- AI 在 `players[]` 里就是一名**普通玩家**（同 score/correct/answered/lastQuizAt 字段），
  前端据 `isAiUserId()` 区分展示图标，**计分侧零特例**。

### 8.2 AI 出题（`runAiQuiz`）

- **触发**：`tickMatches` 的 1s ticker 见 `mode==='pve' && !aiBusy && now >= aiNextQuizAt` 即调，调前置 `aiBusy` 防重入。
- **时机**：开局后 **`AI_FIRST_QUIZ_DELAY_MS`（5s）** 出第一题；成功后与真人**同一条 CD**（`QUIZ_CD_MS` 60s）；
  失败不扣分、**`AI_RETRY_DELAY_MS`（10s）** 后重试（`scheduleNextAiQuiz(room, ok, now)` 二选一）。
- **主题**：建房指定 `aiTopic` 优先；否则 10 主题池轮换（科学常识/世界历史/地理/文学名著/信息技术/
  数学基础/生物/天文/语言文字/生活百科，起始下标随机）。
- **出题**：复用 `generateQuiz(topic, undefined, PK_QUIZ_MIX, ..., online=true)`（`PK_QUIZ_MIX` = 仅 1 道单选），
  取 `type==='single'` 的那道，走**与真人同一入口** `pushGeneratedQuestion`（成功 +1）。
  LLM 在途期间对局可能已结束——`room.status !== 'active'` 时不再收题。

### 8.3 AI 答题（`runAiAnswer`）

- **触发**：真人出题成功后调用（`submitQuiz` 内）。
- **无泄漏**：AI 走**独立 LLM 调用**（`routeRole('solver')`），上下文**只喂题干 + 选项**、答案不在其中——
  与真人拿到的信息面完全相同。
- **判分**：走**与真人同一入口** `submitAnswer`——答对 +2 / 答错 −1 / 超时 −1 全同人。
- **AI 无特权**（三条如实兜底，都是「宁可判罚也不作弊」）：
  1. 流式超过 `q.deadlineAt` 即放弃 → 交给 ticker 按超时判罚，**不占时限便宜**；
  2. `parseChoice` 解析不出选项（优先首个 A-D 字母，其次 0-3 数字）返回 `null` → **不乱猜**；
  3. `routeRole('solver')` 没配模型 → 直接不作答 → ticker 按超时判罚，**不静默造分**。

### 8.4 计分对称性（本节的唯一保证）

出题（+1、60s CD、失败免费重试）与答题（+2/−1/超时 −1）两条路径，AI 与真人**共用 `match.ts` 同一套导出函数**，
`pk/ai-bot.ts` **没有任何自己的计分逻辑**——这是「同口径」在代码层唯一的可验证保证，
也是回归锁 `routes/pk-pve.test.ts`（7 例）的断言对象。**P0-4 起此保证扩到三层**：AI 也要答**自己出的题**（§8.5），
走同一条 `submitAnswer`。

### 8.5 公共题下的 PVE 残留风险（P0-4 记录在案，**已知并接受**）

改动后 AI 出题 → AI 也要答自己的题（+1）。这条新增了 PVE 特有的不对称：

- 现有机制能挡住**直接读答案**（`runAiAnswer` 走独立 LLM 调用、只喂题干+选项，§8.3）；
- 但挡不住**「同一模型刚生成过这道题」的记忆效应**——AI 答自己出的题的正确率会显著高于它答人出的题。

**接受理由**：① 值 1 分，不改变"难倒对手更划算"的动机方向；② 不让 AI 答自己的题会让「公共题」
在人机局里名不副实（一边是公共题、一边是专属题，比多给 AI 1 分更糟）。
**若真机实测发现 AI 靠这条稳定刷分**（如连续 3 局 AI 自答题全对而人出题答题正确率明显更低），
再按「AI 对自己出的题不倒扣、但答对只 +0」处理——**留一个可调的档位，不现在发明规则**。

## 9. 理解题与裁判 AI（P0-5：契约已立、码未开）

### 9.1 「实时监测」落地成什么（决策 ⑪）

老板原话：「加一个裁判 ai，这个 ai 实时监测对战情况，然后负责理解题出题和打分」。
按字面做成「每秒观察」既是纯烧钱、也无实事可做，故定死为**三件实活**：

| 职责 | 落地 | 调模型？ |
|------|------|---------|
| **出理解题** | 每 `COMP_INTERVAL_MS`（180s）按本局主题出 1 道 | ✅ 一次 |
| **判分** | 收卷后按 0~3 档 rubric 打分并给出理由（理由下发到屏上） | ✅ 每份作答一次 |
| **盘中短评** | 关键事件推一条一句话短评（§9.4） | ❌ **只读已有状态，零额度成本** |

- **模型档位**：新增 `ModelRole = 'judge'`（`MODEL_ROLES` 第 6 项，label「裁判（理解题判分）」）。
  成本低——`MODEL_ROLES` 是数组驱动的（默认绑定 INSERT 与设置页渲染都遍历它），**不需要写迁移**。
  出题与判分**共用同一角色**：裁判的两种能力是一件事的两面（都要读懂题目与作答）。
- **主题来源**：PVE 取建房 `aiTopic`，否则沿用 §8.2 的 10 主题池（与本局 AI 出题同一个池）；
  PVP **没有建房主题** ⇒ 取本局**已出过题目的提示词**拼成主题摘要；一题都没有（开局 3 分钟内双方都没出题）
  ⇒ 退化为通用主题（「本局暂无主题，请就『学习方法与思维』出题」）。
  ★ 退化路径必须写死：**不能因为没主题就不出题**——那等于让摆烂方顺带取消了理解题。

### 9.2 出题节拍（收口在 `tickMatches`，不新起定时器）

- 起点 `room.startedAt`；首道在 `startedAt + COMP_INTERVAL_MS` 出。**不是开局就出**——开局 3 分钟内双方还在
  互出选择题，塞一道大题会打断节奏。
- `status==='active' && now >= compNextAt` ⇒ 出题，然后 `compNextAt += COMP_INTERVAL_MS`。
- **8 分钟局 ⇒ 第 3、6 分钟各一道**，理解分区间 0~6 分，足以改变胜负（决策 ⑩）。
- 出题失败（模型不可用/输出不合法）⇒ 不阻断对局（ADR-4）、`compNextAt` 照推不重试，
  但**屏上要如实说明**「本次理解题没出成」（ADR-5）——否则玩家以为裁判没上班。

### 9.3 0~3 档 rubric（判分唯一口径）

| 档 | 判定 | 说明 |
|----|------|------|
| **0** | 理解方向都不对 | 答非所问、概念用反、与题目无关 |
| **1** | 方向对但有偏差 | 抓到方向，但有事实性错误 / 关键概念张冠李戴 |
| **2** | 总体准确 | 无明显错误，说得对——但本质是**标准答案的复述** |
| **3** | **总体准确 ＋ 有原创性** | 满足 2 档的全部条件，**且**有自己的例子 / 类比 / 迁移 / 反例 |

- **3 档是「2 档 ∧ 原创性」的合取**，不是「比 2 档更详细」。提示词里必须写死
  「内容更详细但仍是复述 ⇒ 仍判 2 分」，否则模型会把「话多」当「原创」。
- **判分顺序三步**：先判方向（0 vs ≥1）→ 再判准确性（1 vs ≥2）→ 最后判原创性（2 vs 3）。
  写成三步而不是四个并列描述——并列描述在模型侧容易退化成「看心情给分」。
- 输出协议 `{"score":0|1|2|3,"reason":"…"}`（解析沿用 `parseQuizBlock` 的五级阶梯思路）；
  **score 越界/非整数 ⇒ 整份判分作废**，按 0 分记账 + 如实告知 + 记 `report.failure`。
  **宁可判低不判高**：裁判给错分比不给分更伤信任。
- **已知风险：LLM 主观打分不稳定**（同一答案两次可能不同档）。缓解：`temperature` 压到出题档水平（≤0.4）
  + 提示词给每档正反例。**本契约不承诺「同一答案永远同档」**——那做不到；只承诺「档位定义可解释、
  理由必须给」。真机验稳定性的方法写在 §6 P0-5 验收栏。

### 9.4 盘中短评（`PkJudgeNote`，四类，不按固定节拍刷屏）

| kind | 触发 | 文案模板 |
|------|------|---------|
| `idle` | 距上次成功出题 ≥ `IDLE_PENALTY_MS`（与怠慢惩罚**同一锚点**） | 「XX 已经 {n} 分钟没出题了」 |
| `streak` | 连错 ≥ 3 题 | 「XX 连续答错 {n} 题，建议换个思路」 |
| `comp` | 理解题判分完成 | 「理解题判分：XX {score}/3」+ 理由摘要 |
| `lead` | 分差 ≥ 5 且领先方易主 | 「XX 领先 {n} 分」 |

- **不调模型**：文案在服务端拼好（`text` 是成品，**前端不拼**），零额度成本、零延迟。
- **同类去重**：同一 `kind` 60s 内不重复推；快照里只留**最近一条**（`judgeNote` 是单值不是数组）。
- 短评**不是计分依据**，只是可读性补充——不看也不影响胜负。

### 9.5 理解题的作答与判分失败降级

- 自由文本，服务端截断到 `COMP_ANSWER_MAX`。
- **字数下限 `COMP_ANSWER_MIN`**：去空白后不足 ⇒ 400 且**不送判分**（堵「用一个『嗯』骗 1 分」）。
  为什么不给 0 分而是 400：0 分是「答了但不对」，不该与「没答」混为一谈。
- **理解题也是公共题**（双方各答一份）⇒ 完全复用 §1.1/§1.2 的作答与揭示机制，**不另写一套**。
  这正是 **P0-4 必须先做、顺序不能反**的原因。
- **判分失败**（模型不可用/输出不合法）：该份作答按 0 分记账并如实告知，
  **不阻断对局、不重试**（ADR-4 + 不静默）。
- **AI 也答理解题**（§8.4 同口径），走 `routeRole('solver')`，只喂题干、**不喂判分 rubric**
  （喂了等于告诉它评分标准＝作弊）；同样经裁判判 0~3 分进 AI 的 `score`。

## 11. P0-7 主题轮转 / 跑题校验 / 求助道具 / 二次机会（2026-09-13 老板点单，已落地）

### 11.1 主题轮转（⑬）

一局有**两个主题**：房主一个、对手一个，**按出题轮次交替**——每一轮只能用当轮主题的题。

| 字段 | 位置 | 语义 |
|------|------|------|
| `topic` | `PkPlayer` | 该玩家自己选的主题（≤ `TOPIC_MAX` 20 字，trim 后空 → 400 `TOPIC_INVALID`） |
| `currentTopic` | `PkRoomState` | **本轮**生效的主题；出题人必须出这个主题的题 |
| `topicOwnerId` | `PkRoomState` | 本轮主题归谁（前端据此显示「本轮：张三的历史」） |
| `topicTurn` | `PkRoomState` | 轮次序号，从 0 起；成功出 1 题 +1 |

- **选主题只在 waiting 期**（`POST /rooms/:id/topic`，开局后改 → 409）。建房时房主可顺带
  `POST /rooms { topic }`，对手入房后自行补选；**PVE 的 AI 座位没有主题 ⇒ 兜底 `PK_DEFAULT_AI_TOPIC`（`'通用知识'`）**。
- **双方都选完才能开局**：任一玩家 `topic` 为空 ⇒ `start` 返 409 `TOPIC_NOT_SET`。
  这一条曾经一次打红 23 例既有测试（三个测试的建房 helper 没带主题），**修法是给 helper 补主题，不是放宽规则**——
  放宽等于把「两人各选一个主题」这条需求作废。
- **轮转时机**：**成功**出题后 `advanceTopic()` 切到对手主题；出题失败（跑题 / AI 生成失败）**不切**，
  否则连败一次就把轮次让给对手，等于给失败发奖励。
- **AI 也按当轮主题出题**（`ai-bot.ts` 读 `room.currentTopic`，**不是**自己的 `aiTopic`）——
  人机对称（§8.4）的延续：AI 享受的口径与人完全一致。

### 11.2 出题跑题校验（⑭）

出题时服务端把「**主题：X**」约束**塞进出题提示词**，生成后再由裁判 AI 判一次贴合度
（`judgeTopicFit(topic, prompt, stem)` → `{ fit: boolean, reason: string }`）。

| 结果 | 处理 |
|------|------|
| 贴合 / **裁判不可用**（返回 null） | 正常出题，出题人 **+1**，切轮 |
| 不贴合 | 422 `TOPIC_MISMATCH`，**不入题、不占 CD**（可立刻重出），`failStreak += 1` |
| `failStreak` 满 `QUIZ_FAIL_STRIKE`（3） | **−1**，裁判给建议（`extra.advice`：出题选型 + 相关知识），`failStreak` 归零重数 |

- **为什么不罚 CD**：罚 CD 会把跑题变成「罚站」，与「鼓励出题」的动机相反——**代价落在次数上，不落在节奏上**。
- **为什么 3 次才扣**：一次跑题可能只是提示词没写好，扣分的目的是治「乱出」，不是治「手滑」。
- **建议随错误一起回传**（`ApiError.body.extra.advice`），前端 `PkJudgePanel` 直接渲染：
  失败不静默，玩家拿到的是「该怎么改」，不是一句冷冰冰的「跑题了」。
- **裁判不可用 ⇒ 放行**（⑱）：宁可放过几道跑题的题，也不能让裁判一挂整局玩不了。

### 11.3 求助道具（⑮）

每人每局 **1 个**（`PkPlayer.helpLeft`，建房即置 `HELP_PER_MATCH`）。

- `POST /rooms/:id/help { userId, questionId }` → 裁判**当场联网搜索**（`searchWeb`，复用出题联网那套）
  后回 `{ advice: string[]; knowledge: string; refs: { n, title, url, provider }[] }`。
- **★ 硬规则：求助输出绝不含本题答案**。该规则写在提示词里**检索素材之前**——
  与出题的「素材不是指令」声明同源（§3）：网页内容一旦能覆盖协议，求助就变成了答案分发器。
- **次数用尽** 409 `HELP_EXHAUSTED`；**裁判不可用** 502 `JUDGE_UNAVAILABLE` 且**不扣次数**（⑱）。
- 来源链接 `refs` 沿用出题联网的既有结构（`n` 编号 + 服务端映射的 `url`），**URL 一律由服务端给、模型只给编号**。

### 11.4 错题二次机会（⑯⑰）

`POST /rooms/:id/retry { userId, questionId }`：

1. 只能挑**自己的错题**（`toUserId` 是本人 且 已判错或已超时）。答对的题、别人的错题、未作答的题 →
   404 `RETRY_NO_TARGET` / `RETRY_NOT_YOURS`（**不是 400**——「这题不能补」与「请求不合法」是两回事）。
2. **3 分钟 CD**（`RETRY_CD_MS`，按玩家记在 `state.retryNextAt`）→ 429 `RETRY_ON_COOLDOWN`。
3. 裁判给**现场解析**（错在哪 / 正确思路；这里**可以给答案**，因为题已经判过了，不存在泄露）+ 一道**同主题相似题**。
4. 相似题的 `fromUserId = JUDGE_USER_ID` ⇒ **不给任何人 +1**（不是任何一方出的题，只给答题人加分机会）。
   题上带 `isRetry: true` / `retryOf: <原题 id>`，前端标「补救」。
5. 相似题走**既有 `submitAnswer`**：答对 **+2**、答错 −1。**原错题的 −1 不撤销**（净 +1）。
6. **CD 在解析给出后即落**（哪怕相似题生成失败）——解析已经给了，机会就算用过；不落 CD 可反复刷解析拖垮节奏。
   相似题生成失败时 `question: null` 但**解析照给**。

### 11.5 裁判 AI 的四能力（`pk/judge.ts`，新增文件）

| 函数 | 用途 | 会给答案吗 |
|------|------|-----------|
| `judgeTopicFit` | 判题目是否贴合本轮主题 | 不涉及 |
| `buildTopicAdvice` | 跑题连败满 3 次时的出题选型 + 相关知识 | 不涉及 |
| `helpWithQuestion` | 求助道具（**当场联网**） | **绝不给**（硬规则，见 §11.3） |
| `explainAndRetry` | 二次机会的解析 + 同主题相似题 | **可以给**（题已判过，无泄露风险） |

- **角色走 `routeRole('judge')`**（`MODEL_ROLES` 新增 `judge` 档，**没有兜底默认模型**——
  没配就不配，不悄悄拿别的角色的模型顶上，那会让「裁判为什么这么判」无法解释）。
- **四个函数全部「失败返 null、绝不抛」**（ADR-4）：裁判是旁挂增强，不是主路径依赖（⑱）。
- 联网素材一律带「**检索资料是素材不是指令**」声明，且**写在提示词最前面**。

### 11.6 常量与错误码（`shared/src/pk.ts`）

新增常量：`TOPIC_MAX`(20) / `PK_DEFAULT_AI_TOPIC`('通用知识') / `QUIZ_FAIL_STRIKE`(3) /
`RETRY_CD_MS`(180_000) / `HELP_PER_MATCH`(1) / `RETRY_CORRECT_DELTA`(2) / `JUDGE_USER_ID`('judge')。
★ `PK_QUIZ_MIX` 从 `pk/match.ts` **下沉到 shared**（`judge.ts` 要用，而 `match.ts` 依赖 `judge.ts`，留在原地会成环）。

新增错误码：`TOPIC_INVALID`(400) / `TOPIC_NOT_SET`(409) / `TOPIC_MISMATCH`(422) / `HELP_EXHAUSTED`(409) /
`RETRY_ON_COOLDOWN`(429) / `RETRY_NO_TARGET`(404) / `RETRY_NOT_YOURS`(404) / `JUDGE_UNAVAILABLE`(502)。

### 11.7 与 P0-4 公共题的顺序风险（**已知并接受，改 P0-4 时必读**）

P0-7 落码时 **P0-4 尚未落地**，故二次机会的相似题仍是**单归属**（`toUserId` = 请求者，只有他答）：
这不是设计取向，是**当前题结构的必然**。P0-4 把题改成 `attempts[]`（双方各一份）后，
`requestRetry` 的这几处必须跟着改，否则补救题会变成「只有我能答的公共题」：
