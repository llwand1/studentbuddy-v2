## 0. 一句话与七元素口径

**把「一个会说人话、会求救、能拿词条等你来换」的 AI 学习伙伴放到知识大陆上，而且他是你亲手安置的**——
它是 AI 能力的**可见载体**（用户看得见、点得着、说得上话），也是「开疆拓土」的正反馈。

需求所列的七元素与本册的对应关系（逐条钉死，防止实现漂移）：

| # | 元素 | 落地口径 | 本节 |
| - | ---- | -------- | ---- |
| ① | NPC 接入 AI | 新增 `npc` 模型角色；对话无 key 时**降级到本地台词**（不静默、不说"AI 坏了"）；**创建时也由他起名与人设** | §4 |
| ② | 扩展辅助学习功能 | 对话里伙伴会**就自己守的那条词条**提问／给线索；交换直接送**没见过的词条** | §4 / §6 |
| ③ | 宣传点「创建你的 AI 学习伙伴」 | **玩家在地图上点一格创建**；可改名；花名册落 `app_settings` | §2 / §3 |
| ④ | 与任务清单联动 | NPC 遇怪 ⇒ 派一条 **`npc_rescue`** 求救单；**任务清单顶上另挂"伙伴名额进度"** | §5 |
| ⑤ | 可与 NPC 对话交互 | `POST /api/npc/:id/talk`，上下文 = 人设 + 他守的词条 + 附近的怪 | §4 |
| ⑥ | 卡牌交换 | 拿一张**自己的**卡当信物 ⇒ 换回**同领域没见过的**新词条（复用既有宝箱账本） | §6 |
| ⑦ | NPC 数量受地图大小限制 | ★ **伙伴创建那次改动**：数量由**玩家创建**决定，上限 `npcCapFor(世界半径)`（6～24），门票＝已完成任务数（+ 锚定词条熟度） | §2 |

★★ **本册的立命之本是「零新表、零新迁移」**（与知识大陆优化改动、卡牌改动同一条红线）：七元素里没有一条
需要新账本——求救单是 `study_task` 的第四种 `kind`、交换流水是 `chest_open` 的第三种 `source_kind`、
**伙伴花名册是 `app_settings` 的一个键**。**任何实现方案只要动到 `migrations-list-*.ts`，就是走错了路。**

★★ **2026-09-27 伙伴创建那次改动调整口径**：伙伴**不再按词条数自动派生**——
「每 8 条词条多一位」与 `placeNpcs` 自动派位**整套退役**，改成**玩家在地图上点一格创建**（他守那一格上的词条）。
四项裁定：① **门票＝多个条件**：第 1 位无条件，第 N≥2 位需「已完成任务数 ≥ `3×(N-1)`」**且**锚定词条
`cards≥2`（★1 以上）；② **落位＝玩家自己点格子放**；③ 库里按旧口径存下的那些（本机 9 位）→ **只留一位开局伙伴**
（自愈迁移就地固化，其余清掉）；④ **创建时让 AI 起名 + 一句人设**。
★ 位置因此**改为存库**（玩家点的那一格）——存得起靠开放世界那次改动的**有符号固定中心坐标**：世界半径只增不减 ⇒
已存坐标永不失效（换成旧口径"左上角起算"的坐标，这张表一加词就得整体迁移）。
★ 另新增 `DELETE /api/npc/:id`「让他回家」（**真删**：门票按名册序号算，留一个隐身位就是免费刷位）。

★ **落地后的三处分工修正**：① 交换那一行 `chest_open` 的写口落在 `learning/npc.ts` 的 `grantTradeDraw`，
**不在** `chest.ts`——同一张表上的两套付账规则（扣钥匙／不扣钥匙）分开住既贴切，也让 `chest.ts` 守住了
400 行红线；② 前端取数与横幅拆出了 `continent-partners.tsx`；③ 伙伴创建那次改动之后姓名的**归属**也变了：
名字不再是"主伙伴专用一个 KV"，而是**每位伙伴自己的字段**（见 §3）。三处都是**红线与语义逼出来的拆法**。

## 1. 边界：与既有三册的分工线

- **边界①：NPC 不是第二套怪、不是第二套卡。** 伙伴不占格（不参与领地扩散、不挡英雄走位），
  他也不发卡——交换落的是**既有** `chest_open` 流水，"收下"走**既有** `POST /api/cards/chest/accept`。
  ⇒ 卡数口径（`TERM-CARDS-SPEC` §1）一字未动，从宝箱来的词条与从 NPC 来的词条**在卡墙上长得一样**。
- **边界②：伙伴不新增刷新频率。** 地图取数仍只有 `GET /api/terms/review/map` 一条只读口；
  NPC 列表随 `GET /api/npc` 单取一次，**不轮询、不订阅新 SSE**（对话是请求-响应，不是推送）。
  ★ 伙伴创建那次改动新加的那份"名额门票"挂在**既有** `GET /api/cards/state` 上（便宜口径，见 §2.3），也没有新连接。
- **边界③：伙伴不替用户做学习动作。** 他会催、会给线索、会求救，但**不代答、不改复习阶段、
  不写复习流水**。解除占领的唯一路径仍是「答对那道题」（`KNOWLEDGE-CONTINENT-SPEC`）。

## 2. 数量与位置：玩家创建 + 名额门票

### 2.1 数量

```
npcQuotaFor(ownerId, count) = { count, max, doneTasks, needTasks, canCreate, blockedBy }
  count     = 花名册在册人数
  max       = npcCapFor(worldRadiusFor(词条数))            // 6 ～ 24（跟世界涨，开放世界那次改动）
  doneTasks = COUNT(study_task WHERE status='done')       // 门票的账本（零新表）
  needTasks = npcTasksRequiredFor(count + 1)              // 第 1 位 0，第 N≥2 位 3×(N-1)
npcCapFor(radius) = clamp(floor((2*radius+1)^2 / 40), NPC_MAX_MIN=6, NPC_MAX_CAP=24)   // ≈ 每 40 格站 1 位
NPC_TASKS_PER_PARTNER = 3
```

- ★★ **上限跟世界半径走（开放世界那次改动，裁定「跟着世界涨」）**：世界开放后地图不再封在 140 格，若上限仍写死 6，
  327 条词条就顶死、加词再无奖励 ⇒ 与 ⑦「鼓励开疆拓土」相悖。本机实测：`R=9 ⇒ cap 9`；`R=7 ⇒ cap 6`；
  `R=20 ⇒ cap 24`（封顶）。⚠️ 密度口径是**产品感受值**（把握度中）：要调只改 `npcCapFor` 一处。
- ★★ **`count` 是唯一"数量"，且它来自花名册**（不再是词条数的派生量）：**玩家创建几位就有几位**。
  ⇒ 「不要那么多」这条要求由**门票**承担，不由派生公式承担（派生公式那套已退役）。
- ⚠️ **键缺失时的便宜口径（如实写）**：`npc_party` 键不存在（旧库）时，`partyCountFor` 报 **1**（库里有词条）
  或 **0**（空库）——因为下一次读到地图时 `syncParty` 会把**开局伙伴**固化出来（§3）。
  报 0 会让任务清单说"可创建 1 位"、而地图上立刻已经有 1 位（两条记录互相打脸）。
  ⚠️ 一个**已知的窄边角**：有词条却一格都没冒怪的地（到期词条全在复习范围）时迁移不会写键，
  于是便宜口径报 1 而地图上 0 位——这条**只有大陆页的横幅会如实说**（"这块地上暂时站不下伙伴"）。

### 2.2 位置：玩家点的那一格，**存库**

```
POST /api/npc { row, col }             // row/col = 玩家在地图上点的那一格
  ① 门票：npcQuota.canCreate 必须为真（§2.3）
  ② 那一格必须是 scanMap.candidates 里的格（**有词条 + 没冒怪**）
     · 不在候选里：是怪的本体格 ⇒ "这一格被「X」的怪占着"；否则 ⇒ "得挑一块有词条、没冒怪的地"
  ③ 同一条词条不能已经有伙伴守着 ⇒ "「X」已经有一位伙伴守着了——换一格吧"
  ④ 第 2 位起：锚定词条要 cards ≥ 2（NPC_TRADE_MIN_CARDS）
  ⑤ 起名与人设（§4.4）⇒ 追加一条花名册成员 { id: npc:<termId>, name, bio, termId, row, col }
```

- ★ **为什么要锚定 `termId`**：伙伴得有个「他懂的那一块知识」才能说人话（§4 的提问、§6 的交换领域
  都从这里取）。⇒ 他守的词条 = 玩家安置他时点的那一格上的词条。
- ★★ **创建之后不再自动搬走**：那一格后来冒出了怪（逾期词条）时，他**留在原地**并判为**遇险（距离 0）**
  ——这正是"他的地被夺走了"，也是本玩法最想被看见的一幕。旧口径那条"先过滤 `!hasMonster` 再取"
  是**自动派位**的规则，随自动派位一起退役（`npcDistress` 现在允许距离 0，见 §5.1）。
- ★ **同一格/同一条词条只许一位**：`parseNpcParty` 按 `id`（= `npc:<termId>`）与 `row,col` 两把尺子去重，
  创建时再校验一次（§2.2 ③）——两处都要守，因为写库那条路（自愈迁移）不经过创建校验。
- ★ **伙伴不占格**：他**不进** `spreadLands` 的 `blocked`、不改 `walkable`。
  ⇒ 走位／领地／点击分流的既有逻辑**一行未改**（这是"接入而非改造"的直接好处）。
- ★ **锚定词条被删** ⇒ 那位伙伴自动出册（他守的知识没了，"他是谁"就说不清了）；由 `syncParty` 在
  每次读花名册时清（§3 的"防挂单"）。

### 2.3 门票：三个条件，各说一句人话

1. **名额**：在册数 < `npcCapFor(世界半径)`。满了 ⇒「这块大陆最多站 N 位伙伴——先让一位回家，位置就空出来了。」
2. **任务**：已完成任务数 ≥ `npcTasksRequiredFor(在册数 + 1)`。不够 ⇒「还差 M 单任务，就能再创建一位伙伴。」
3. **熟度**（第 2 位起）：锚定词条 `cards ≥ 2`。不够 ⇒「这位伙伴得守一条你熟的词条（★1 以上，至少 2 张卡）。」

- ★★ **第 1 位无条件**（`needTasks = 0`）：宣传点是「创建你的 AI 学习伙伴」，用户第一眼必须创建得出来；
  一上来就要 3 单任务，他看到的是一枚永远灰着的钮——"这个功能是坏的"。
- ★★ **账本用既有 `study_task` 的 `status='done'` 行数**（零新表）：它天然把「推进／破停滞／补池／救伙伴」
  四类单都算进来——**做过的事都算**。
- ★★ **门票按名册序号算，不按"历史创建次数"**：否则"让他回家再重建"就是免费刷位（这也是 `DELETE`
  必须**真删**的原因）。
- ★ **三条各一句人话**（`NpcQuota.blockedBy` 由**服务端**算好）：压成一句"暂时不能创建"，用户就永远
  不知道该去做什么。UI 直接显示这句话，**不许自己按 count/max 再编理由**。
- ★ **为什么这份读数要挂在 `GET /api/cards/state`**：任务清单要显示"还差几单"，而 `doneTasks` 就是
  `/state` 里 `tasks` 的 `done` 行数——**同一个瞬间**读出来，才不会出现"清单说做完了 3 单、
  进度却说还差 3 单"。它是**便宜口径**（两条 COUNT + 一次 `app_settings` 读，**不铺图**）⇒ 挂在被
  轮询的 `/state` 上不怕；地图那份（含可落位格）在 `GET /api/npc`，只有进大陆页才拉。

## 3. 身份：花名册落 `app_settings.npc_party`

- 键：`SETTING_KEY_NPC_PARTY = 'npc_party'`，值 = JSON `{ members: NpcPartyMember[] }`，
  成员 = `{ id, name, bio, termId, row, col }`（`id` = `npc:<termId>`）。
- ★★ **写就写整份、从不删键**：键在 = "这个库已经初始化过"。若空册时删键，自愈迁移会在下一次读到时
  又把开局伙伴放回来——"让他回家"当场失效。
- ★★ **自愈迁移**（`syncParty`，旧库升级的唯一入口）：
  - 键缺失 + 库里有词条 ⇒ 取**旧口径哈希序第 0 位**（`continentHash('npc|' + termId)` 升序，同值按
    `termId` 升序）就地固化一位"开局伙伴"——**与升级前地图上看到的是同一位**，位置一致、用户无感；
  - 键缺失 + 空库 ⇒ 固化一个**空册**（免得以后加了词条凭空冒出一位——玩家创建的才该出现在地图上）；
  - 键缺失 + 有词条却没一格可站 ⇒ **不写键**，下次读到地图再试（§2.1 那条窄边角）。
- ★ **防挂单**：锚定词条被删掉的成员在读取时出册并回写。
- ★ **容错解析**（`parseNpcParty`，数据容错 ADR-6）：坏 JSON／缺字段／坐标不是有限数 ⇒ **跳过该条而不抛**；
  缺 `id` 时按 `npc:<termId>` 补齐；条数封顶 `NPC_MAX_CAP`。
- 写：`PUT /api/npc/:id`（改名）、`DELETE /api/npc/:id`（解散）。改名归一化（去首尾空白、按码点截到
  `NPC_NAME_MAX = 12` 字），**空串是入参错（400）**——伙伴创建那次改动之后每位伙伴都有存下来的名字，"清空"不是一个动作。
- ★★ **名字属于"那一位伙伴"，不再属于"主伙伴"**：伙伴创建那次改动之后没有任何"第 0 位特殊"的规则
  （旧口径那套"名字存单键、跟着第 0 位走"随自动派位一起退役）。

## 4. AI 接入：`npc` 角色 + 起名 + 本地降级

### 4.1 角色

- `shared/src/domain.ts` 的 `ModelRole` 加 `'npc'`；`llm/router.ts` 的 `MODEL_ROLES` 加
  `{ role: 'npc', label: '学习伙伴（大陆 NPC）' }`。★ 数组驱动 ⇒ 默认种子与设置页自动带上，**无需迁移**。
- **降级链**（照 `coach` 的既有形状，理由同源）：`npc` 角色未绑定 ⇒ 回退 `explain`（讲解）。
  伙伴对话本质是日常对话，用讲解模型是合理默认；老库升级后 `role_bindings` 里本就没有这一行，
  若按"必须绑定"处理，用户看到的是「该角色还没绑定模型」而他从没改过任何设置。
- ★ 这条链由 `resolveNpcTarget` 提供**唯一口径**，**对话与起名共用**（住 `npc-genesis.ts`：那里不依赖
  `npc.ts`，也就不出 `genesis → talk → npc.ts` 那个环）。

### 4.2 无 key 时的降级台词（★ 本册最容易被做错的一处）

- `resolveNpcTarget` 返回 null、或 `model`/`apiKey` 为空 ⇒ **走 `NPC_FALLBACK_LINES`**：
  按 `continentHash(`${npcId}|${轮次}`)` 从台词池里选一条，**永不报错、永不空回**。
- ★ **为什么降级而不是报错**：NPC 是**地图上的常驻元素**，用户点他是"想跟伙伴说句话"，
  不是"提交一次模型调用"。报「没有可用的服务商」会让地图上多出一块**坏掉的功能**——
  这正是立项要消灭的观感（"AI 含量太少"）。
- ★ **但降级必须可识别**：响应体带 `source: 'ai' | 'fallback'`，UI 在 fallback 时说清
  「伙伴现在靠固定台词应答——到设置里给他绑一个模型，他就能真的聊起来」。
  **降级可以，假装没降级不行**（ADR-5 的"报错说真话"在这里的等价物是"降级说真话"）。
- 台词池**只谈他守的那条词条与其领域**，不编造用户进度（编就会与卡墙/task 的数字对不上）。

### 4.3 对话上下文（送给模型的就这几块）

人设（伙伴名 + 他守的词条 + 领域）+ **他当前是否遇险**（§5 的结论）+ 本轮用户输入。
★ **不带用户的完整卡墙/复习流水**：伙伴的职责是"陪聊＋守好自己那块地"，把全库塞进上下文
既费钱，又会让他说出与任务清单打架的话（"你还有 5 条欠账"由 `coach` 说，不由 NPC 说）。

- 温度 `0.8`（比 coach 的 0.6 高：伙伴要有人味）、上限 `NPC_MAX_TOKENS = 600`（短对话）。

### 4.4 创建时起名与人设（伙伴创建那次改动新增，`npc-genesis.ts`）

```
generateNpcIdentity({ ownerId, termId, term, domain }) → { name, bio, source }
  · 提示词要求**只回一个 JSON 对象**：{ "name": "…", "bio": "…" }
    name：2~6 字，像住在附近的人的名字/绰号，不许"助手/AI/小助手"
    bio ：第一人称一句话、带一点脾气或习惯，≤ NPC_BIO_MAX = 40 字
  · 解析：从输出里抠**第一个** JSON 对象（不要求整段是 JSON，模型常带一句解释）
  · 归一化：name/bio 各按码点截断；**两样都要非空**，否则整份回退
  · 回退（无 key／上游抖动／解析失败／只拿回一半）：name = npcNameFromPool(termId)、
    bio = npcTemplateBio(term)，并标 source = 'fallback'
```

- ★★ **"只拿回一半"也整份回退**：否则会出现"AI 的名字 + 模板的人设"这种半吊子，还把它标成
  `source:'ai'`——降级可以，假装没降级不行。
- ★ **人设不许编造用户进度**（同台词池那条判断标准）：只许谈他守的词条与领域。
- ★ **本地兜底全是确定性的**（`npcNameFromPool` 按 `continentHash('npcname|' + termId)` 选址）：
  同一个词条每次兜底都同一位，可单测、可复现。
- ★ **UI 要说真话**：`source === 'fallback'` 时创建成功的横幅里补一句"名字是本地起的；到设置里绑个模型，
  他会自己取"（与 §4.2 同一条纪律）。

## 5. 与任务清单联动

### 5.1 判断标准：什么叫「遇怪求救」

```
npcDistress(npc, monsterCells) = 曼哈顿距离 ≤ NPC_DANGER_RANGE(1) 的最近怪的本体
  ⇒ 有 ⇒ { termId, term, distance }（威胁）
  ⇒ 无 ⇒ null
```

- 输入只有「怪的本体格」（`!hasMonster` 的格不会出现）；**领地格不算威胁源**——
  领地是怪**已经**吞下的地，伙伴站在上面是"地丢了"，不是"被围住"，两者文案不同（§7.4）。
- ★ 距离取 1（正相邻），与「靠近才开打」（`canStrike`）**同一条判断标准**：伙伴喊"救命"的位置，
  就是用户**一步就能打到**的位置。距离放宽到 2 会出现"他说被围住了，我却够不着"。
- ★★ **距离 0 是合法威胁**（伙伴创建那次改动）：怪正好压在他守着的那一格上——"他的地被夺走了"。
  旧口径靠"先过滤 `!hasMonster`"回避这件事，那条规则随自动派位一起退役（§2.2）。

### 5.2 派单

- `study_task.kind` 新增 `'npc_rescue'`（ASCII 键，同三条既有 kind 的判断标准）。
- 字段：`title = '去救「<伙伴名>」'`、`why = '它被「<词条>」的怪堵住了——答对那道题，怪就散了。'`、
  `termId = 威胁怪的词条 id`、`refId = npcId`、`dedupeKey = npcRescueDedupeKey(npcId)`（**不含会变的数**）。
- ★ **求救单派在队列最前**（`dispatchTasks` 的 intents 里 `npc_rescue` 置首）：它是**有时效**的
  （怪还在那儿），而"推进/破停滞/补池"三单随时可做。`MAX_OPEN_TASKS = 4` 的额度被占满时，
  先出局的该是那三单。
- ★ 遇险的伙伴**每位一单**，且**不占新的调度器**：仍挂既有 6 小时 tick（`TERM-CARDS-SPEC` §5）。

### 5.3 完成判断标准（`isDone`）

```
npc_rescue ⇒ refId 对应的伙伴「当前不再遇险」即完成
  · 怪被答对 ⇒ 状态离开 due/overdue ⇒ 怪消失 ⇒ 伙伴脱险 ⇒ 这单自动 done + 发一把钥匙
  · 词条被删 / 词条被移出复习范围 ⇒ 怪没了 ⇒ 同样脱险 ⇒ done
  · 伙伴本身没了（被「让他回家」删掉 / 锚定词条被删而出册）⇒ 不在遇险集合里 ⇒ done（★ 防挂单）
```

- ★★ **实现方式只有一句**：`isDone` 问 `learning/npc.ts` 要**当前遇险伙伴 id 的集合**，
  `refId` 不在里面就完成。⇒ "伙伴缺失判完成防挂单"那条要求**自动满足**，不需要单独分支。
- ★ 发钥匙仍走**唯一那处翻转**（`reconcileTasks` 的 `changes === 1`），本册不新增发钥匙路径。

### 5.4 任务清单上的「伙伴名额进度」（伙伴创建那次改动新增，点名「任务列表功能也要优化」）

- `TaskListPanel` 顶上常驻一条：`AI 学习伙伴 · 已有 N 位（最多 M 位）` + 一句进度
  （能创建 ⇒「已完成 K 单任务——现在就能去地图上再安置一位。」；不能 ⇒ `blockedBy` 原句）+
  一枚「去地图上安置」（切到知识大陆页，创建落点在那边）。
- ★★ **不新增第 5 种 `task kind`**：那会让"任务"这个词同时指两件事（要做的单／能不能建伙伴），
  而 `kind` 是四值联合类型，多一个值就要连带动 `KIND_LABEL` 与求救单那套判断标准。
- ★ 数与理由**都来自同一个 `NpcQuota`**（随 `/api/cards/state` 一起来，同一瞬间），UI 不自己算。

## 6. 交换：信物卡 → 同领域新词条

### 6.1 语义（★★ 一处被实测纠正过的口径，必须照此实现）

```
POST /api/npc/:id/trade  body { termId }   // termId = 用户拿出来的**信物卡**（自己的词条）
  · 信物必须 cards >= 2（`NPC_TRADE_MIN_CARDS`）——★0 的卡拿不出手（那是"刚记下来"，不是"我熟"）
  · 回的是一条**没见过的**新词条，且 domain 与信物**同领域**（伙伴只懂自己那一块）
  · **不花钥匙、不落信物账**；落账只写一行 `chest_open`（`source_kind='npc'`、`pool_slug=条目 slug`）
  · 收下这张卡走**既有** `POST /api/cards/chest/accept`（收下 / 收下并纳入复习两枚钮，一字不改）
  · ★ 写口是 `learning/npc.ts:grantTradeDraw`——**不动 `chest_keys`**（不扣免费次数、不扣赚来的钥匙）
```

### 6.2 ★★ 为什么信物**不能**存进 `chest_open.pool_slug`（实测纠正，别再写回去）

`pool_slug` 是**抽卡去重集**的键：`drawablePool()` 读 `chest_open.pool_slug` 判「本人已抽过」，
`ux_chest_open_pool` 是它的唯一索引。把信物卡 id 兼存进去会**立刻破坏抽卡去重**——
宝箱会重复抽出用户早就抽过的词。⇒ 信物卡**只作领域定向**（决定"回赠哪个领域"），**不落任何账**。

### 6.3 ★ 代价如实记：卡是**读数**不是道具，所以"给出信物"没有真实损耗

`TERM-CARDS-SPEC` §1 边界① 钉死了「卡数是流水派生，库里没有可扣的库存」。因此：

- **信物无法被消耗**（扣它就要么伪造流水、要么开一条只有 UI 知道的旁路账——两者都是 §1 明令禁止的）。
- ⇒ 交换的真实约束**只能落在别处**，本册用两条：
  1. **每日上限** `NPC_TRADES_PER_DAY = 2`：按 `chest_open` 里 `source_kind='npc' AND opened_day=今天`
     的行数判（`opened_day` 是既有列，**零迁移**做到了日级闸门）。
  2. **信物门槛** `cards >= 2`：用户得真的碰过那条词条（★1 以上）才有资格去换。
- ★ 用一句人话写进 UI 与文档，不让用户以为"卡被扣了"：**「换一次要挑一条你熟的词条
  （★1 以上）当信物——卡本身不会少，但每天只换得动两次。」**

### 6.4 选词与失败

- 选词：`drawablePool(ownerId)` 里**筛出信物同 domain** 的条目，按 `continentHash(`${npcId}|${slug}`)`
  升序取第一（**确定性**，同一伙伴同一次选择稳定；不随机 ⇒ 可单测）。
- 领域里没得换 ⇒ **回落全池**并如实告知（比"换不了"有用，且失败原因说清了）。
- 全池空 ⇒ `409`，文案与宝箱的 `empty` 一致（"词池里没有你没见过的新词了"）。
- 信物不存在 / 不是自己的 / `cards < 2` ⇒ `409`，三种各一句（不许压成一句"换不了"）。

## 7. HTTP 与 UI

### 7.1 路由：新册 `routes/npc.ts`，挂 `/api/npc`

| 方法 | 路径 | 说明 |
| ---- | ---- | ---- |
| GET | `/` | `{ partnerName, npcs: NpcView[], tradesLeft, quota, spots }`（一次读全，含处境与名额门票） |
| POST | `/` | `{ row, col }` 创建 ⇒ `{ state, memberId, source }`（★ 回**整份新状态**） |
| PUT | `/:id` | `{ name }` 改名 ⇒ `{ state }` |
| DELETE | `/:id` | 「让他回家」⇒ `{ state }` |
| POST | `/:id/talk` | `{ text }` → `{ reply, source }` |
| POST | `/:id/trade` | `{ termId }` → `{ draw }`（`draw.openId` 交给 `/api/cards/chest/accept`） |

- `NpcView = { id, name, bio, termId, term, domain, row, col, distressed, threat? }`。
  ★ **位置与处境结论都由服务端给**：前端不重算铺格/领地（双份口径 = 「图上画着伙伴遇险、
  清单里没有那单」的开端）。`spots`（可落位格）同理——它是"哪些格能站"的**服务端结论**。
- ★★ **三个写口都回整份 `NpcState`**：创建会改变名额与可落位格、解散会空出一格，只回"改成功了"
  会让前端立刻看到一份过期地图。
- ★ 端点**不新增 SSE 事件**：求救单的到达走既有 `task_dispatched`，`/state` 回读即可。

### 7.2 绘制（`continent-canvas.ts`）

- `drawNpc(ctx, spot, bob, distressed, pulse)`：像素小人（比英雄**矮一头**、戴橙帽）。
  ★ 与英雄的区别做在**高度 + 帽檐**两处，不只靠配色。遇险时头顶冒一个**红色惊叹块**（只动 `opacity`）。
- ★ 画序（**按实现定稿**）：**领地 → 宝箱 → 怪 → NPC → 英雄**。伙伴永远在怪之上
  （"他在怪的地盘上"要看得见，伙伴创建那次改动之后也包括"怪和他同格"）、在英雄之下（玩家自己的角色永不被遮）。
- ★ **选位态**（伙伴创建那次改动）：`ContinentMap` 收到 `placeSpots`（＝服务端给的 `spots`）时，把每一格画一个
  **绿框**（`COLOR.sprout`），与悬停的白框、锁定的金框区分开。★ **"给没给"就是选位态本身**，
  不另设布尔 prop——两个状态变量迟早会打架；且默认值必须是**稳定引用**（`NO_SPOTS`），
  否则绘制 effect 每帧重跑。
- ★ 只动 `transform`／`opacity`／颜色；`prefers-reduced-motion` 下 `bob = 0`、惊叹块常亮。
  ★ 惊叹块的呼吸**不新开 rAF 循环**：地图静止时停在当前相位。

### 7.3 交互

- **创建（选位态）**：横幅上的「创建伙伴」⇒ 进选位态（横幅改口径 + 地图标绿框）⇒ 玩家点一格 ⇒
  `POST /api/npc` ⇒ 成功退出选位态并说"他来了"（`fallback` 时补一句"名字是本地起的"）；
  **失败留在选位态**并把服务端那句话原样说出来（换一格再点就好）。「取消安置」可退。
  ★ **选位态优先于一切点击分流**：这一下点击的意思是"安置他"，不是走位/开打/看详情。
- **点伙伴** ⇒ 开对话面板：名字、人设、他守的词条、当前状态（安好／遇险）、对话框、
  信物选择（`cards>=2` 的词条下拉）、"换一条新词"按钮、剩余可换次数、**改名输入**、
  **「让他回家」（两段式）**。
- ★ **「让他回家」为什么两段式**：它不可撤销（且会占掉一个名额位，重建要重新交门票）。
  第一下只把按钮变成「确认送他回家」，第二下才真的调 `DELETE`。
- ★ 遇险时面板顶部给一个**直达按钮**：「去救他」⇒ 关面板 + 镜头/提示指向威胁怪（不代打）。
- ★ 对话输入与走位的冲突照既有形状：`frozen = hunting || chestAt || npcOpen` 时**键盘走位让位**。
- ★ **地图点击分流里伙伴排在宝箱之后**：宝箱是**一次性**的（开了就没），伙伴一直站在那儿。

### 7.4 文案必须说真话的五处

1. 空库：`quota.blockedBy` ⇒ "大陆上还没有词条——伙伴得有块地守，先去「词条」页加几条。"
2. 门票/名额：见 §2.3 那三句，**逐字用**（服务端算好，UI 不自己编理由）。
3. 降级（对话）：`source === 'fallback'` ⇒ "伙伴现在靠固定台词应答——到设置里给他绑一个模型就能真聊。"
4. 降级（起名）：`source === 'fallback'` ⇒ 创建成功的横幅里补"名字是本地起的；到设置里绑个模型，他会自己取"。
5. 交换代价：见 §6.3 那句原句，**逐字用**，不许改写成"消耗一张卡"。

## 8. 验证标准

1. **零迁移可证**：`git diff` 不含 `migrations-list-*.ts`；`study_task`/`chest_open`/`app_settings`
   三张既有表承担全部新状态。
2. **自愈迁移**：旧库（无 `npc_party` 键）读一次 ⇒ 固化出**旧口径哈希序第 0 位**那一位，
   位置与该定序的独立重算逐字段相同；空库 ⇒ 固化空册，之后加词条也不凭空冒人。
3. **门票**：第 1 位无条件（`doneTasks = 0` 也能建）；第 2 位起 `doneTasks < 3×(N-1)` ⇒ 409 且说清差几单；
   任务够了但锚定词条 `cards=1` ⇒ 409 且含「★1」。
4. **逐格校验**：荒地／怪的本体格／已有伙伴守着的词条格 ⇒ 三种 409、三句不同的话。
5. **遇险**：把某条 due 词的怪**答对** ⇒ 原本遇险的伙伴消失遇险标记、对应 `npc_rescue` 单翻 done
   且 `chest_keys.earned_keys` +1（同事务）。★ **距离 0** 也要判成遇险（怪压在他那一格上）。
6. **解散即完成**：把遇险的伙伴 `DELETE` 掉 ⇒ 那单自动 done（他不在遇险集里了，§5.3）。
7. **求救单幂等**：连跑两次 `dispatchTasks` ⇒ `npc_rescue` 行数增 0。
8. **交换**：信物 `cards=1` ⇒ 409；`cards>=2` 且同领域有可抽词 ⇒ 落一行 `chest_open`（`source_kind='npc'`）
   + 返回一条**库里没有**的词；当天换满 2 次后第三次 ⇒ 409（`opened_day` 日闸门实测）。
9. **无 key 环境** `POST /:id/talk` ⇒ `200` + `source='fallback'`，**不 5xx、不空串**；
   `POST /` 创建 ⇒ `source='fallback'` 且名字取自名字池。
10. `ownerId = null` 走 `ownerForWrite` ⇒ 只看无主行；`npc_rescue`/交换/花名册都不得串到别人。
11. `npm run check` 四连全绿；测试文件逐条登记进 `docs/TEST-PLAN.md`。

## 9. 不做什么（登记不欠账）

- **不做伙伴的等级/亲密度/好感度养成**（那需要新账本，破 §0 红线；要做得单独立册）。
- **不做伙伴代答/代复习**（边界③）。
- **不做伙伴之间的互动与对话**（NPC↔NPC 是另一个量级的系统）。
- **不做伙伴的"搬家"**（创建后位置固定；怪压上来就是遇险，玩家要救的是那块地，不是给他换地方）。
  要换位置只能"让他回家"再创建——那要重新交门票，这是有意的。
- **不做语音**（`TERM-CARDS-SPEC` §9 的合成音效已覆盖"有声"的最小面）。
- **不改 hero 区与对外文案的既有闸门**（项目内存红线：「概念图」承诺禁入对外文案）。
- **不给 `chest_open` 加 `npc_id` 列**（§6.3 已用 `source_kind` + `opened_day` 达成闸门；加列就要迁移）。
- **不给花名册建表**（§3；一个 `app_settings` 键足够，且键的存在本身就是"已初始化"这个状态）。
