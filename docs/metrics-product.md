# 产品度量框架（metrics-product）

> 状态：[活跃] | 建立：2026-09-24 | 维护：项目所有者本人
> 定位：回答「产品被真实使用得怎么样」的**唯一权威文档**。本文件只收**聚合数**（人数、条数、比例），
> 不收任何可定位到个体的字段（邮箱、IP、会话内容、设备指纹一律不进）。
> 与 `docs/metrics.md` 的分工：那份是**工程指标**（代码规模/测试/覆盖率，由 `tools/metrics.mjs` 产出、CI 漂移锁）；
> 本份是**产品使用指标**（线上库聚合读数，手工采集、每行带取证命令）。两份不许互相引用数字。

## §0 三条红线（先于一切数字）

1. **不得虚构**。每个数必须附「采集时间 + 数据源 + 复核命令」，读者自己能重跑。落不出这三样的数一律不进本文件。
2. **不得夸大**。GitHub clone 计数不是用户数（见 `project-growth.md` §2）；「测试账号」与「真实用户」在 users 表里同权，
   所以用户数一行永远带「其中含 owner 自己」的脚注。
3. **小样本不出百分比**。分母 < 30 时只报原始计数，禁一切「留存率 x%」「转化率 y%」表述——
   那是把噪声包装成结论，与本产品的诚实原则直接冲突（同 `GROWTH-SPEC.md` §0：只许放宽「什么算一次」，不许改标签）。

### §5.1 §2.2 那条 SQL 的「新用户」列必然错（现场复现于合成库）

**矛盾本身不需要生产库就能定罪**：6 与 58 出自**同一次采集、同一个库**，而
「各日新注册之和 ≤ 全表用户数」是恒成立的 ⇒ **两数必有一错，或两者口径不同却写在同一张表里**。
读 SQL 即定罪（不需要真库）：

```sql
(SELECT COUNT(*) FROM users u WHERE date(u.created_at)=date(m.created_at)) new_users
```

它数的是**用户行**，却挂在 `GROUP BY 消息日` 上——**跨行不跨次都不去重**，于是三重错：

1. **重复计数（把数抬高）**：某用户 A 注册于 09-19，但 09-21／09-22／09-23 都发过消息
   ⇒ A 的 `created_at` 日期同时命中这三个分组日，**一个人被记成三次「新注册」**。
   owner 自己的账号几乎必然踩中这一条（它在每一天都有消息）。
2. **时区口径不一致（把归属打乱）**：`date()` 吃的是 UTC 文本（真库 `messages.created_at` 是 UTC 且无 `ts` 列），
   而这张表的表头是 CST 日历日 ⇒ 边界 8 小时内的注册会被分到错误的日格。
3. **只能数到「有消息的那些日」**：注册后一句话没说的人**整行不出现**；反过来某天零消息那天就直接缺格。

★ **合成复现没复现出那个大数，而这件事本身就是结论**（一次内存库 `node:sqlite` 实验，零生产接触）：
照抄 §2.2 的 total 列造 6 个用户（每日 1 个）后，旧 SQL 逐行吐的是 `1,1,1,1,1,1`、列合计恰好＝全表 6。
⇒ 这条 SQL 的真正语义是「**该日注册的账号数**（在该日有消息的那些格里各重复报一次）」，
**它结构上不可能读出 28／14／11，除非 `users` 表里真有那么多当天注册的行**——而那与 §2.1 的 6 直接矛盾。
**三条可能，本会话无法在此分辨（诚实的未决，不是没查）**：
  a) 那一列被采集时打错／串了列（它和「user 消息」列形状太像：72/35/28 vs 28/14/11）；
  b) 同一条 SQL 里两处 `date()` 有一处吃的是别的字段（本文件没留当时的原始命令输出）；
  c) §2.1 的 `COUNT(*) FROM users` 与 §2.2 不是同一时刻读的（同一纸面写了「同一次采集」，但无日志可自证）。
⇒ 唯一的收口方式＝**在生产库上把两条数各跑一次**（§5.1 新 SQL ＋ §5.4 A1），A1 会自动判定谁在说谎。
★ 因此上面那三重错的定性要收着读：**它们都是这条 SQL 的固有缺陷（结构可判），但没有一条单独能解释 28 这个量级**
⇒ 本节只能定到「**这一列不可解释、不得引用**」，定不到「它把数抬高了」——那是超出证据的推断。
**旁证一条（main 在册，方向支持「真实日注册是个位数或 0」）**：`docs/AUTH-SPEC.md` §末尾那条
「同夜线上只读取证：GoatCounter 当日 27 PV、**新注册 0**」。

**替换 SQL（只从 `users` 表单表算 ⇒ 结构上不可能再超过全表数；日键统一本地，对齐 S1-a 那条「日键统一本地」裁决）**：

```sql
SELECT date(created_at, 'localtime') AS d, COUNT(*) AS new_users
FROM users GROUP BY d ORDER BY d;
```

⚠️ 换完之后的「新用户」列与 §2.2 那六格**不会相等**，而且方向不可预知（第 1 条把它抬高、第 3 条把它压低）
⇒ **必须重采一次才能落新表**；在那之前这一列只能标「不可引用」，不许拿差值编一个「修正后数字」。

### §5.4 四条一致性断言（§0 第 1 条的机器化，跑在任何只读副本上，零写入）

```sql
-- A1 注册总数 vs 按日新注册之和（§5.1 那次错就是它该红而没红；第二行 diff≠0 即口径漏了）
SELECT 'users_total' AS chk, COUNT(*) AS v FROM users
UNION ALL
SELECT 'sum_of_daily_new', SUM(n) FROM (
  SELECT COUNT(*) AS n FROM users GROUP BY date(created_at, 'localtime'));
-- A2 判决过的表不该再有新行（本批现查＝0 行；非 0 说明有别的写者，得查是谁）
SELECT 'quiz_stats' AS chk, COUNT(*) AS v FROM quiz_stats;
-- A3 event_log 的 kind 必须全部落在 OBS_KINDS 里（出现表外的 kind ＝ 有人绕过契约写它）
SELECT DISTINCT 'obs_kind_out_of_contract' AS chk, kind AS v FROM event_log
WHERE kind NOT IN ('tool_error','budget_cutoff','quiz_parse_fallback','quiz_svg_dropped',
                   'search_empty','thumbs_down','low_confidence','no_evidence','compact');
-- A4 复习是有流水的（它才是「记不记得」那条主线唯一现存的真实信号）
SELECT 'term_review_log' AS chk, COUNT(*) AS v FROM term_review_log;
```

⇒ **A1 是防止 6/58 这类事复发的最小闸**；A2 是防止「已下线功能还写库」的闸。
⚠️ **本批未收口**：这四条此刻**只是文档里的 SQL，没有任何工具在跑**（本文件不像 `README` 数字那样进 CI 门禁）。
要不要给它一把锁、锁在哪一层（新脚本／并入 `tools/metrics.mjs`／只做人肉清单），是另一次决策——见 §5.5 第 1 条。
