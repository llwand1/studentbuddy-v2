# 产品度量框架（metrics-product）

> 状态：[活跃] | 建立：2026-09-24 | 维护：项目所有者本人
> 定位：回答「产品被真实使用得怎么样」的**唯一权威文档**。本文件只收**聚合数**（人数、条数、比例），
> 不收任何可定位到个体的字段（邮箱、IP、会话内容、设备指纹一律不进）。
> 与 `docs/metrics.md` 的分工：那份是**工程指标**（代码规模/测试/覆盖率，由 `tools/metrics.mjs` 产出、CI 漂移锁）；
> 本份是**产品使用指标**（线上库聚合读数，手工采集、每行带取证命令）。两份不许互相引用数字。

---

## §0 三条红线（先于一切数字）

1. **不得虚构**。每个数必须附「采集时间 + 数据源 + 复核命令」，读者自己能重跑。落不出这三样的数一律不进本文件。
2. **不得夸大**。GitHub clone 计数不是用户数（见 `project-growth.md` §2）；「测试账号」与「真实用户」在 users 表里同权，
   所以用户数一行永远带「其中含 owner 自己」的脚注。
3. **小样本不出百分比**。分母 < 30 时只报原始计数，禁一切「留存率 x%」「转化率 y%」表述——
   那是把噪声包装成结论，与本产品的诚实原则直接冲突（同 `GROWTH-SPEC.md` §0：只许放宽「什么算一次」，不许改标签）。

## §1 指标分层：哪些现在能报、哪些必须等

| 层 | 指标 | 现状 | 前置条件 |
|---|---|---|---|
| L0 物理量 | 服务可用性、内存、延迟、上游成本 | ✅ 随时可报（watchdog 日志 + `platform_usage` 表） | 无 |
| L1 使用量 | 用户数、会话数、消息数、题库数 | ✅ 已落第一笔真账（§2） | 无 |
| L2 行为分布 | 功能使用占比、角色调用分布、工具命中率 | ⚠️ 可报计数，**不可报百分比结论** | 分母 ≥30（§0 第 3 条） |
| L3 留存/转化 | 次日留存、7 日活跃、注册→首次对话转化 | ❌ 暂不发布 | 遥测心跳（§3）+ 累计 ≥4 周真实流量 |

★ L3 挂起不是修辞，是**机制缺失**：`event_log` 自建立以来为空（v36 审计实测 0 行），
产品内没有「谁在什么时候打开了什么」的事件流；空库与"没人用"在现有设施内不可区分。
⇒ 恢复 L3 的唯一前提是先把遥测心跳做实，且心跳本身要能被证伪（有已知流量时读数非零）。

### §2.2 按日活跃（新用户 / user 消息 / assistant 消息 / 该日消息行总数）

| 日期 | 新用户 | user | assistant | 消息行总数 |
|---|---|---|---|---|
| 2026-09-19 | 1 | 0 | 1 | 1 |
| 2026-09-20 | 2 | 0 | 2 | 2 |
| 2026-09-21 | 2 | 4 | 4 | 8 |
| 2026-09-22 | 28 ² | 72 | — ² | 178 |
| 2026-09-23 | 14 | 35 | — ² | 76 |
| 2026-09-24（截至 14:09） | 11 | 28 | — ² | 60 |

² 09-22 起该列改报「消息行总数」而非 assistant 单列：当日 assistant 与 tool 角色行混在 total 里，
当时未逐角色拆分留档 ⇒ 本表 total 列可复核，assistant 拆分列**缺档就写缺档**，不回填估计值。

**取数 SQL（可整段重跑）：**

```sql
SELECT date(created_at) d,
       (SELECT COUNT(*) FROM users u WHERE date(u.created_at)=date(m.created_at)) new_users,
       SUM(role='user') user_msgs, SUM(role='assistant') asst_msgs, COUNT(*) total
FROM messages m GROUP BY d ORDER BY d;
```

### §2.3 由这笔记下的三个诚实结论

1. **使用是真实发生的**（9-21 起有非 owner 用户的对话），但量级是「个位数日活」，
   任何对外表述只能用绝对数，禁用「增长中」「用户量攀升」这类斜率词——6 天画不出一条可信斜率。
2. **刷题漏斗断在第一格**：3 个题库、0 条作答记录。这要么是功能没被走到，要么是作答链路对用户不可见——
   两种解释在现有遥测下**不可区分**（§3 心跳缺失的实例）。修复前本行不改。
3. **term_library 201 ≠ 用户价值**：绝大多数是 SEO 批次产物，报「词条 201+」时必须带这个脚注。

## §3 缺口登记（本文件欠什么账）

| 缺口 | 现状证据 | 补齐动作 | 补齐前本文件的限制 |
|---|---|---|---|
| 遥测心跳 | `event_log` 0 行（v36 审计），L3 全挂起 | 至少一条「服务活着且被访问」的周期写入，且能用已知流量证伪 | L3 行永远标 ❌，不许用 L1/L2 数字代答留存问题 |
| 按角色的模型调用分布 | 消息行有 role，但「explain/quiz-generator/…哪个被用」未留聚合位 | `event_log` 心跳落地后一并采集 | L2 只报得到消息总量 |
| 前端行为计数 | `/api/growth/counters`（GROWTH-SPEC）firstDay=2026-09-24，累计 app_open 7 / demo_enter 1 / register_done 1，单位 ip_day | 自然积累，无需施工 | 计数口径是「次」不是「人」，引用时必须带单位 |
