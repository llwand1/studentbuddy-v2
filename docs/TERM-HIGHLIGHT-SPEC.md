### v1.1 追加（英文发音）

- **[P-103]** 老板：「studentbuddyv2中的哪个词条显示的功能,对于英语单词要单独做一个特化,就是如果被标记的词是英语单词,那么就可以点击播放英文发音」
- **[P-104]** 老板（三选一拍板）：交互＝**卡片内加喇叭**（不占 span 点击手势）；引擎＝**浏览器本地语音**（Web Speech API）；范围＝**只改对话正文高亮**。

★ **为什么不是「点词直接发音」**：span 的 click 已被完整卡占用（v1.0 §3 拍板 G 方案）。把它改成发音，等于让「想深入看词条」这个更高频的诉求让位给发音，且要推翻已拍板的形态——**手势不能一个位置挂两个语义**。喇叭做成卡片内的独立按钮，两个诉求各得其所。
★ **为什么不选在线真人发音**（记账，防将来重复讨论）：本项目定位是**本地优先**，在线音频要联网、依赖第三方非契约接口（有失效与被墙风险）、离线不可用；而发音在本功能里是**辅助手段**（帮读音），不是内容本身，音质不构成选型理由。若日后要真人音，另立契约，不在本契约留开关。

## §1 目标与服务哪一环

**一句话**：词条库的匹配能力**已经存在**（`learning/term-usage.ts` 每轮回复完成后就在扫命中、+1 `usage_count`、落提及流水），但**只写进数据库、没上屏幕**——用户在对话里看不见「我刚才这段回答里用了哪些他学过的词条」。本功能把这条关系**显性化**：正文里的词条标出来，悬停看词条卡，点击能回写词条库。

- 服务闭环：**忆（M3 词条库）的读侧闭环**。词条库此前只有「词条库页」一个可见面；本功能让它在**对话现场**可见可用（ADR-1 自检通过，不新建第六环）。
- 入口闸门（§0.14）：三个月后被删的唯一可能是忆域整体换记忆机制 ⇒ 白写率低。
- 设计范式：取「**术语链接（term link）**」这一成熟做法（词典/维基/wiki 内链的既有直觉），不取它所属产品的包袱（不做词条页跳转即唯一出口、不做自动弹窗）。

## §3 交互形态（老板拍板 = demo 方案 G）

**一个组件的三个状态**，不是三个组件：

```
① 默认态（阅读中）  只有下划线：首现＝实线＋极淡底纹；复现＝虚点线
② 悬停态（想扫一眼）速览卡：词名 + 领域 + 释义 + 已用次数（锚定该词条，移开即走）
③ 点击态（想深入）  完整卡：＋别名 ＋复习状态 ＋动作按钮（点击后固定，点空白/× 关闭）
```

- ★ **为什么是两态而非二选一**：需求里藏着两个不同强度的诉求——「扫读时别打扰我」与「我要能点进去看全甚至操作」。参考 `COACH-SPEC` 的「一个组件两种状态」先例（胶囊↔抽屉），折叠态低打扰、展开态高承载。
- ★ **首现强调的口径：同一个渲染块内首次出现**（块 = 段落 / 列表项 / 引用行 / 表格单元格）。
  **为什么不做「整条回复内首现」**：那需要每个块知道自己在全文中的字符偏移，而 `parseBlocks` 只返回块、不返回偏移；为它改块协议（`lib/markdown.ts`）的收益不抵复杂度。块内首现已能消除长回复的主要视觉噪声（同一段里同一词出现 3 次不再变成一排框）。
- ★ **移动端没有 hover**：点击态是天然路径（tap 即弹完整卡），不需要为移动端单独做一套形态。
- 高亮元素必须是 `<span>`（不是 `<a>`）：它不是导航，是**信息浮现**；用 `<a>` 会误导用户以为会跳页，且污染「链接」的可访问性语义。

### §3.1 英文发音（v1.1 追加）

**位置**：喇叭是**卡片内的独立按钮**，紧跟词名右侧（`词名 🔊 领域 …`）——发音是「这个词的属性」，跟着词走最直观；卡片头部右侧已被「已用 N 次」与 `×` 占用，再塞会挤。**mini 与 full 两态都有**：速览态是 hover 即出的、最顺手的那一态，只在完整卡给等于让用户为了听读音多点一次。

★ **判定与朗读共用同一个输入 `say`（正文里显示的那段文本），不用 `item.term`**。这是本版最容易做错的一处：别名命中时正文显示 `closure`、而 `item.term` 是 `闭包`——用后者判定会**漏掉喇叭**，用后者朗读会**用英文语音读中文**。所以 `TermText` 给每个高亮 span 挂 `data-say={命中原文}`，判定与朗读都读它。

| 规则 | 口径 | 为什么 |
|---|---|---|
| 判定「是英语词」 | `isEnglishWord(say)`：trim 后非空、长度 ≤ 64、**至少一个拉丁字母**、且只由 `[A-Za-z0-9'’\-. ]` 构成 | 排除中文/日文词条（不发音）；排除 `C++`/`C#`/`A(B)` 这类符号型词条（读出来是噪音）；长度上限防「整句英文被当词条朗读」——词条本身是短术语，64 是防御性上限不是功能阈值 |
| 朗读引擎 | 浏览器本地语音（`speechSynthesis` + `SpeechSynthesisUtterance`，`lang='en-US'`） | 零依赖、零联网、离线可用，与「本地优先」同向（§0 已记账为何不用在线音频） |
| 不支持时 | **按钮不渲染**（`canSpeak()` 为假） | 同 §6「不做假按钮」：点了一定失败的按钮比没有按钮更糟 |
| 成功态 | 由**声音本身**承担，不刷文案 | 卡片内刷「已朗读」会让卡片抖动且毫无信息量；三态里的「成功」在这里的天然载体就是听到声音 |
| 失败态 | 必须给文案（复用卡片的 `msg` 行） | `AGENTS.md` 红线 5「操作必有成功/失败/进行中三态，禁止静默」——**系统没装英文语音时 `speak()` 会静默无声**，不提示等于用户以为功能坏了 |
| 连点/切词 | 每次朗读前 `cancel()` 上一句；被自己打断的（`canceled`/`interrupted`）**不算失败** | 不 `cancel` 会叠音；把「自己打断」当失败会让 UI 闪一条假报错 |

★ **朗读不因卡片关闭而中断**：用户点了发音就是要听，关卡片不代表要停（强行 `cancel` 会让「点完顺手关掉卡片」变成听不到）。本契约不做这个联动。
★ **发音与 `usage_count` 无关**：听读音不是「使用」这个词条，计数仍只由回复文本命中驱动（同 §7 末条）。

## §4 匹配口径（唯一事实源）

★ **规则上提到 `packages/shared/src/term-highlight.ts`，服务端与前端共用一份**。理由与 `doc-rag.ts` 常量双写、`ebbinghaus.ts` 判定双写同源：规则写两份，必然出现「服务端统计命中了 3 个、正文只标出 2 个」这种当场露馅的不一致。

| 规则 | 口径 | 为什么 |
|---|---|---|
| 匹配键 | `term` + `aliases`，**大小写不敏感** | 别名是 tidy 合并的产物（`TERM-TIDY-SPEC` §7.3 已定：别名在回复中出现照样计数），呈现侧必须同口径，否则「统计里有、屏幕上没有」 |
| 含拉丁字母的键 | `(?<![a-z0-9])…(?![a-z0-9])` **词边界** | 防子串误报：`let` 不该命中 `outlet`（既有实现已验证） |
| 纯中文键 | 子串匹配 | 中文无词边界概念 |
| 同一位置多个键命中 | 取**更长**者 | 防长词被短词截断（`机器学习` vs `机器`） |
| 匹配失败/空文本 | 返回空数组，不抛错 | ADR-4 失败隔离：高亮是次级功能，不能影响正文渲染 |

★ **服务端 `replyHitsKey` 改为调用 shared 的 `textHitsKey`（行为逐字等价）**——这是本次唯一碰服务端统计链路的改动，故必须由既有 `term-usage` / `terms` 测试锁住等价性。

## §5 数据路线：前端索引匹配（路线 ①）

```
TermIndexProvider（对话页挂载）
  → api.terms.list() 拉全量词条
  → 建索引：key(小写) → TermItem，并按长度降序缓存合并正则
  → 正文渲染时 findTermHits(text, keys) 一次扫描拿全部命中
```

**为什么不走服务端标注回传（路线 ②）**（记账，防将来重复讨论）：

1. **流式要求逐字即时高亮**——服务端 `countUsage` 在**回复完成后**才跑，路线 ② 只能等整段答完才上色，与「边出字边看」冲突；
2. **历史消息也要能高亮**——路线 ② 要么落「命中快照」（新增迁移 + 与词条变更失同步），要么每次回放重算（等于又回前端）；
3. **不改 SSE 契约**——本仓契约先行，加事件类型的成本远高于收益。

**代价与处置**：① 规则必须抽 shared（§4，已做）；② 词条量大时前端匹配有开销 → 合并正则**按索引缓存**（不是每次渲染重编译），且高亮挂在既有 `stableCut` 增量结构上（`stable` 块的命中结果随块 memo 复用，只有尾块每帧重扫）；③ 卡片数据**每次现取当前词条状态**，不做快照（用户改了释义/合并了别名，卡片跟着变）。

## §6 卡片内容与动作

| 档位 | 字段 | 来源 |
|---|---|---|
| 速览卡 | `term` / `domain` / `definition` / `usage_count` | `TermItem` |
| 完整卡 | ＋`aliases` ＋复习状态（`computeReviewState` → `reviewStateLabel`） | `TermItem` + `shared/ebbinghaus` |
| 两态共有 | ＋`say`（发音按钮的**判定与朗读共用输入**，`isEnglishWord(say)` 为真才出现） | **不是 `TermItem` 字段**——由 `TermText` 从命中原文注入（§3.1） |

**动作（只做真实存在的接口，不做假按钮）**：

| 动作 | 调用 | 说明 |
|---|---|---|
| 纳入复习 / 移出复习 | `api.terms.scopeTerm(id, enabled)` | 按当前 `review_in_scope` 决定方向；★ 纳入会**清零进度**（老板拍板），故反馈文案必须说出来 |
| 打开词条库 | `onOpenTerms(term)`（App 的 `openTerms`） | 带词条名直达词条库搜索（复用既有跨页入口） |
| **朗读发音**（v1.1） | `speakEnglish(say)`（`lib/speech.ts`） | **只读动作，不打任何接口**；仅当 `say` 判为英语词且浏览器支持时按钮才渲染（§3.1） |

⚠️ **「标记已掌握」不在本契约**：现有接口里没有它（复习推进只有 `POST /api/terms/:id/review {remembered}`，语义是「复习一次」而非「免复习」）。demo 里那个按钮是形态示意，**落地时必须砍掉或先立接口契约**——不做没有接口的按钮。

**词条不在复习范围时**：完整卡显示「未纳入复习范围」并把主按钮显示为「纳入复习」；已在范围内则显示复习状态 + 「移出复习」。

## §7 不做（范围红线）

- **不做高亮开关设置项**：首版不做（形态是拍板结果）。若实测视觉噪声不可接受，再单独立项。
- **不改 SSE 契约**、**不新增 HTTP 路由**、**不新增迁移**（本功能零 DB 改动）。
- **不在代码块 / 行内 `code` 内高亮**：代码里出现词条名（如 `let`）属于语法，标出来是污染。
- **不做「整条回复内首现」**（见 §3 口径说明）。
- **不做服务端命中清单回传**（见 §5）。
- **不碰 `usage_count` 统计口径**：高亮是纯读侧呈现，不因「用户看见了」而计数（计数仍只由回复文本命中驱动）。

### v1.1 追加的不做项

- **不做在线音频源**（真人发音）：见 §0 记账；要真人音另立契约。
- **不做「点高亮词即发音」**：span 的 click 归完整卡（§0 记账）。
- **不覆盖词条库页 / 复习卡 / 复习队列**（`[P-104]` 范围红线）：本次只改对话正文高亮。★ `lib/speech.ts` 刻意写成**不依赖对话页的通用工具**，将来要扩到 `TermsPage` 是零改造成本——但**本契约不承诺那个范围**，别拿「将来能用」当现在做了。
- **不做发音偏好设置**（语速 / 口音 / 音量 / 男女声）：用系统默认。做设置项要先答 §0.14「三个月后它会被删的原因」。
- **不做「发音失败」的自动重试或降级到在线音频**：失败就如实提示（§3.1 失败态）。

## §10 风险（§0.5）

| 级别 | 风险 | 处置 |
|---|---|---|
| P1 | **流式性能**：尾块每帧重解析，若每帧对全量词条重扫会掉帧 | 合并正则按索引**缓存**（索引不变则复用同一个 `RegExp` 实例）；命中结果随既有 `stableCut` 的 stable 块 memo 复用，只重扫尾块；实测长回复（>2000 字、词条 300+）确认无可感掉帧 |
| P1 | **服务端统计漂移**：`replyHitsKey` 上提后行为若不等价，`usage_count` 会静默变口径 | 抽 shared 时**逐字保留**原判定逻辑；既有 `terms.test.ts` / `term-usage` 用例全绿作为等价性证据；新增边界用例（词边界、大小写） |
| P2 | **误高亮泛词**：词条库里若有「引用」「快照」这类泛词，正文会花斑 | 本契约**不加停用词表**（拍脑袋阈值不可解释）；先上，靠「首现强调」压噪声；若实测不可接受，另立「泛词过滤」契约 |
| P2 | **卡片遮挡与边缘溢出** | 定位做视口边缘夹取 + 空间不足时上下翻转；卡片宽度固定、不超出容器 |
| P2 | **数据一致性**：用户在别处改了释义/合并了别名 | 卡片数据一律现取当前 `TermItem`（索引在会话开始与词条变更后刷新），不缓存释义文本 |
| P2 | **词条数增长**：全量拉取在词条上千时变重 | 首版直接全量（实测 278 条）；上千时再评估增量/分页，本契约不预做 |

### v1.1 追加的风险

| 级别 | 风险 | 处置 |
|---|---|---|
| P1 | **发音文本取错源**（拿 `item.term` 而不是命中原文）⇒ 别名命中时**漏掉按钮**，或**用英文语音读中文** | `data-say` 单源（§3.1）；`TermText.test.tsx` 有一条专测别名场景（断言读的是 `closure` 而非 `闭包`） |
| P2 | **系统没装英文语音时静默无声** ⇒ 用户以为功能坏了 | `onerror` 必须给文案（三态里的失败态）；`speech.test.ts` 钉住 |
| P2 | **自己 `cancel()` 被误判为失败** ⇒ UI 闪一条假报错，并把真失败淹没 | `canceled` / `interrupted` 一律 resolve（§3.1） |
| P2 | **移动端 / iOS 首次无声**（静音开关、需用户手势触发） | 点击本身满足手势要求；但**契约不承诺「一定响」**——系统侧因素不在本功能可控范围，如实记账，不假装已解决 |
| P2 | **切词时发音状态残留**（A 播着、B 的喇叭一上来就禁用） | 卡片 `key={active.term}` 强制重挂载；顺带修掉「A 的操作提示挂在 B 的卡上」这个既有小瑕疵 |
| P2 | **文本朗读的隐私/网络面** | 本地语音不出网，无隐私问题（这正是选它而非在线音频的理由之一，§0） |

## §11 验收（人工项，探针不替人做审美验收）

1. 对话里问一个已入库词条相关的问题 → 回复正文中该词**首现实线下划线**、复现虚点线；
2. 悬停 → 速览卡出现（词名/领域/释义/已用次数），移开消失；
3. 点击 → 卡片固定，出现别名、复习状态与两个动作；
4. 点「纳入复习」→ 词条库该词条变为已纳入（进度清零的提示文案必须出现）；
5. 点「打开词条库」→ 跳到词条库页且搜索框已填该词条名；
6. 长回复（含代码块）→ 代码块内**没有**高亮；正文滚动流畅无可感掉帧。

### v1.1 追加（英文发音）

7. 正文里的**英文词条**（如 `closure`）→ 卡片内有 🔊 → 点击**听到英文发音**；悬停的速览卡里也有；
8. **中文词条**（如 `闭包`）→ 卡片内**没有** 🔊；
9. ★ **别名命中**（正文显示 `closure`、主词条是 `闭包`）→ 卡片内**有** 🔊，且读的是 `closure`（不是「闭包」）；
10. 连点喇叭**不叠音**；系统没有英文语音时给出失败提示（**不许静默**）；
11. ⚠️ **本条需在真浏览器里人工听**：`jsdom` 里没有语音 API，自动化测试只能证明「接线对了」，
    证明不了「真的有声音」。若本机系统缺英文语音，第 7 条会表现为失败提示——那是**环境问题不是代码问题**，
    记在验收结论里，别当成 bug 去改代码。
